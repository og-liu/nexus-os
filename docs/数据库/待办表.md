# 待办表（todos）

> **一行 = 一件待办。** 它回答的问题是：「这个人还有哪些事没做完？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| 🚧 设计中 | 2026-10-20 | 2026-10-20 |

## 一、怎么理解它

待办是「要做的事」，不是「记下的话」:一行只有一句标题，没有正文、没有分类、没有到期日。它的一生只有两个状态——**没做完**和**做完了**，而「做完了」这件事本身带着一个时间。

它和便签（`sticky_notes`）是两种东西，别混：

| | 便签 | 待办 |
|---|---|---|
| 一句话 | 写完就忘，回头再翻 | 做完就打勾，勾完就该消失 |
| 有终点吗 | 没有 | 有，就是那个勾 |
| 越长越好吗 | 可以长 | 越短越好，超过 200 字就该改成便签 |

它和将来的日历 / 日程（还没建）也是两回事：待办问的是「**做什么**」，日程问的是「**什么时候做**」。本表刻意不含日期，就是为了不往日程的方向长（见 §七）。

## 二、这张表管什么

- **新建待办**：加一行（`title` + `user_id` + `created_at`，`completed_at` 留 NULL）
- **勾选完成**：把 `completed_at` 写成当前时间
- **取消勾选**：把 `completed_at` 改回 NULL
- **删除待办**：删掉这一行（没有软删除、没有回收站）
- **清除已完成**：`DELETE ... WHERE completed_at IS NOT NULL`
- **工具页列表**：读未完成（`completed_at IS NULL`，创建时间倒序）与已完成（`completed_at` 倒序）两段
- **首页待办卡**：读未完成的前 3 行 + 一个全局计数（已完成数 / 总数）
- 它**不**记录优先级、标签、所属清单、截止日期（见 §七）

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS todos (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id      INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title        TEXT    NOT NULL,
  completed_at INTEGER,
  created_at   INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_todos_user_id ON todos(user_id);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这件待办的内部编号 | 与 `users` / `sticky_notes` 同款：`AUTOINCREMENT` 保证编号永不复用 |
| `user_id` | INTEGER | NOT NULL，外键 → `users.id`，级联删除 | 这件待办属于谁 | 现在只有一个用户，但归属从第一天就写进数据里；级联删除保证删账号时不留无主的行 |
| `title` | TEXT | NOT NULL | 要做的那件事，一句话 | 只存纯文本：不存 HTML、不存 Markdown，渲染按纯文本显示，天然没有 XSS 面。上限 200 字（服务端校验），超过就该写成便签 |
| `completed_at` | INTEGER | **可为 NULL** | 什么时候做完的（毫秒时间戳）；**NULL = 还没做完** | **完成状态和完成时间是同一个事实，所以只存一列**。同时存一个 `done` 布尔，就可能出现「`done = 1` 但 `completed_at` 是 NULL」的矛盾行，而且没有约束拦得住。有这一列，排序（已完成区按完成时间倒序）也顺带解决了 |
| `created_at` | INTEGER | NOT NULL | 什么时候加进来的（毫秒时间戳） | 未完成区的排序依据（新加的在上）；也是排查时要的信息 |

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `idx_todos_user_id` | 显式建（`CREATE INDEX`） | 按用户取未完成 / 已完成两段：工具页列表、首页前 3 条、全局计数 |
| `sqlite_autoindex_todos_1` | 主键（rowid 别名） | 按 `id` 勾选 / 删除 |

**为什么按 `user_id` 建索引**：SQLite 只为 `UNIQUE` 和主键自动建索引，不为主键以外的外键建。查询天然按 `user_id` 过滤，索引要从现在就有。

**排序本身没有专门索引**：个人量级（几百行）走一遍索引扫描就够；等数据量或查询模式变了再考虑联合索引，现在提前建只会增加写放大。

## 六、常用查询

```sql
-- 未完成：新加的在上（工具页未完成区、首页前 3 条）
select id, title, created_at
from todos
where user_id = 1 and completed_at is null
order by created_at desc, id desc;

-- 首页卡：同样的排序，只取 3 条
select id, title
from todos
where user_id = 1 and completed_at is null
order by created_at desc, id desc
limit 3;

-- 已完成：最近做完的在上（工具页已完成区）
select id, title, completed_at
from todos
where user_id = 1 and completed_at is not null
order by completed_at desc, id desc;

-- 首页卡的计数（已完成 / 全部）
select count(*) as total, count(completed_at) as done
from todos where user_id = 1;

-- 看时间（毫秒转 +8 的人读时间）
select id, title,
       datetime(created_at/1000, 'unixepoch', '+8 hours') as created,
       datetime(completed_at/1000, 'unixepoch', '+8 hours') as completed
from todos order by id desc;
```

> `count(completed_at)` 只数非 NULL 的行——这是「只存 `completed_at`」顺手带来的好处，不需要再 `where done = 1`。

## 七、常见疑问

**Q：为什么没有 `done` 布尔列？**（`sticky_notes.pinned` 明明是布尔）
因为两件事的语义不同：置顶没有「什么时候置顶的」这种需求，布尔最省；完成有——已完成区要按「最近做完的在上」排。一个布尔加一个时间戳是**同一个事实存两处**，两列一旦不同步就是坏数据。这里的判据是 `completed_at is null`，只有一处能出错。

**Q：为什么没有 `updated_at`？**
本版不支持编辑标题，这一列没有写入时机。存一列永远不会更新的 `updated_at` 是**谎话**：读代码的人会以为改标题会刷新它。将来加编辑，按《数据库/README》§六 用幂等 `ALTER TABLE ... ADD COLUMN` 补上即可。

**Q：为什么表名叫 `todos`，不叫 `todo` 或 `todo_items`？**
表装的是多行，表名用复数（《数据库/README》§三）。`todos` 也没有和别的领域撞词——便签占掉了 `sticky_notes`，笔记留给以后的知识条目。

**Q：为什么不做到期日（`due_date`）？**
有日期就不再是「做什么」，而是「什么时候做」——要回答逾期怎么显示、时区怎么算、要不要提醒，而提醒要定时任务和通知通道。`todos` 刻意保持「下一步行动」的语义。真要日程，那是另一张表、另一个功能。

**Q：`completed_at` 可为 NULL，索引还有效吗？**
有效。SQLite 的普通索引用 NULL 做键，`is null` / `is not null` 都能走索引。真正要小心的是排序里 NULL 的位置（SQLite 把 NULL 排在最前），所以查询必须显式带上 `completed_at is null` 或 `is not null`，不靠 NULL 的排序位置。

**Q：清掉已完成会不会误删没做完的？**
不会——`DELETE ... WHERE user_id = ? and completed_at is not null`，未完成的 `completed_at` 是 NULL，条件不成立。
