# 出勤设置表（attendance_settings）

> **一行 = 一个人的周六制度。** 它回答的问题是：「这个人的周六，按单休、双休，还是单双休算？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已完成（v0.8.5） | 2026-10-23 | 2026-10-24 |

## 一、怎么理解它

单双休（大小周）看起来是「排班」，其实是**一条规则**：周六上不上班，两周一个循环。所以这张表只存**规则本身**，不存任何一天的具体结果：

- `saturday_mode` 说「哪一档」：单休（每周六上班）/ 双休（每周六休息）/ 单双休（两周交替）
- 选了单双休，才需要 `anchor_saturday` + `anchor_is_work` 两个锚点列：**从哪个周六起算、那一周算哪种**

具体某一天是班还是休，是**算出来的**（`lib/attendance/schedule.ts`），不落库。这就是它为什么这么瘦：一年 52 个周六一行数据都不占。

## 二、这张表管什么

- **保存制度**：UPSERT 一行（`user_id` 是主键，一个人只有一行）
- **单双休的锚点**：保存时把锚点重设到「本周六 + 本周类型」——用户永远只需回答「这周是哪种」，不用回答「三个月前某个周六上没上班」
- **恢复默认**：删掉这一行，回到内置默认制度（单双休、2026-10-24 那周双休）；**手动覆盖不受影响**（在另一张表里）
- 它**不**记录历史：换制度不保留「以前是什么制度」。需要留痕时再说

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS attendance_settings (
  user_id         INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  saturday_mode   TEXT    NOT NULL CHECK (saturday_mode IN ('work', 'off', 'alternate')),
  anchor_saturday TEXT,                    -- 仅 'alternate' 用：交替从哪个周六起算
  anchor_is_work  INTEGER CHECK (anchor_is_work IN (0, 1)),
  created_at      INTEGER NOT NULL,
  updated_at      INTEGER NOT NULL,
  -- 交替模式必须带锚点；单休 / 双休时两列为 NULL
  CHECK (saturday_mode <> 'alternate'
         OR (anchor_saturday IS NOT NULL AND anchor_is_work IS NOT NULL))
);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `user_id` | INTEGER | **主键**，外键 → `users.id`，级联删除 | 这份制度属于谁 | 一个人只有一份制度，所以它同时是主键：换制度是 UPSERT，天然不会堆出第二行 |
| `saturday_mode` | TEXT | NOT NULL，`CHECK` 只许三个字面量 | `work` = 单休（周六上班）、`off` = 双休（周六休息）、`alternate` = 单双休（大小周） | 存「周六这一天算不算上班」而不是制度名（`single`/`double` 会让人误以为在描述一周休几天）。`CHECK` 钉死三个值，写不进第四种 |
| `anchor_saturday` | TEXT | 可空，`YYYY-MM-DD` | 交替从哪个周六起算 | 每次读取都拿「今天所在那周」当起点，排出来的单双周会随日子往前走而漂；必须钉一个固定锚点 |
| `anchor_is_work` | INTEGER | 可空，`CHECK` 只许 0/1 | 锚点那一周的周六上不上班（`1` = 单休周） | 单双休的「相位」只有一个比特：知道某周是单休周，往后两周就推得出来 |
| `created_at` | INTEGER | NOT NULL | 第一次设制度的时间（毫秒时间戳） | 排查用；毫秒是数值，能直接比较（《数据库/README》§二） |
| `updated_at` | INTEGER | NOT NULL | 最后一次改制度的时间 | 有这个写入路径：UPSERT 时确实会改。`created_at` 保持第一次设定时的时刻，不被覆盖 |

**表级 `CHECK` 是两列的守门员**：选 `alternate` 就必须带锚点，选 `work`/`off` 时两列必须是 NULL（不给没在用的数据留位置）。

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `sqlite_autoindex_attendance_settings_1` | 主键（`user_id`） | 按用户取制度 —— 全部查询都是它 |

**不需要额外索引**：表里最多和用户数一样多的行，查询永远是 `WHERE user_id = ?`，主键就是那个索引。

## 六、常用查询

```sql
-- 这个人的周六制度
select saturday_mode, anchor_saturday, anchor_is_work
from attendance_settings where user_id = 1;

-- 谁设了单双休
select user_id, anchor_saturday, anchor_is_work
from attendance_settings where saturday_mode = 'alternate';
```

## 七、常见疑问

**Q：为什么表里可以没有行？**
没设过 ≠ 没有制度。`resolveDayStatus()` 用 `DEFAULT_SETTING` 兜底（单双休、2026-10-24 那周双休），所以新账号打开日历**直接有答案**，不会看到一片空白。表里有没有行只影响「要不要去改」，不影响「界面上有没有答案」。

**Q：为什么默认制度写死在代码里，不落进这张表？**
默认值写死是**同一份**，落库就意味着每个新账号要写一行「和默认一样」的数据——那是冗余，还会让「恢复默认」变成「写回默认」而不是「删掉」。默认值写死的代价是一年之后有人看到 `2026-10-24` 会疑惑，所以它在代码里带了注释说明为什么是固定日期（换成「今天所在那周」的话，相位会跟着日子漂）。

**Q：为什么加第三档（单双休）要整表重建？**
SQLite **改不了已有的 `CHECK` 约束**。老表的 `CHECK (saturday_mode IN ('work','off'))` 会把 `'alternate'` 直接拒掉，只能 改名 → 按新定义建表 → 搬行 → 删老表，整个过程包在事务里（`initSchema()` 的 `migrateAttendanceModeCheck`）。幂等判据是建表语句里有没有 `'alternate'`。

**Q：老库补锚点两列为什么没有 `CHECK`？**
`ALTER TABLE ADD COLUMN` 带不上表级 `CHECK`，所以 `migrateAttendanceAnchor` 补出来的两列只有应用层校验兜底；新库由 `SCHEMA` 里的 `CHECK` 管住。补出来的值一律 NULL（那一版只有单休 / 双休，本来就没有锚点）。
