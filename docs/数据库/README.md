# 数据库设计

> 这个目录回答**库层面**的问题：有哪些表、每张表一行是什么、库放在哪、改结构有什么规矩。
> **单张表的逐字段说明在各自文件里**（见下表）；某个功能为什么需要这些表见 `docs/功能/`；选型与连接配置见《技术栈说明》§3.5。
>
> 维护规则：**先改这里，再改代码。** 表结构的唯一权威是 `src/lib/auth/db.ts` 里的 `initSchema()`
> ——文档与代码不一致时，以代码为准，并立刻回来改文档。
> 结构有变化时，同一次改动要一起更新：本目录 + `initSchema()` + 对应功能文档 + 《开发日志》。

## 一、这里有哪些表

| 表 | 一行是什么 | 它回答的问题 | 详细说明 |
|---|---|---|---|
| `users` | 一行 = **一个人** | 这个账号**存在**吗？密码对不对？ | [`账号表.md`](./账号表.md) |
| `auth_sessions` | 一行 = **一张还没过期的通行证** | 这个请求**是谁发的**？ | [`登录状态表.md`](./登录状态表.md) |
| `sticky_notes` | 一行 = **一张便签** | 这个人**随手记下了什么**？ | [`便签表.md`](./便签表.md) |
| `todos` | 一行 = **一件待办** | 这个人**还有哪些事没做完**？ | [`待办表.md`](./待办表.md) |
| `attendance_settings` | 一行 = **一个人的周六制度** | 这个人的周六**按单休、双休还是单双休算**？ | [`出勤设置表.md`](./出勤设置表.md) |
| `attendance_overrides` | 一行 = **被手动改过的一天** | 这一天**为什么不是推算出来的那个状态**？ | [`出勤覆盖表.md`](./出勤覆盖表.md) |

**一句总话**：`users` 是**户口本**（谁是这里的人），`auth_sessions` 是**门禁刷卡记录**（现在谁在屋里、手里那张卡还有效），`sticky_notes` 是**冰箱门上的便利贴**（贴完就不管，靠时间和置顶找回来），`todos` 是**桌上的待办卡片**（做完就划掉，靠那个勾推进），`attendance_settings` 是**排班规则手册**（周六按哪档算），`attendance_overrides` 是**规则手册上的手写批注**（哪天例外、为什么是例外）。有户口本不代表人在屋里。

> `.schema` 里还会看到一张 `sqlite_sequence` —— 那不是我们建的表，是 `AUTOINCREMENT` 的记账表，不手动读写（详见 `登录状态表.md`）。

**新增一张表时**：先在①这张清单里加一行，再按第七节格式建它的说明文件，然后才改 `initSchema()`。

## 二、库放在哪、怎么建

**存储形态**：SQLite —— **整个数据库就是一个文件**。

| 环境 | 文件位置 | 谁指定 |
|---|---|---|
| 本地开发 | `data/nexus-os.db` | 代码里的默认值（`data/` 不入 Git） |
| 线上 | `/opt/nexus-os/shared/data/nexus-os.db` | 环境变量 `DATABASE_PATH`（`shared/` 跨版本保留，发布不丢库） |

**建表由代码完成**：`initSchema()` 里的 `CREATE TABLE IF NOT EXISTS`，服务启动后第一次用到数据库时执行。
生产库（文件）与测试库（内存）**共用同一份定义**——两处各写一份迟早漂移，测试就会在"结构其实不同"的库上通过。

**每个连接都会开的两个 pragma**：

| PRAGMA | 值 | 为什么 |
|---|---|---|
| `journal_mode` | `WAL` | 读写不互斥：一个长查询不会把写入卡住 |
| `foreign_keys` | `ON` | **SQLite 默认关闭外键**。不打开的话，`auth_sessions` 上的 `ON DELETE CASCADE` 只是一句注释，删用户后会话会变成"僵尸行" |

**时间戳一律 INTEGER 毫秒。** 不存字符串、不存秒：毫秒是数值，能直接比大小、能直接相减算间隔。（换算成人读的时间：`datetime(created_at/1000,'unixepoch','+8 hours')`。）

## 三、列命名的约定

| 约定 | 例子 | 为什么 |
|---|---|---|
| 表名复数、小写 | `users`、`auth_sessions` | 一张表装的是**多行**；单个实体在代码里另起名字（`User`） |
| 表名带领域前缀 | `auth_sessions` | 把裸词留给别的领域：将来 Agent 的对话叫 `agent_sessions`，不撞车 |
| 列名 `snake_case` | `password_hash`、`created_at` | SQL 里的通行写法；与 TypeScript 的 `camelCase` 一眼区分开 |
| 时间列以 `_at` 结尾，存毫秒时间戳 | `created_at`、`expires_at` | 见到名字就知道是"某一刻" |
| 归一化/派生出来的键以 `_key` 结尾 | `username_key` | 一眼看出"它不是用户看到的那一列" |
| 一列只存一个值 | —— | 需要多值就建关联表（能走索引），不塞 JSON 数组（只能全表扫） |

**代码里的名字与库里的名字不一样，转换只在一个地方发生**：`src/lib/auth/user.ts` 的 `toUser()` 把 `snake_case` 的行转成 `camelCase` 的对象。库里是库、代码里是代码，中间只留一道门。

## 四、索引的规矩（跨表）

- SQLite **只为 `UNIQUE` 和主键自动建索引，不会为外键建**。所以"按某列批量查/删"的列要显式建 —— 例子是 `idx_auth_sessions_user_id`，没有它，"按用户查会话"就要全表扫。
- 每张表自己有哪些索引、服务于哪个查询，写在各自的文件里（见这份文档的 `## 索引` 一节）。

---

## 五、两类"只存派生值"的列（安全约定）

这是本项目在数据层最重要的一条安全约定：**库里不能有可以直接拿去用的秘密**。

| 列 | 库里存的是什么 | 原文在哪里 | 怎么校验 | 库泄露会怎样 |
|---|---|---|---|---|
| `users.password_hash` | `scrypt$16384$8$1$<盐>$<哈希>` | 只在用户脑子里 | 用同一个盐和参数重算，再 `timingSafeEqual` 比对 | 拿不到任何明文密码；**每个账号盐不同**，同密码的两个账号哈希也不同，彩虹表与撞库比对失效 |
| `auth_sessions.token_hash` | `sha256(token)` 的十六进制 | 只在用户的 cookie 里（`HttpOnly`，JS 读不到） | 把 cookie 原文再算一次 sha256 去查 | 拿不到可用的登录凭证——哈希不可逆，且服务端随时能删掉这一行（即时登出） |

一句话：**密码用"故意慢"的算法存，通行证用"不可逆"的哈希存。**

## 六、改表结构的流程（给写代码的人）

1. **先改这里**：新表/新列先在本目录写清楚含义与理由（这些文档就是评审件）。
2. **再改 `initSchema()`**：建表语句一律 `CREATE TABLE IF NOT EXISTS`，可重复执行。
3. **加列用幂等检测**：`PRAGMA table_info(<表>)` 查列在不在，缺则 `ALTER TABLE ... ADD COLUMN`。
   数据量还小的时候，这比引入迁移框架更轻，也不会有"迁移状态表"这种额外概念。
4. **改表名要带迁移**：`ALTER TABLE ... RENAME TO` 写在建表之前（先建新表会让老库跳过迁移、把老行留成孤儿）。SQLite 改名不会跟着改索引名，旧索引要显式丢掉。
5. **排序记得补 `rowid` 兜底**：毫秒时间戳会撞车，SQL 不保证等值行的稳定顺序。
6. **跑门禁**（《技术栈说明》§4.4 的五项：`typegen` → `typecheck` → `lint` → `test` → `build`），测试库是内存库，建表语句一变就会被所有用例过一遍。
7. **《开发日志》记一条**：为什么加、加了之后谁受益。

## 七、单张表文件的统一格式

一张表一个文件，**文件名用中文**（`账号表.md`、`登录状态表.md`）——文档首先是给人看的。表名与文件的对应关系写在第一节的表清单里，找不到表就去那里查。

节次固定、顺序固定；用不上的节写「不涉及」而不是删掉——多张表并排看时才对得上位置。

1. **一句话 + 表头** —— 一行 = 什么、回答什么问题
2. **怎么理解它** —— 需要的背景、要先破的误解（没有就写「不涉及」）
3. **这张表管什么** —— 什么时候加行、改行、读它
4. **建表 SQL 原文**
5. **逐字段说明** —— 表格：字段 / 类型 / 约束 / 含义（人话）/ 为什么这么设计
6. **索引** —— 这张表有哪些、服务于哪个查询
7. **常用查询** —— 能直接粘进 Navicat 跑的
8. **常见疑问** —— 读者真会问的问题，正面的和负面的都写（"是不是多余的""为什么没有某某字段"）
9. **变更记录** —— 每次实质修改追加一行

## 八、目前还没有的东西（不提前建）

| 还没有 | 什么时候再说 |
|---|---|
| 全文检索（SQLite FTS5） | 等知识库 / 笔记功能落地——那时要顺带定分词器（中英文切分行为差别很大） |
| 多对多关系的关联表 | 第一个需要多对多的功能出现时；用独立关联表，不用 JSON 数组列 |
| 活跃设备列表 | 想做"某台设备退出登录"时：除了会话表，还要额外记浏览器自报的设备信息（那是给人看的，认证用不上） |
| ORM 与迁移框架 | 现在是手写 SQL（语句少、容易看懂）；什么时候值得换见《技术栈说明》候选表 |
| 备份策略 | 库文件是一个文件，备份就是复制它——但要等真正有值得备份的数据时再定 |
