# 音乐播放状态表（music_playback）

> **一行 = 「这个人上次播到哪」。**
> 它回答的问题是：「他刚才听到哪儿了？关掉重开能不能接上？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-11-03 | 2026-11-03 |

## 一、怎么理解它

它跟 `music_tracks` 是两个层面的东西：曲目表记「有哪些歌」，这张表记**一个人此刻听到哪儿**。

**一人一行**（`user_id` 是主键）。这不是「每次播放一条历史」，而是「当前这一个位置」——
用户从 A 歌听到 30 秒，切到 B 歌，A 的那条就被覆盖了。要看播放历史是另一张表的事，这里不做。

**存在服务端而不是 localStorage**，理由有三条：

1. **按用户隔离是天然的**——localStorage 是「这台浏览器」的，换账号登录就读到上一个人的进度；
2. **换设备能接上**（跟原生音乐 App 一个体验）；
3. 数据量极小：每人一行，几百字节，一次 UPSERT 而已。

## 二、它管什么

- **刷新 / 关掉重开**：前端 `GET /tracks` 时一并带回，恢复成「那首歌、那个歌单、第几秒」，停在暂停态
- **切歌、歌单被删**：读回来时对齐（歌没了整条作废，歌单没了退回全库），见 `resolvePlaybackState()`
- **它不管**「是不是正在播」：浏览器不许网页无手势自动播，记了也用不上

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS music_playback (
  user_id     INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  -- 歌或歌单被删时置空而不是删整行：位置还留着，下次播同一首还能接上
  track_id    INTEGER REFERENCES music_tracks(id) ON DELETE SET NULL,
  playlist_id INTEGER REFERENCES playlists(id) ON DELETE SET NULL,
  position_ms INTEGER NOT NULL DEFAULT 0,
  -- 上次离开时是不是正在播：刷新后据此决定要不要自动按播放
  is_playing  INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL
);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `user_id` | INTEGER | 主键，外键 → `users.id`，级联删除 | 这是谁的进度 | 一人一行；删账号时整行消失 |
| `track_id` | INTEGER | 可空，外键 → `music_tracks.id`，**删除置空** | 上次播的那首 | `SET NULL` 而不是 `CASCADE`：歌删了不代表「上次听歌」这件事不存在，而且置空后下次播任何一首都不会错跳到已删除的 id |
| `playlist_id` | INTEGER | 可空，外键 → `playlists.id`，**删除置空** | 当时在哪个歌单里（空 = 全库） | 同上。歌单删了但歌还在时，恢复成「全库播放」是对的 |
| `position_ms` | INTEGER | 非空，默认 0 | 播到第几毫秒 | 毫秒不是秒：`<audio>` 的 `currentTime` 精度就是秒的小数，秒级存会来回丢精度 |
| `is_playing` | INTEGER | 非空，默认 0 | 上次离开时是不是正在播（0 暂停 / 1 在播） | 2026-11-04 补：不记这一项时，恢复逻辑会顺带调 `play()`，**暂停着刷新页面也会自己响**。老库补列默认 0——「不记得就按暂停算」，宁可少播一次 |
| `updated_at` | INTEGER | 非空 | 最后上报时刻（毫秒） | 排查用，也用来算「恢复中的静默窗口」的兜底 |

## 五、写入时机（这是设计里最需要说清的部分）

前端**不是每帧都写**——`timeupdate` 每秒四次，全写一天能写几十万行。只在四个时机上报：

| 时机 | 为什么 |
|---|---|
| 每 15 秒（播放中） | 兜底：崩了、断电了最多丢 15 秒，而不是整首 |
| 暂停那一刻 | 「听到这儿先停」是最常见的离开方式，这一下必须记准 |
| `pagehide`（关页面 / 刷新） | 最后一次机会；用 `fetch(..., { keepalive: true })` 让请求在文档销毁后还能发出去 |
| `visibilitychange` → hidden | 手机切后台 / 切标签页，很多场景不会触发 `pagehide` |

**恢复期间禁止上报**：从服务端拿回进度到 `loadedmetadata` 之间（几十到几百毫秒），`audio.currentTime` 还是 0。
这期间如果因为「暂停就上报」写一次，库里的 45 秒就变成 0 了。`restoringRef` 就是干这个的。

## 六、常用查询

```sql
-- 读某个人的进度
SELECT track_id, playlist_id, position_ms FROM music_playback WHERE user_id = 1;

-- 写（有则覆盖）
INSERT INTO music_playback (user_id, track_id, playlist_id, position_ms, updated_at)
VALUES (1, 42, NULL, 45000, 1700000000000)
ON CONFLICT(user_id) DO UPDATE SET
  track_id = excluded.track_id,
  playlist_id = excluded.playlist_id,
  position_ms = excluded.position_ms,
  updated_at = excluded.updated_at;
```

## 七、常见疑问

**「为什么不用 localStorage？本地读写不是更简单？」**
更简单，但会串号：同一个浏览器上 A 用户播到 45 秒，B 用户登录后读到的是 A 的进度。
要么在 key 里塞 userId（那还得先知道 userId），要么就认下这个 bug。存服务端一次 UPSERT 就解决了，
而且顺带换来「换设备能接上」。

**「为什么不记时间戳、记历史？」**
那是「播放历史」功能，不是「接着播」。历史要多一张表、要考虑保留多少条、要一个列表页面。
本表只服务一件事：下次打开能不能接上刚才那一下。

**「多人同时用一个账号开着两个标签页会怎样？」**
互相覆盖，最后写的赢。跟音量、窗口位置这类「此刻状态」一样，不做冲突合并。
