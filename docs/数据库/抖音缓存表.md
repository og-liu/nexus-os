# 抖音缓存表（douyin_videos）

> **一行 = 一次抖音解析的结果。** 它回答的问题是：「这条视频之前解析过吗？能不能省一次付费调用？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已上线 | 2026-11-02 | 2026-11-03 |

## 一、怎么理解它

抖音的解析接口是**按次收费**的（TikHub，$0.001/次），所以「同一个视频解析第二次」这件事必须避免。
这张表就是那道挡箭牌：解析前先来看一眼，有就直接用，没有才去花钱。

**它不是用户资产，是外部接口响应的本地副本。** 同一个公开视频，谁解析都拿到同一份数据，
所以表里**刻意没有 `user_id`**——按用户存只会把同一份公开数据存好几遍。将来做「我的收藏夹」
时另建用户维度的表，不在这张表上加列。

一个容易混的点：**「过期」不等于「消失」。**

- `fetched_at` 超过 24 小时 = 这条记录的**直链**大概率失效了，解析时要重新调上游（`fetch` 一次）
- 但下载路径还是会**先拿旧直链试一次**——很多情况下它其实还能用，试一下比花一次调用便宜
- 真的老了（7 天以上）才会被删掉，清理由写入时顺手做

## 二、这张表管什么

- **解析成功**：写入或覆盖一行（同一个 id 是 `UPSERT`，不会变成两行）
- **解析之前**：读 `fetched_at`，判断这条还算不算「新鲜」（24 小时内）
- **下载之前**：不看时间直接读，拿旧的 `play_url` 先试；403 了再走一次重解析
- **每次写入时**：顺手删掉 `fetched_at` 早于 7 天的行（连同 `douyin_links` 里指向它们的映射）
- 它**不**记录「谁解析过」「解析了几次」「花了多少钱」——那些属于统计，不属于缓存

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS douyin_videos (
  aweme_id    TEXT    PRIMARY KEY,        -- 抖音作品 id，天然唯一，直接当主键
  title       TEXT    NOT NULL,
  author      TEXT    NOT NULL,
  cover_url   TEXT    NOT NULL,
  duration_ms INTEGER NOT NULL,
  play_url    TEXT    NOT NULL,           -- 抖音 CDN 直链，会过期；fetched_at 决定还能不能直接用
  fetched_at  INTEGER NOT NULL            -- 毫秒时间戳；超过 24 小时视为过期，重新解析
);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `aweme_id` | TEXT | 主键 | 抖音作品 id，一串 19 位左右的数字（如 `7702415046048193446`） | 它**天然唯一**，直接当主键就省掉了自增 id。用 TEXT 而不是 INTEGER：这串数字超过了 JS 安全整数范围（2^53），当成数字会丢精度 |
| `title` | TEXT | NOT NULL | 视频标题（抖音的文案，可能含表情和 `#话题`） | 展示用，也是下载文件名的来源（清洗与截断在 `lib/douyin/filename.ts`） |
| `author` | TEXT | NOT NULL | 作者昵称 | 结果卡上要显示「谁发的」 |
| `cover_url` | TEXT | NOT NULL | 封面图地址（抖音 CDN） | 结果卡显示缩略图。**不下载到本地**：封面随时会变，且本地存图要配一套清理，不值得 |
| `duration_ms` | INTEGER | NOT NULL | 时长（毫秒） | 结果卡显示「几分几秒」；用毫秒与全站时间口径一致 |
| `play_url` | TEXT | NOT NULL | 播放地址（**无水印**的那条） | 这是整个工具的核心产出。它会**过期**，所以不能当成永久链接用 |
| `fetched_at` | INTEGER | NOT NULL | 这一行是什么时候取回来的（毫秒时间戳） | 判断新鲜度和清理老行的唯一依据。不用 `created_at`/`updated_at` 两列：这一行只有「最后一次取回来是什么时候」这一个时间概念 |

## 五、索引

只有主键 `aweme_id`（SQLite 的 `PRIMARY KEY` 自带索引）。查询全部是「按 id 精确取一行」，用不到别的索引。

清理用的 `DELETE ... WHERE fetched_at < ?` 走全表扫描——表本来就只有几十到几百行，扫一遍的代价远小于维护一个索引。

## 六、常用查询

```sql
-- 现在缓存了多少条
SELECT COUNT(*) FROM douyin_videos;

-- 最近解析的 10 条
SELECT aweme_id, title, author,
       datetime(fetched_at/1000,'unixepoch','+8 hours') AS 取回时间
FROM douyin_videos
ORDER BY fetched_at DESC
LIMIT 10;

-- 哪些已经超过 24 小时（下次解析会重新调上游）
SELECT COUNT(*) FROM douyin_videos
WHERE fetched_at < (strftime('%s','now') - 86400) * 1000;

-- 手动清空（线上慎用：清完下次解析全都要花钱）
-- DELETE FROM douyin_videos;
```

## 七、常见疑问

**为什么不挂 `user_id`，每个人看到的不是自己解析的？**
看到的确实是同一条公开数据——视频标题、作者、直链，谁来问都是这一份。挂 `user_id` 等于同一份数据存 N 份。
「谁能用这个工具」由 `user_secrets` 那张表管（有没有配自己的 Key），和缓存无关。

**缓存命中是不是就不用花钱了？**
是。只要 `fetched_at` 在 24 小时内，解析请求根本不会发到 TikHub。

**为什么是 24 小时？**
抖音 CDN 的直链通常几小时就会失效，24 小时是个保守值：短到不会拿到一堆死链，长到「今天解析、明天再下」还能命中。

**为什么 7 天才删，不是 24 小时就删？**
24 小时是「不新鲜」，7 天是「没用」。中间这几天，用户点「下载」时还能用旧直链试一次——
很多链接其实还活着，试一下不要钱；真删了就只能重新付费解析。

**`play_url` 会过期，为什么还存？**
因为「过期」是个概率，不是必然。存着 + 先试一次，比重解析便宜太多。真 403 了再刷新，用户感知不到。
