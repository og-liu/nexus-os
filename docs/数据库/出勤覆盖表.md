# 出勤覆盖表（attendance_overrides）

> **一行 = 我被手动改过的一天。** 它回答的问题是：「这一天为什么不是推算出来的那个状态？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已完成（v0.8.5） | 2026-10-23 | 2026-10-24 |

## 一、怎么理解它

制度（`attendance_settings`）负责「规律」，这张表负责「例外」：调休、请假、临时改班，**规则算不出来的那些天**。

翻开日历，每一天的状态按这个顺序定：

```
这一行在不在？  → 在：用它（最高优先级，换制度也冲不掉）
              → 不在：按周六制度推算（周一到周五上班、周日休息、周六看制度）
```

一张表只装**人真正改过的日子**。一年可能十几行，也可能一行都没有。

## 二、这张表管什么

- **改某一天**：UPSERT 一行（`work` / `off`）
- **「跟随自动」**：**删掉这一行**，回到推算值
- **点回推算值 = 跟随自动**：如果选的状态跟按制度算出来的一样，服务端不写这一行、把已有的删掉——否则「改成班 → 再改回休」之后库里留着一行等于推算值的记录，界面上「已手动调整」的小横条一直挂着，看起来像没改回去
- 它**不**记录「为什么改」：曾经有过一个 `note` 备注列，见 §七

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS attendance_overrides (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  day_key    TEXT    NOT NULL,             -- 'YYYY-MM-DD'
  status     TEXT    NOT NULL CHECK (status IN ('work', 'off')),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, day_key)
) WITHOUT ROWID;
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `user_id` | INTEGER | NOT NULL，外键 → `users.id`，级联删除 | 这一行属于谁 | 每个人各改各的：A 的调休不该出现在 B 的日历上。级联删除保证删账号时不留下孤儿行 |
| `day_key` | TEXT | NOT NULL，`YYYY-MM-DD` | 哪一天 | 这是一**天**不是一个**时刻**，所以存日期字符串不存时间戳：`'2026-10-24'` 可读、能 `BETWEEN '2026-10-01' AND '2026-10-31'` 一次捞整月（42 格只用一次查询），也不会因为时区换算漂到前一天 |
| `status` | TEXT | NOT NULL，`CHECK` 只许 `work` / `off` | 这天被改成了「上班」还是「休息」 | `unset` 不进库：用一行数据表达「没有例外」，比存一个 `'auto'` 再到处判断更省事 |
| `created_at` | INTEGER | NOT NULL | 第一次改这天的时间 | 排查用 |
| `updated_at` | INTEGER | NOT NULL | 最后一次改这天的时间 | 有这个写入路径：同一天改两次是 UPSERT，会刷新它 |

**复合主键 `(user_id, day_key)`** 保证「某人某天」只有一行，`WITHOUT ROWID` 省掉一层额外索引（查询键就是主键本身）。

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `sqlite_autoindex_attendance_overrides_1` | 复合主键 | 按用户 + 日期区间取一个月的覆盖；按用户 + 某天取单条 |

**为什么不做 `user_id` 单列索引**：复合主键的左前缀正好是 `user_id`，`WHERE user_id = ? AND day_key BETWEEN ? AND ?` 直接走它，再建一个单列索引只是重复。

## 六、常用查询

```sql
-- 某个月有哪些天被手动改过
select day_key, status from attendance_overrides
where user_id = 1 and day_key between '2026-10-01' and '2026-10-31'
order by day_key;

-- 某一天是不是例外
select status from attendance_overrides
where user_id = 1 and day_key = '2026-10-24';

-- 某个人一共改了多少天
select count(*) from attendance_overrides where user_id = 1;
```

## 七、常见疑问

**Q：为什么没有 `note`（备注）列？**
2026-10-24 删掉了。它建出来却**没有任何写入路径**——弹层里没有备注输入框、写入语句恒填 `NULL`、界面上也不显示，而文档还写着「带备注的日子显示小字」。一个永远是空的列会让下一个读代码的人以为「备注功能是有的」，比没有这个功能更糟。真要备注时再加：那时得先定清楚它是「给自己看的」还是「说明给别人看的」，两者的长度限制和显示位置都不一样。
老库由 `initSchema()` 的 `migrateAttendanceOverrideNote()` 处理：`PRAGMA table_info` 看到 `note` 就 `ALTER TABLE ... DROP COLUMN`（SQLite 3.35+），看不到就跳过。

**Q：为什么「跟随自动」是删行，不是存一个 `'auto'`？**
存 `'auto'` 等于用一行数据表达「这里没有例外」。之后每个读这张表的地方都得判断「这个值算不算例外」，漏一处就会把「自动」当成「手动」——「已手动调整」的小横点会挂在没改过的日子上。删行是**零成本的真相**：没有行就是没有例外。

**Q：为什么不存整月快照？**
快照会和制度脱钩：改了制度，历史快照里还是旧状态，日历上会出现「同一套制度、两种答案」。按规则现算，永远只有一份真相。

**Q：跨月补齐的 42 格里，上下月的日子也能改吗？**
能。它们是真实日子，改了就存这一天（`day_key` 是那一格真实的日期），与它属于哪个月无关。查询区间也会跟着 42 格一起放宽（`monthCells[0]` ~ `monthCells[41]`）。

**Q：删了账号，这些行会留着吗？**
不会。`user_id` 上有 `ON DELETE CASCADE`，而且每个连接都开了 `PRAGMA foreign_keys = ON`（《数据库/README》§二）——用 `sqlite3` 命令行手工删用户时要自己加 `pragma foreign_keys=ON;`，CLI 默认是关的。
