# 保险库条目表（vault_items）

> **一行 = 保险库里的一个条目（一条记录）。** 它回答的问题是：「这个人想记住的那件事，具体是什么？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| 🚧 开发中 | 2026-10-29 | 2026-10-29 |

## 一、怎么理解它

一条条目 = **一个标题 + 一串自定义字段**。没有固定字段：这条是「招商银行信用卡 / 卡号 / 密码 / 客服电话」，那条是「阿里云 / AK / SK / 登录地址」，另一条可能是「老家 WiFi / 密码」。

所以要破的第一个误解是：**这张表没有「用户名」「密码」「网址」这些列，也从不会有。** 字段的名字由用户自己起，存在 `fields` 里。

第二个误解：`fields` 存 JSON 不是偷懒。它是《数据库/README》§三「一列只存一个值，多值就建关联表」这条约定的**登记例外**，理由写在 §七第一节，评审时先看那段。

它和 `sticky_notes` 的区别：便签只有一段正文，写完就不管；条目是**被反复查用的结构化记录**——你会为了复制一个密码把它找出来，所以它有标题、有分组、有排序。

## 二、这张表管什么

- **新建条目**：加一行（标题 + 可选群组 + 字段数组 + 两个时间）
- **编辑条目**：改标题 / 字段 / 所属群组，同时把 `updated_at` 刷成当前时间（顺序因此重排，见 §七）
- **删除条目**：删掉这一行（没有软删除、没有回收站，界面二次确认）
- **批量移动**：按 `id` 批量改 `group_id`，一次 `UPDATE ... WHERE id IN (...)`
- **批量删除**：按 `id` 批量删
- **左栏「所有条目」**：不按 `group_id` 过滤，取这个人的全部条目
- **某个群组**：`where group_id = ?`
- **搜索**：只按 `title` 模糊匹配（见 §七）
- 它**不**记录「这个值是不是密码」「要不要打码」——没有类型系统（见 §七）

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS vault_items (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  group_id   INTEGER REFERENCES vault_groups(id) ON DELETE SET NULL,  -- NULL = 未分组
  title      TEXT    NOT NULL,
  fields     TEXT    NOT NULL DEFAULT '[]',   -- JSON 数组：[{"key":"卡号","value":"8821319"}]
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_vault_items_user_id ON vault_items(user_id);
CREATE INDEX IF NOT EXISTS idx_vault_items_group_id ON vault_items(group_id);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这条记录的内部编号 | 批量移动 / 删除都按 `id IN (...)` 操作；编号永不复用，前端把「选中了哪几条」存起来时不会指错行 |
| `user_id` | INTEGER | NOT NULL，外键 → `users.id`，级联删除 | 这条记录属于谁 | 所有查询都带 `user_id = ?`，**这是账户隔离的唯一落实点**。A 账户查不到 B 的条目，不靠界面藏，靠每条 SQL 都带这个条件 |
| `group_id` | INTEGER | **可为 NULL**，外键 → `vault_groups.id`，`ON DELETE SET NULL` | 属于哪个群组；NULL = 未分组 | 未分组是**一等状态**，不是「没有这个字段」：用户可以先记下来、以后再归类。`ON DELETE SET NULL` 让「删群组」自动把组内条目降级成未分组，不需要在删群组前手动搬移，也不会因为漏搬而连坐删除 |
| `title` | TEXT | NOT NULL | 条目标题，用户自己起（「招商银行信用卡」） | 唯一**固定的**展示字段：列表的列头、右栏的大标题、搜索的对象都是它。新建时默认「未命名」，重名自动补序号——标题重复是合法的（同名的两张卡可能只差尾号） |
| `fields` | TEXT | NOT NULL，默认 `'[]'` | 自定义字段的 JSON 数组，**顺序有意义** | 每一项是 `{"key": "...", "value": "..."}`。用**数组**不用对象：对象存不住顺序，而字段顺序用户要能拖拽调整（数组下标天然就是顺序号，不用另存 `position` 列）。理由详见 §七 |
| `created_at` | INTEGER | NOT NULL | 什么时候建的（毫秒时间戳） | 右栏「创建于 …」与排查要用。不参与排序，排序看 `updated_at` |
| `updated_at` | INTEGER | NOT NULL | 最后一次**内容变更**的时间（毫秒时间戳） | 列表与「所有条目」的排序主依据：刚改的那条浮到最上面。**移动群组也要刷新它**——移完就想一眼看到，不然可能在另一个群组里翻半天 |

**为什么字段值只存字符串，不存「类型」**：类型一进来（文本 / 密码 / URL / 多行），弹窗就得给每个字段配一个下拉框，用户每加一个字段多一次决定，而收益只是「密码行显示成圆点」。这个功能要的是「记得住、找得到、复制得走」，不是「被规则绑住」。

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `idx_vault_items_user_id` | 显式建（`CREATE INDEX`） | 左栏「所有条目」、搜索、批量操作前的归属校验 |
| `idx_vault_items_group_id` | 显式建（`CREATE INDEX`） | 按群组过滤列表；**也是 `ON DELETE SET NULL` 的执行效率保证**——删群组时 SQLite 要按 `group_id` 找到所有子行去置空，没有这个索引就是全表扫 |
| `sqlite_autoindex_vault_items_1` | 主键 | 按 `id` 更新 / 删除 |

**为什么按 `group_id` 建索引，而群组表那边不建联合索引**：外键不会自动建索引（SQLite 只为 `UNIQUE` 和主键建），而「删群组」这个动作每次都靠它定位子行；点群组看列表也靠它。它不是为想象中的查询准备的，是现在就每次都在用的。

**排序列为什么也不建索引**：`ORDER BY updated_at DESC, id DESC` 在几百行规模下走一遍 `user_id` 索引取出来再内存排序就够；提前建 `(user_id, updated_at)` 联合索引会让每次写入多维护一棵树，收益是零。

## 六、常用查询

```sql
-- 「所有条目」：不分组、最近改的在前
select id, group_id, title, fields, created_at, updated_at
from vault_items
where user_id = 1
order by updated_at desc, id desc;

-- 某个群组（group_id 为 NULL 时用 is null）
select id, group_id, title, fields, created_at, updated_at
from vault_items
where user_id = 1 and group_id = 3
order by updated_at desc, id desc;

-- 搜索（只搜标题；中文用 like 就行，两头的 % 让索引失效但个人量级无所谓）
select id, title from vault_items
where user_id = 1 and title like '%银行%'
order by updated_at desc, id desc;

-- 批量移动到某个群组（含移到未分组：group_id 传 null）
update vault_items
set group_id = 5, updated_at = 1761700000000
where user_id = 1 and id in (12, 13, 14);

-- 字段数组长什么样
select id, title, json_extract(fields, '$[0].key') as first_key,
       json_array_length(fields) as field_count
from vault_items where user_id = 1;

-- 看时间（毫秒转 +8 的人读时间）
select id, title,
       datetime(created_at/1000, 'unixepoch', '+8 hours') as created,
       datetime(updated_at/1000, 'unixepoch', '+8 hours') as updated
from vault_items order by id desc;
```

## 七、常见疑问

**Q：`fields` 存 JSON 数组，不是违反《数据库/README》§三「一列只存一个值」吗？**
是例外，已经登记在《数据库/README》§三的例外清单里。逐条对一下这条约定原本要防什么：

| 约定要防的问题 | 这里为什么不成立 |
|---|---|
| 「多值塞一列就只能全表扫」 | 我们的访问模式**永远是整条取出来显示**：列表要列头（读全部字段名），右栏要全文，弹窗要回填。**没有任何查询是「按字段值找条目」**——搜索只搜标题（这是需求定的）。不能按值查，索引就无从谈起，也就没有「只能全表扫」的损失 |
| 「多值该建关联表，能走索引」 | 关联表要多一列 `position` 才能保序，而字段顺序用户要拖拽调整；拖一次就要批量重写所有行的 `position`，还得在一个事务里。数组的顺序就是下标，天然有序、整体覆盖写一次就完成 |
| 「多值该建关联表，好查询」 | 字段与条目是**共生**关系：没有独立生命周期，不会脱离条目存在，也不会被别的条目引用。它不是「标签」那种多对多 |

什么情况下该推翻这个决定：有一天要「搜索字段值」或「按字段类型统计」。那时把 `fields` 展开进 `vault_item_fields` 表（`item_id / key / value / position`）是一次 `INSERT ... SELECT json_each(...)`，迁移成本可控。现在为那个未来多维护一张表，是拿今天的确定性换想象。

**Q：为什么没有 `password` 列？为什么不做加密？**
没有固定字段，所以没有「密码」这个概念——密码只是一行的 `key` 恰好叫「密码」。加密这件事主人明确要求一期不做：整个项目是他个人使用的工作台，而且**「做一半的加密」比明文更危险**（密钥存在进程里、明文在日志里、备份里）。要真做是另一层设计：主密码 + 密钥派生 + 内存解密。文档里如实写明「库里是明文」，谁打开库文件都能读到——这是知情选择，不是疏忽。

**Q：界面上的「眼睛」遮挡算不算一层保护？**
不算，别把它当安全边界。它只是把**屏幕上的显示**换成 `***`：库里、复制到剪贴板里的、以及任何能打开这个 `.db` 文件的人拿到的，全都是明文。它的用途是「旁边有人时别让密码亮在屏幕上」，防的是肩窥，不是防入侵。真正的安全边界只有一条：**这个库文件本身别泄露**。

**Q：为什么要 `user_id` 和 `group_id` 两个外键，`title` 不能当主键吗？**
标题不唯一（同名两张卡是合法的），而且用户随时改标题。`id` 稳定、不随内容变，批量操作和前端选中状态都靠它。

**Q：`updated_at` 为什么在「只是移到另一个群组」时也要刷新？**
排序就是「最近动过的在最上面」。移完群组后，用户马上要在**新群组**里看到它——不刷新的话它按旧时间沉在新群组的列表里，等于「移过去了，找不着」。

**Q：删群组时条目去哪了？是这张表自己处理的吗？**
是 `group_id` 上的 `ON DELETE SET NULL` 做的，但**前提是连接开着 `foreign_keys = ON`**（`createConnection()` 已开）。这个 pragma 默认是关的，关掉时 `SET NULL` 只是一句注释、完全不执行——子行会变成指向已删群组的孤儿，界面按群组查就查不到它们，像数据丢了。这是本功能最隐蔽的坑（《功能/保险库》§七）。

**Q：一个条目能属于多个群组吗？**
不能。`group_id` 是单值。多归属是标签模型，见《数据库/保险库群组表》§一。
