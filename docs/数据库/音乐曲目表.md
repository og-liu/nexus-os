# 音乐曲目表（music_tracks）

> **一行 = 曲库里的一首歌。** 它回答的问题是：「这个人有哪些歌？每首在磁盘上叫什么、多长、多大？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-11-03 | 2026-11-03 |

## 一、怎么理解它

**库里存的是「索引」，不是「歌」。** 音频文件本身在磁盘上
（`<数据库所在目录>/music/<userId>/<uuid>.<ext>`），这张表只记它的名字、时长、体积和展示名。
删一行 + 删文件才等于「删掉一首歌」，两者在不同地方，代码里由同一个函数按固定顺序做。

三个容易混的点：

1. **`file_name` 不是用户看到的歌名。** 用户看到的是 `title`。磁盘上的名字是 `uuid`，
   与用户输入完全无关——这是路径穿越（`../../etc/passwd`）和同名覆盖的唯一防线。
2. **`codec` 不是扩展名。** 它是 ffmpeg 探出来的**真实编码**。浏览器能不能播跟的是编码，
   所以 `.mp3` 扩展名里装着 AAC 时，这一列会告诉你真相（`aac`），落盘扩展名也会跟着它走。
3. **`position` 决定列表顺序，而列表顺序就是播放顺序。** 它由用户拖拽产生，新歌追加到末尾（2026-11-03 改；此前是 `created_at` 升序——整张专辑一次传进来，
   从上往下播正好是专辑顺序。倒序会让「下一首」永远往更早传的方向走。

## 二、这张表管什么

- **上传成功**：磁盘文件已经写好、编码与时长已经探完 → 插一行
- **列曲库**：`WHERE user_id = ? ORDER BY position ASC, id ASC`
- **播放**：先按 `id + user_id` 取这一行，再拼出磁盘路径交给流接口
- **删除**：先 `DELETE` 这一行，拿到 `file_name` 再删文件
- **配额**：`SUM(size_bytes) WHERE user_id = ?`，超过 5 GB 拒传
- 它**不**记录播放次数、最后播放时间、进度——那些是「听的行为」，不是「有什么歌」

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS music_tracks (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title       TEXT    NOT NULL,
  artist      TEXT,
  file_name   TEXT    NOT NULL,
  codec       TEXT    NOT NULL,
  size_bytes  INTEGER NOT NULL,
  duration_ms INTEGER,
  position    INTEGER NOT NULL,
  created_at  INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_music_tracks_user_id ON music_tracks(user_id);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这首歌的编号 | 流接口、删除接口都用它寻址；不暴露 `file_name` 给前端 |
| `user_id` | INTEGER | 非空，外键 → `users.id`，级联删除 | 歌属于谁 | 每条查询都带它。删账号时行会级联删掉（**磁盘文件不会**，要单独清） |
| `title` | TEXT | 非空 | 界面上显示的歌名 | 优先取文件自带的标题标签，没有才用文件名去扩展名。与磁盘上的名字彻底分开 |
| `artist` | TEXT | 可空 | 文件自带的歌手标签 | 很多文件没有标签，NULL 就是「不显示这一段」，不用空串假装有值 |
| `file_name` | TEXT | 非空 | 磁盘上的文件名，形如 `<uuid>.<ext>` | **不含任何路径**。目录由代码按 `userId` 推导，换机器、换目录时库不用动 |
| `codec` | TEXT | 非空 | ffmpeg 探到的真实音频编码 | 决定流接口的 `Content-Type` 与列表上的格式标签；扩展名会撒谎，编码不会 |
| `size_bytes` | INTEGER | 非空 | 落盘后的真实字节数 | 配额判断与列表显示都用它，不去 `stat` 每个文件 |
| `duration_ms` | INTEGER | 可空 | 时长（毫秒） | 可空：探不出时长不该拦住上传，列表显示 `--:--` 就行 |
| `position` | INTEGER | 非空 | 用户拖出来的顺序（升序） | 列表排序依据，新歌追加到末尾；末尾 `id ASC` 兜底同值 |
| `created_at` | INTEGER | 非空 | 上传时刻（毫秒） | 只用于显示「上传于」，不再决定顺序 |

## 五、索引

| 索引 | 服务于哪个查询 |
|---|---|
| `idx_music_tracks_user_id` | 列表（`WHERE user_id = ?`）、配额求和、删除前的归属校验。SQLite 不为外键自动建索引 |

## 六、常用查询

```sql
-- 某人的曲库，按上传顺序
SELECT id, title, artist, codec, size_bytes, duration_ms, position, created_at
FROM music_tracks WHERE user_id = 1 ORDER BY position ASC, id ASC;

-- 已用配额
SELECT COALESCE(SUM(size_bytes), 0) AS used FROM music_tracks WHERE user_id = 1;

-- 磁盘上有行、文件可能已经不在的（排查用）
SELECT id, file_name FROM music_tracks WHERE user_id = 1;
```

## 七、常见疑问

**「为什么不存 mime？」**
它完全由 `codec` 决定，一张映射表在用（流接口的 `Content-Type` 与列表的格式标签）。
存一列等于让同一件事有两个真相，改了编码忘了改 mime 就会吐错类型。

**「为什么没有播放进度 / 最后播放时间？」**
~~播放状态是「此刻」的状态，住在浏览器内存里~~ **2026-11-03 改了**：进度现在存在 `music_playback`（一人一行，
见《数据库/音乐播放状态表》），但**不在这张表上**——曲目表记「有哪些歌」，进度记「一个人听到哪儿」，
两者生命周期完全不同（删歌不该删掉「上次听歌」这件事）。这张表里的 `created_at` 也只用于显示，不再决定顺序。

**「删账号时磁盘文件会一起删吗？」**
不会。`ON DELETE CASCADE` 只删行。目前没有删账号功能，真要支持时得先删目录再删用户。
