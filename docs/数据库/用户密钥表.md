# 用户密钥表（user_secrets）

> **一行 = 一个用户在某一家服务商那里的 Key（密文）。** 它回答的问题是：「这个人配了自己的 Key 吗？能不能用这个工具 / 和模型说话？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已上线 | 2026-11-02 | 2026-11-03 |

## 一、怎么理解它

这是全站**唯一**存「别人的钱」的地方：每个用户把自己的 DeepSeek / TikHub Key 填进来，
用他自己的额度跑功能。站点不再统一持有一份 Key 替所有人付钱——那是产品形态错误，
单用户时看不出来，第二个人登录就暴露了（《功能/用户密钥》）。

三件必须清楚的事：

1. **库里只有密文。** AES-256-GCM，格式 `v1.<iv>.<tag>.<data>`，全是 base64。
   `SELECT` 出来看到的是一串看不懂的字符，没有明文、也没有「前 8 位 + 省略号」那种残留。
2. **主密钥不在库里。** 它在环境变量 `ENCRYPTION_KEY`（32 字节）。库和钥匙分开保管：
   单偷到数据库文件解不开，单偷到环境变量也不知道该解哪一行。
3. **主密钥换了，所有人得重填。** 这是有意的，不做自动迁移——迁移意味着「用旧钥匙解、新钥匙加密」，
   而如果旧钥匙已经泄露，迁移只会让攻击者多拿到一次明文。

## 二、这张表管什么

- **保存 Key**：先调上游验活，`401/403` 直接拒（不写库）；通过后加密写入，同一家服务商是 `UPSERT` 覆盖
- **读 Key**：消费方（Agent、抖音下载）在**每次用之前**按 `user_id` 现读现解，不缓存、不放进 session
- **判断有没有配**：`hasSecret()` 只查行存在与否，**不解密**——这是「能不能用这个功能」的门槛，排在缓存查询之前
- **清除 Key**：删掉这一行（就地确认条确认后）
- 它**不**存「余额」「用量」「上次用是什么时候」——那些要额外调上游，属于另一个功能

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS user_secrets (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider   TEXT    NOT NULL,
  ciphertext TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, provider)
) WITHOUT ROWID;
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `user_id` | INTEGER | 主键之一，外键 → `users.id`，级联删除 | 这个 Key 属于谁 | 删账号时把 Key 一起带走。**永远从 `requireUser()` 取**，不接受客户端传——否则任何人都能往别人名下写 Key |
| `provider` | TEXT | 主键之一 | 哪一家服务商：目前是 `deepseek` / `tikhub` | 用**英文 id**，不用中文名——它同时是代码里读 Key 的键（`readSecret(db, userId, "tikhub")`），换成「模型」那种中文就没法当 URL 参数、也不方便排查。名字给人看的版本在 `lib/secrets/providers.ts` 的注册表里 |
| `ciphertext` | TEXT | NOT NULL | 加密后的 Key：`v1.<iv>.<tag>.<data>` | 带版本前缀（`v1`），将来换算法可以并存；GCM 自带认证标签（`tag`），密文被改一个字节就解不出来，不会解出一串垃圾当 Key 发出去 |
| `created_at` | INTEGER | NOT NULL | 第一次填这个 Key 的时间（毫秒） | 排查用（「这人是不是刚配的」） |
| `updated_at` | INTEGER | NOT NULL | 最后一次覆盖的时间（毫秒） | 同上。**不拿它判断过期**——Key 没有「过期时间」这个概念，能不能用靠上游验活 |

**为什么用 `(user_id, provider)` 当联合主键**：天然保证「一个人一家只能有一条」，
覆盖保存直接 `INSERT ... ON CONFLICT DO UPDATE`，不需要先查再决定插还是改。

**为什么 `WITHOUT ROWID`**：这张表的查询永远是「按 `(user_id, provider)` 精确取一行」，
而且一行就是一个几百字节的字符串，没有「按 id 找」的需求。`WITHOUT ROWID` 把数据直接存在主键的 B 树里，
省掉一次「索引 → 行」的跳转。表小的时候差别不大，但这是张会被频繁点名的表（每次对话、每次解析都要查），
省一次跳转是白捡的。

## 五、索引

主键就是全部索引。所有查询都是「按 `(user_id, provider)` 取一行」或「按 `user_id` 列出全部」，
两者都走这个主键的 B 树前缀。

## 六、常用查询

```sql
-- 谁配了什么（只列 provider，不解密）
SELECT u.username, s.provider,
       datetime(s.updated_at/1000,'unixepoch','+8 hours') AS 更新时间
FROM user_secrets s
JOIN users u ON u.id = s.user_id
ORDER BY u.id, s.provider;

-- 某个人配了几家
SELECT COUNT(*) FROM user_secrets WHERE user_id = 24;

-- 密文长什么样（能看出格式，看不出 Key）
SELECT provider, substr(ciphertext,1,12) || '…' AS 前缀, length(ciphertext) AS 长度
FROM user_secrets;

-- 删掉某人的某一个 Key（正常走设置页，不要手删）
-- DELETE FROM user_secrets WHERE user_id = 24 AND provider = 'tikhub';
```

> **密文长度能反推明文长度**：`v1` + iv(16) + tag(24) + data 的 base64 长度。
> 53 字符左右说明明文只有几个字符（大概率是乱码），90 多字符通常是正常的 Key。
> 这个特性在实测时帮过大忙——一眼看出用户填的是乱码。

## 七、常见疑问

**为什么不在登录时把 Key 解出来放进 session？**
那等于把明文多散出去一份（cookie / 内存 / 日志都可能碰到），而且退出登录还得记得清。
一次解密是微秒级，现读现解没有任何性能问题。

**主密钥丢了会怎样？**
库里所有密文都解不开，每个人要重新填一遍。所以 `ENCRYPTION_KEY` 要和数据库一样被保护，
但它**不该**和数据库放在同一个地方——现在是环境变量 vs 数据库文件，分开的。

**能不能存明文？反正只有一个用户。**
不能。这是「以后会多人」的项目，而且明文一旦进库，备份、日志、`SELECT` 任何一处泄露都是全量泄露。
加密的成本只有一行 `createCipheriv`。

**为什么要验活？存进去不就行了吗？**
只验「有没有填」不验「对不对」，填一串乱码也能通过，然后命中别人解析过的缓存照样能用——
校验形同虚设（实测踩过两次，见《功能/用户密钥》§七）。

**`provider` 的显示名改中文了，库里的值要跟着改吗？**
不用。库里的 `provider` 是**机器码**，显示名在注册表里改，两者是分开的。
反过来才要小心：`provider` 的值一旦改，老数据就对不上了，等于所有人的 Key 都失效。
