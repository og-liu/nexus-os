# 保险库群组表（vault_groups）

> **一行 = 保险库里的一个群组（文件夹）。** 它回答的问题是：「这个人的记录打算怎么归类？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| 🚧 开发中 | 2026-10-29 | 2026-10-29 |

## 一、怎么理解它

群组是**保险库内部的分类文件夹**，不是权限边界，也不是标签。

它和「标签」的区别：一个条目最多属于**一个**群组（可以一个都不属于），而标签天然是多对多。这里要的是「放到哪个抽屉」，不是「贴几张便签」。

它和 `users` 的区别：群组属于某一个人，但它**不共享**。现在没有「把群组分享给另一个账号」这种事，将来也不打算用这张表实现——分享是另一套权限模型（见《功能/保险库》关键决策）。

## 二、这张表管什么

- **新建群组**：加一行（`user_id` + `name` + `created_at`）
- **重命名群组**：只改 `name`
- **删除群组**：删掉这一行，**组内条目不会被删**——`vault_items.group_id` 上的 `ON DELETE SET NULL` 会把它们变成「未分组」（见《数据库/保险库条目表》§五）
- **左栏渲染**：按用户取全部群组，按「建得早的在上」排
- 它**不**记录「群组里还有几条记录」——那是查询时 `COUNT` 出来的，存一列「条目数」就得在每次增删改时记得同步，早晚不同步

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS vault_groups (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name       TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  UNIQUE (user_id, name)
);

CREATE INDEX IF NOT EXISTS idx_vault_groups_user_id ON vault_groups(user_id);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这个群组的内部编号 | 与全库一致：`AUTOINCREMENT` 保证编号永不复用。**条目引用的是这个值**，所以它必须稳定——用群组名当外键的话，改个名所有条目就全断了 |
| `user_id` | INTEGER | NOT NULL，外键 → `users.id`，级联删除 | 这个群组属于谁 | 归属从第一天就写进数据（同 `sticky_notes`）；删账号时群组跟着走，不会留下无主的抽屉 |
| `name` | TEXT | NOT NULL；与 `user_id` 组合唯一 | 群组名，用户自己起（「银行」「阿里云」「工作账号」） | 组合唯一而不是全局唯一：不同用户的群组名互不干扰。**同一个人不能有两个同名群组**——左栏里两个「银行」谁也分不清，重名是纯粹的困扰 |
| `created_at` | INTEGER | NOT NULL | 什么时候建的（毫秒时间戳） | 左栏排序的唯一依据：**按建组顺序排**，新建的加在最后。按名称排会让群组在改名后跳位置，手会跟着乱 |

**为什么没有 `updated_at`**：群组只有两个会被改的动作——改名、删除。改名不需要「最近修改时间」这个概念，它不参与任何排序，界面上也不显示。留一列永远没人读的 `updated_at` 会让读代码的人以为群组有「按最近编辑排序」的能力（便签表当初删掉 `note` 空壳列是同一个理由）。

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `sqlite_autoindex_vault_groups_1` | `UNIQUE (user_id, name)` 唯一约束 | 重名检测；顺带也是按 `user_id` 过滤的索引（唯一键的最左列是 `user_id`） |
| `idx_vault_groups_user_id` | 显式建（`CREATE INDEX`） | 按用户取全部群组（左栏） |
| `sqlite_autoindex_vault_groups_2` | 主键 | 按 `id` 改名 / 删除 |

**这里的索引和 `sticky_notes` 的关系要说清楚**：唯一约束 `(user_id, name)` 其实已经能给「按用户查群组」用上，那为什么还显式建 `idx_vault_groups_user_id`？因为**唯一索引的最左列虽然能当普通索引用，但它的存在理由不是查询**——哪天把唯一约束掀了（比如允许重名），查询就会悄无声息地退化成全表扫。显式建一遍，两个需求各自有各自的索引，互不牵连。个人量级下这点冗余不值得省。

**条目表不建 `(user_id, group_id)` 联合索引**：条目按 `updated_at` 排序输出，`group_id` 只用来过滤；几百行规模下 SQLite 用 `user_id` 索引取全部再过滤足够快。等条目上千再说，现在建是为想象中的查询打补丁。

## 六、常用查询

```sql
-- 左栏：取这个人的全部群组，建得早的在上（带每个群组的条目数）
select g.id, g.name, g.created_at,
       (select count(*) from vault_items i where i.group_id = g.id and i.user_id = g.user_id) as item_count
from vault_groups g
where g.user_id = 1
order by g.created_at asc, g.id asc;

-- 改名（唯一约束会挡住重名：SqliteError: UNIQUE constraint failed）
update vault_groups set name = '银行' where id = 3 and user_id = 1;

-- 删群组：组内条目由外键自动变成未分组（要求 foreign_keys = ON）
delete from vault_groups where id = 3 and user_id = 1;

-- 看时间（毫秒转 +8 的人读时间）
select id, name, datetime(created_at/1000, 'unixepoch', '+8 hours') as created
from vault_groups order by id desc;
```

## 七、常见疑问

**Q：为什么群组名要唯一，条目标题却不唯一？**
群组是**导航**：左栏里出现两个「银行」，用户每次点都要猜哪个是对的。条目标题是**内容**：两个「招商银行信用卡」可能真的是两张不同的卡（尾号不同），标题一样完全合理，右栏的字段会把区别显示出来。

**Q：删群组为什么不把里面的条目一起删？**
群组是盒子，条目是盒子里真正值钱的东西。删盒子顺手烧掉里面的东西，是灾难性操作；而且条目已经有「移动到指定群组」的能力，正确的操作顺序是「先把要留的移走，再删盒子」。界面上的二次确认会写明「该群组还有 N 条记录，删除后它们变为未分组」，用户是知情后才点的。

**Q：为什么不做群组嵌套（群组里再建群组）？**
备忘录类产品里嵌套真的发生了才值得做。个人记录量级下，一层分类够用；两层会让左栏变成树，还要额外定义「父群组被删时子群组怎么办」。真需要时，加一列 `parent_id` 即可，不用现在建。

**Q：群组能排序吗？**
不能，也不需要。排序规则就是建组顺序（`created_at ASC`），稳定、可预期。想做手动排序得给群组加 `position` 列并在拖拽后批量重排——这不是现在的需求。

**Q：群组能设颜色 / 图标吗？**
不能。全站是黑白灰基调（《界面设计规范》），图标只会让左栏变成一排彩色贴纸，反而降低扫读效率。
