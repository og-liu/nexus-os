# 抖音链接映射表（douyin_links）

> **一行 = 「这条分享链接对应哪个作品」。** 它回答的问题是：「这个短链我之前解析过吗？能不能不再花一次钱？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已上线 | 2026-11-02 | 2026-11-03 |

## 一、怎么理解它

抖音的分享链接有两种：

- **长链**：`https://www.douyin.com/video/7702415046048193446` —— 里面**直接带着作品 id**，不需要这张表
- **短链**：`https://v.douyin.com/xxxxxx/` —— 六七个随机字符，**看不出是哪个视频**，只有请求一次上游（或跟一次 302）才知道

短链是分享时最常见的形态。如果没有这张表，同一条短链每贴一次就要重新解析一次——而每次都是钱。
所以把「链接 → 作品 id」这条对应关系记下来，第二次贴同一条链接就能直接跳到缓存。

它和 `douyin_videos` 是**从属关系**：映射指向的作品行被清掉时，映射也跟着删（`ON DELETE CASCADE`）。
留一条指向不存在作品的映射，会让系统以为「这条链接解析过」，然后查缓存查了个空。

## 二、这张表管什么

- **短链解析成功**：记下 `share_url → aweme_id`
- **贴短链之前**：先查这里，命中就直接用 `aweme_id` 去 `douyin_videos` 取数据，不发请求
- **作品行被清理时**：映射跟着一起删（级联）
- 长链不进这张表——它自带 id，查了也是白查

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS douyin_links (
  share_url  TEXT    PRIMARY KEY,
  aweme_id   TEXT    NOT NULL REFERENCES douyin_videos(aweme_id) ON DELETE CASCADE,
  fetched_at INTEGER NOT NULL
);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `share_url` | TEXT | 主键 | 用户贴进来的那条链接（原样） | 直接当主键：同一条链接只可能对应一个作品，不需要自增 id |
| `aweme_id` | TEXT | NOT NULL，外键 → `douyin_videos.aweme_id`，**级联删除** | 这条链接解析出来是哪个作品 | 级联是硬要求：作品的直链过期被清掉后，留着映射会让人以为「解析过」，实际查出来是空的 |
| `fetched_at` | INTEGER | NOT NULL | 这条映射是什么时候记下的（毫秒时间戳） | 排查用；目前**不拿它判断过期**——映射是「链接 → id」，id 不会过期，作品行没了会级联删掉 |

## 五、索引

只有主键 `share_url`。查询只有一种：「拿这条链接来换 id」。

## 六、常用查询

```sql
-- 现在记了多少条映射
SELECT COUNT(*) FROM douyin_links;

-- 某条短链对应哪个作品
SELECT aweme_id FROM douyin_links WHERE share_url = 'https://v.douyin.com/xxxxxx/';

-- 看有没有悬空映射（正常情况下应该永远是 0 行）
SELECT l.share_url
FROM douyin_links l
LEFT JOIN douyin_videos v ON v.aweme_id = l.aweme_id
WHERE v.aweme_id IS NULL;
```

## 七、常见疑问

**为什么不把短链「展开」成真实地址再存，而要单独建一张表？**
展开就需要发一次请求，而那次请求同样要钱。直接记「我解析出来的 id」更省，也更稳——展开的结果还可能带一堆追踪参数。

**长链为什么不用存？**
`https://www.douyin.com/video/7702415046048193446` 里的数字就是 `aweme_id`，正则抠出来直接用，查一次表纯属浪费。

**同一首歌的短链会有很多条吗？**
会。用户可能从不同渠道拿到不同的短链，都指向同一个作品。表里会存多行、指向同一个 `aweme_id`，这是正常的。
每行只是几十字节，比多一次付费调用便宜得多。
