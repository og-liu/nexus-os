# 音乐歌单表（playlists / playlist_tracks）

> **一张表是歌单本身，另一张是「哪首歌在哪个歌单里」。**
> 它们回答的问题是：「这个人建了哪些歌单？每个歌单里有哪些歌？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-11-03 | 2026-11-03 |

## 一、怎么理解它

歌单是**一层挂在曲目上面的分类**，不复制歌曲：`music_tracks` 里一行还是一首歌，歌单只记
「这首歌属于哪几个歌单」。所以：

- 同一首歌可以同时出现在**多个**歌单里（「通勤」和「收藏」都收它），这是多对多的唯一理由；
- 删歌单**不删歌**——只删关联行，歌还在曲库里；
- 删歌**会**把关联行一起带走（外键 `ON DELETE CASCADE`），否则歌单里会留下指向空气的条目。

跟 `md_tags` / `md_document_tags` 的关系一模一样：一张表存分类，一张表存归属。区别是这里
**歌单内的顺序是独立的 `position` 列**（2026-11-03 起可以拖拽）。它跟 `music_tracks.position` 是两套，互不影响：在歌单里排顺序不会把「全部歌曲」也搅乱。

## 二、这两张表管什么

**`playlists`**

- **建歌单**：插一行（`name` 同一个人不许重名）
- **改名**：`UPDATE name`，同时刷 `updated_at`
- **删歌单**：删一行，`playlist_tracks` 里的关联由外键级联删掉
- 它**不**存封面、描述、播放次数——第一版都没有

**`playlist_tracks`**

- **把歌加进歌单**：插一行（`PRIMARY KEY (playlist_id, track_id)` 保证同一首不会重复加两次）
- **从歌单移除**：删一行
- **读歌单里的歌**：`WHERE playlist_id = ? ORDER BY position ASC, track_id ASC`
- **拖拽排序**：`reorderPlaylistTracks()` 把整份新顺序写回 `position`（一次事务逐行写）

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS playlists (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name       TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE (user_id, name)
);

CREATE INDEX IF NOT EXISTS idx_playlists_user_id ON playlists(user_id);

CREATE TABLE IF NOT EXISTS playlist_tracks (
  playlist_id INTEGER NOT NULL REFERENCES playlists(id) ON DELETE CASCADE,
  track_id    INTEGER NOT NULL REFERENCES music_tracks(id) ON DELETE CASCADE,
  position    INTEGER NOT NULL,
  added_at    INTEGER NOT NULL,
  PRIMARY KEY (playlist_id, track_id)
) WITHOUT ROWID;

-- 反查「这首歌在哪些歌单里」要按 track_id 找；外键不自动建索引
CREATE INDEX IF NOT EXISTS idx_playlist_tracks_track ON playlist_tracks(track_id);
```

## 四、逐字段说明

### playlists

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 歌单编号 | 前端到处用它寻址 |
| `user_id` | INTEGER | 非空，外键 → `users.id`，级联删除 | 歌单属于谁 | 每条查询都带；删账号时整片消失 |
| `name` | TEXT | 非空 | 歌单名 | 同一个人不能重名（见下面的唯一约束） |
| `created_at` | INTEGER | 非空 | 建立时刻（毫秒） | 左栏排序依据（建得早的在上） |
| `updated_at` | INTEGER | 非空 | 最后改动时刻（毫秒） | 改名或增删曲目时刷新；将来要做「最近用过的歌单」靠它 |

**`UNIQUE (user_id, name)`**：同一个人不能有两个同名歌单——否则左栏出现两个「通勤」，
用户分不清点哪个。不同的人当然可以各有一个「通勤」。

### playlist_tracks

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `playlist_id` | INTEGER | 非空，外键 → `playlists.id`，级联删除 | 属于哪个歌单 | 复合主键的一半 |
| `track_id` | INTEGER | 非空，外键 → `music_tracks.id`，级联删除 | 是哪首歌 | 复合主键的另一半；**删歌时这行自动消失** |
| `position` | INTEGER | 非空 | 歌单内顺序（升序） | 拖拽产生；新加的歌追加到末尾；跟曲库的 `position` 互不影响 |
| `added_at` | INTEGER | 非空 | 加进来的时刻（毫秒） | 只做记录，不再决定顺序 |

`WITHOUT ROWID`：这张表只用复合主键查询与写入，不需要额外的 rowid，省一份索引。

## 五、索引

| 索引 | 服务于哪个查询 |
|---|---|
| `idx_playlists_user_id` | 左栏列歌单（`WHERE user_id = ?`） |
| `idx_playlist_tracks_track` | 反查「这首歌属于哪些歌单」（编辑弹框要勾选）；SQLite 不为外键自动建索引 |
| 主键 `(playlist_id, track_id)` | 打开歌单看曲目、判断某歌是否已在歌单里 |

## 六、常用查询

```sql
-- 某人的所有歌单 + 每个歌单几首
SELECT p.id, p.name, count(pt.track_id) AS n
FROM playlists p
LEFT JOIN playlist_tracks pt ON pt.playlist_id = p.id
WHERE p.user_id = 1
GROUP BY p.id
ORDER BY p.created_at ASC, p.id ASC;

-- 某个歌单里的歌（按用户拖出来的顺序）
SELECT t.id, t.title, t.artist
FROM playlist_tracks pt
JOIN music_tracks t ON t.id = pt.track_id
WHERE pt.playlist_id = 7 AND t.user_id = 1
ORDER BY pt.position ASC, pt.track_id ASC;

-- 一首歌属于哪些歌单
SELECT playlist_id FROM playlist_tracks WHERE track_id = 42;
```

## 七、常见疑问

**「为什么不做歌单内拖拽排序？」**
拖拽排序要一套指针交互 + 一个 `position` 列 + 每次拖动批量重排（`position` 冲突处理）。
~~第一版用「加入时间」已经能表达顺序~~ **已推翻**：真正用起来才发现脑子里的顺序跟加进来的顺序对不上。现在是 `position` + 拖拽，`reorderPlaylistTracks()` 全量重写。

**「删歌单会不会把歌删掉？」**
不会。`playlist_tracks` 只是关联，删歌单级联删的是**关联行**，`music_tracks` 一行不动。

**「一首歌能被加进同一个歌单两次吗？」**
不能。复合主键 `(playlist_id, track_id)` 会直接拒绝；加歌用的是 `INSERT OR IGNORE`，
重复加不报错也不多一行。

**「歌单名为什么不允许重名？」**
左栏是两个并列入口，两个都叫「通勤」就分不清。改名时同样走这条唯一约束，
重名会被拒绝并给一句人话（不是抛 `SQLITE_CONSTRAINT`）。
