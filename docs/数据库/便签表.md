# 便签表（sticky_notes）

> **一行 = 一张便签。** 它回答的问题是：「这个人随手记下了什么？」

| 状态 | 建立 | 最近更新 |
|---|---|---|
| ✅ 已上线 | 2026-10-17 | 2026-10-22 |

## 一、怎么理解它

便签是「随手贴」，不是笔记：**一行里只有一段正文**，没有标题、没有分类、没有层级。找它不是靠翻目录，而是靠「什么时候写的」和「有没有被置顶」。

它和将来的知识条目（笔记 / 文章）是两回事：知识是**要整理、要被 AI 读懂**的内容，便签是**贴完就忘**的内容。所以这张表刻意长得很瘦——字段一多，它就会忍不住往笔记的方向长。

## 二、这张表管什么

- **新建便签**：加一行（`body` + `user_id` + 两个时间）
- **编辑正文**：改 `body`，同时把 `updated_at` 刷新成当前时间
- **置顶 / 取消置顶**：写 `pinned` 与 `pinned_at`（置顶 = 现在；取消 = NULL），**不碰 `updated_at`**
- **删除便签**：删掉这一行（没有软删除、没有回收站）
- **首页便签卡**：读它 —— 按「置顶优先 + 置顶时间 / 更新时间倒序」取前 3 行
- 它**不**记录「在哪台设备写的」「有没有被读过」——现在没有这些需求（见 §七）

## 三、建表 SQL 原文

```sql
CREATE TABLE IF NOT EXISTS sticky_notes (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  body       TEXT    NOT NULL,
  pinned     INTEGER NOT NULL DEFAULT 0,
  pinned_at  INTEGER,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_sticky_notes_user_id ON sticky_notes(user_id);
```

## 四、逐字段说明

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这张便签的内部编号 | 与 `users` 同款：`AUTOINCREMENT` 保证编号永不复用，删掉的便签不会把号让给下一张 |
| `user_id` | INTEGER | NOT NULL，外键 → `users.id`，级联删除 | 这张便签属于谁 | 现在只有一个用户，但归属从第一天就写进数据里；以后加人不用改表。级联删除保证删账号时不会留下无主的便签 |
| `body` | TEXT | NOT NULL | 便签正文 | 只存纯文本：不存 HTML、不存 Markdown。渲染时按纯文本显示，天然没有 XSS 面；换行靠 `whitespace-pre-wrap` 呈现，不用再存一份「格式化结果」 |
| `pinned` | INTEGER | NOT NULL，默认 0 | 是否置顶：`1` 置顶、`0` 普通 | SQLite 没有布尔类型，用 0/1；它能直接参与排序（`ORDER BY pinned DESC`）。置顶操作**不改 `updated_at`**，否则「更新时间」会变成谎话 |
| `pinned_at` | INTEGER | 可为 NULL | 什么时候置顶的（毫秒时间戳）；NULL = 未置顶 | 置顶组内要按「最近置顶的在前」排，而置顶不刷新 `updated_at`，没有这一列刚置顶的旧便签会沉到末尾。老库由 `initSchema()` 幂等补列，并把已有的置顶行回填成 `updated_at` |
| `created_at` | INTEGER | NOT NULL | 这张便签什么时候写的（毫秒时间戳） | 展示与排查要用；毫秒是数值，能直接比较、相减（《数据库/README》§二） |
| `updated_at` | INTEGER | NOT NULL | 最后一次**改正文**的时间（毫秒时间戳） | 列表排序的主依据。只有改正文才刷新——置顶不算「更新」，否则取消置顶后便签会莫名其妙跳到最前 |

## 五、索引

| 索引 | 由什么产生 | 服务于哪个查询 |
|---|---|---|
| `idx_sticky_notes_user_id` | 显式建（`CREATE INDEX`） | 按用户取全部便签：工具页列表、首页前 3 条 |
| `sqlite_autoindex_sticky_notes_1` | 主键（rowid 别名） | 按 `id` 更新 / 删除 |

**为什么按 `user_id` 建索引**：SQLite 只为 `UNIQUE` 和主键自动建索引，不为主键以外的外键建。现在一张表里只有一个人的数据，扫全表也很快；但查询天然是按 `user_id` 过滤，索引要从现在就有，以后人多才不用回头补。

**排序本身没有专门索引**：`ORDER BY pinned DESC, pinned_at DESC, updated_at DESC, id DESC` 在个人量级（几百行）走一遍索引扫描就够了；等数据量或查询模式变了再考虑联合索引，现在提前建只会增加写放大。

## 六、常用查询

```sql
-- 按界面的排序看全部便签（置顶优先、组内按置顶时间、其余按更新时间、id 兜底）
select id, body, pinned, pinned_at, updated_at
from sticky_notes
where user_id = 1
order by pinned desc, pinned_at desc, updated_at desc, id desc;

-- 首页便签卡：同样的排序，只取 3 条
select id, body, pinned, pinned_at, updated_at
from sticky_notes
where user_id = 1
order by pinned desc, pinned_at desc, updated_at desc, id desc
limit 3;

-- 看时间（毫秒转 +8 的人读时间）
select id, body, pinned,
       datetime(created_at/1000, 'unixepoch', '+8 hours') as created,
       datetime(pinned_at/1000, 'unixepoch', '+8 hours') as pinned,
       datetime(updated_at/1000, 'unixepoch', '+8 hours') as updated
from sticky_notes order by id desc;
```

## 七、常见疑问

**Q：为什么表名是 `sticky_notes`，不就叫 `notes`？**
`notes` 这个词要留给以后的笔记 / 知识条目（知识页的正文、文章）。同一张库里「便签」和「笔记」是两种东西，词先分清，以后才不会出现一张表两种含义。表名与工具 slug（`sticky-notes`）一致，排查时不用翻译。

**Q：为什么没有 `title`？**
便签的价值是**少做一次决定**：写下第一行字就是内容。加标题意味着每次新建都要想「标题写什么」，而大多数便签只有一句话。

**Q：为什么不做软删除（`deleted_at`）？**
软删除的代价是**每一个查询都要记得带上 `deleted_at is null`**，漏一处就会把已删的便签重新显示出来；还会引出「什么时候真删」的清理任务。便签误删的代价本来就不高，界面上的二次确认更便宜。

**Q：置顶为什么同时要 `pinned` 和 `pinned_at`，不嫌多吗？**
`pinned` 回答「是不是」，`pinned_at` 回答「什么时候置顶的」——后者是置顶组内的排序依据。没有它，刚置顶的旧便签只能按 `updated_at` 沉到置顶区末尾，用户会以为置顶没生效。两列是**同一件事的两面**，只在 `setNotePinned` 一处一起写：置顶写 `pinned=1, pinned_at=now`，取消写 `pinned=0, pinned_at=NULL`。

**Q：老库怎么补 `pinned_at`？**
`initSchema()` 里的 `migrateStickyNotePinnedAt()` 先看 `PRAGMA table_info`：列不存在才 `ALTER TABLE ... ADD COLUMN`，并把已置顶的行回填成 `pinned_at = updated_at`（保留原来的相对顺序）；列已存在就什么都不做，重复启动不会覆盖新置顶的时间。

**Q：正文超过 1000 字会怎样？**
服务端拒绝保存，界面给字段级提示。上限是保护：便签写成长文，说明它该去知识页了。按字符数计（`Array.from`），一个汉字算 1、一个 emoji 也算 1。

**Q：便签可以属于多个用户吗？**
不可以。一行一个 `user_id`，归属唯一。多用户共享是另一个功能（协作），现在连影子都没有。
