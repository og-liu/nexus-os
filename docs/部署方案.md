## 一、目标

1. 通过域名 `https://nexusos.work` 访问到真实运行的线上服务
2. 本地改完代码，**一条命令（或直接 push）就让线上更新**
3. **真实生产形态**，不是 demo：真构建、真反向代理、真 HTTPS、真自动部署
4. 过程可学习、可回溯

---

## 二、最终架构

```
浏览器
  │  https://nexusos.work   (443)
  ▼
阿里云 ECS · 华东1（杭州）
  └─ Nginx                     反向代理 + HTTPS 证书终止
       │  http://127.0.0.1:3000
       ▼
     Next.js 生产服务（next build 产物 + next start）
       └─ systemd 守护：进程崩了自动拉起，开机自启
```

**为什么中间要有 Nginx**：Next.js 自己跑在 3000 端口上，不直接对外。Nginx 负责 443 端口、证书、压缩、静态资源缓存，以及把请求转发给本地服务。这是标准生产形态。

## 三、CI/CD 概念速查

本地 `git push` 之后，GitHub 会临时借一台机器替你跑一串任务：

```
本地 git push origin main
   ↓
GitHub Actions 临时机器
   ① 拉代码  ② 装依赖  ③ 类型检查  ④ 代码规范  ⑤ 构建   ← 这一段叫 CI（持续集成）
   ⑥ 通过 SSH 把构建产物传到服务器                        ← 这一段叫 CD（持续部署）
   ↓
ECS：更新产物 → 重启服务 → 新版本上线
```

| 名词 | 大白话 |
|---|---|
| **CI**（持续集成） | 每次提交自动跑检查与构建，防止坏代码进主干 |
| **CD**（持续部署） | 检查通过后自动发布到服务器 |
| **Workflow** | 一个 YAML 文件，描述「什么时候、做什么」 |
| **Runner** | GitHub 提供的临时执行机器，跑完即销毁 |
| **Job / Step** | 流水线里的阶段 / 阶段里的一步 |
| **Secrets** | 加密存放的密钥（服务器地址、SSH 私钥等），只有流水线能读，日志自动打码 |
| **push-to-deploy** | CD 的最简形态：推送即上线 |

**触发规则**：只有 `push` 到 `main` 才执行发布；其他分支只跑检查、不上线。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| **在哪儿构建** | **在 GitHub Actions 上构建**，服务器只跑产物 | 服务器只有 2 GiB 内存，`next build` 大概率 OOM；CI 机器内存管够，且这就是 CI 该干的活 | 服务器上构建（否决：内存不足，且服务器被迫装整套构建工具链，不干净） |
| **产物怎么上去** | **SSH 传输构建产物**（待确认） | 服务器不必装 git 与完整工具链，只留运行依赖 | 服务器上 `git pull` 再本地构建（否决：又回到服务器构建的 OOM 问题）；Docker 镜像（否决：当前规模下概念负担过重） |
| **反向代理** | **Nginx**（已定） | 资料最多、生产环境最通用，值得学 | Caddy（否决：配置更简单但学习价值低） |
| **进程守护** | systemd（待确认） | 系统自带、无需额外依赖、开机自启天然支持 | pm2（否决：多一个全局依赖，且需要额外维护其自身） |
| **HTTPS 证书** | Let's Encrypt 系（acme.sh / certbot），自动续期（待确认） | 免费、自动续期、业界标准 | 阿里云付费证书（否决：没必要） |
| **部署形态** | 单机单体（待确认） | 当前规模没有多机需求 | 负载均衡 / 多实例（否决：过度设计） |

## 五、已知环境事实

| 项 | 值 |
|---|---|
| 域名 | `nexusos.work` |
| 域名注册商 | 阿里云 |
| 服务器 | 阿里云 ECS · 华东1（杭州） |
| 实例规格 | 经济型 e `ecs.e-c1m1.large`（2 vCPU / 2 GiB） |
| 操作系统 | Alibaba Cloud Linux 3.2104 LTS 64 位 |
| 系统盘 | ESSD Entry 40 GiB（无数据盘） |
| 公网带宽 | 固定带宽 **3 Mbps**（峰值约 375 KB/s） |
| 计费方式 | 包年包月 |
| 代码仓库 | https://github.com/og-liu/nexus-os （私有 commit 推送到 main） |

> **带宽提醒**：3 Mbps 是峰值约 375 KB/s，个人作品站够用，但 Next.js 首屏资源较大，首次访问会有等待。后续可让静态资源走 OSS + CDN。

## 六、分步计划

### 阶段 A · 手工部署一次（让域名/服务真的跑起来）

先手工做通一遍，才知道「自动化」到底要自动化什么 —— 跳过硬做 CI/CD，出错会不知道错在哪。

1. ECS 创建与初始化
   - 设置登录凭证（密钥对）
   - 安全组放行 **22**（限来源 IP）、80、443
   - 更换实例名称（去掉系统默认名）
2. 服务器环境
   - 装 Node.js 22、pnpm
   - 装 Nginx
   - 建部署目录与运行用户
3. 首次上线
   - 本地构建产物 → 传到服务器
   - 服务器装生产依赖 → `next start`
   - 写 systemd 服务（守护 + 开机自启）
   - 写 Nginx 反向代理配置
4. 验证：用 `http://公网IP:3000` 与服务直连、再用 `http://公网IP:80` 经 Nginx，确认整条链路通

### 阶段 B · 接上 GitHub Actions（真正的 CI/CD）

1. 生成**部署专用** SSH 密钥对（不复用本机现有密钥）
2. 服务器上配置该公钥、限制权限
3. 在 GitHub 仓库配置 Secrets（服务器地址、用户、私钥等）
4. 编写 `.github/workflows/deploy.yml`：检查 → 构建 → 传输 → 重启
5. 验证：本地改一次代码 → `git push` → 观察流水线 → 线上自动更新

### 阶段 C · 域名与 HTTPS

1. 域名解析：A 记录指向 ECS 公网 IP
2. **ICP 备案通过**（前置条件）
3. 申请证书 + 配置 Nginx 的 443
4. 配置自动续期
5. 验证：`https://nexusos.work` 正常访问，证书链完整

> **阶段 C 依赖备案**，备案与 A、B **并行推进**，不阻塞开发。

## 八、风险与注意事项

| 风险 | 说明 | 对策 |
|---|---|---|
| **备案周期** | 现实约 2~4 周，期间域名无法访问内地服务器 | 备案立刻开跑，与开发并行；期间用 `http://公网IP:3000` 验证 |
| **服务器内存** | 2 GiB，跑构建会 OOM | 构建放到 CI 上做；必要时加 swap |
| **带宽较小** | 3 Mbps ≈ 375 KB/s 峰值 | 静态资源后续走 OSS + CDN |
| **单盘存储** | 只有一块 40 GiB 系统盘，实例释放即全部丢失 | 数据（数据库文件等）定期备份；关键配置纳入仓库 |
| **密钥安全** | 部署私钥泄露 = 服务器失守 | 部署用**独立**密钥对，不复用个人密钥；GitHub 中存为 Secret；服务器上限制授权来源 |
| **回滚能力** | 部署失败要能退回上一版 | 部署目录保留上一版，或按版本号保留多个目录 + 软链接切换 |
| **环境变量** | 密钥不能进仓库 | 服务器上单独维护环境变量文件，权限收紧；仓库只保留 `.env.example` |
