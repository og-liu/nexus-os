## 一、日常操作

### 改代码上线（走「分支 + PR」，见《Git协作规范》）

```bash
# 1. 开分支（基线取最新 main）
git switch -c lingda/<短名> origin/main
# 2. 改代码；本地过门禁（三项全绿再推，CI 也会跑一遍同样的检查）
pnpm typecheck && pnpm lint && pnpm test
pnpm dev                      # 需要肉眼看界面时再起
# 3. 提交、推分支，在 GitHub 开 PR → Squash 合并进 main
git add -A && git commit -m "feat: xxx" && git push -u origin lingda/<短名>
```

合并进 **main** 后自动完成：**检查 → 构建 → 传服务器 → 切版本 → 重启**，约 1 分钟。
只有 **main** 更新才部署，其他分支只跑检查；直接推 `main` 不再允许（纪律，见《Git协作规范》）。

### 看状态 / 排障 / 回滚

| 想干什么 | 怎么做 |
|---|---|
| 看流水线跑得怎样 | GitHub 仓库 → **Actions** 页，或 `gh run list` |
| 手动触发一次发布 | `gh workflow run deploy.yml` |
| 看服务活着吗 | `ssh root@<公网IP> 'systemctl status nexus-os'` |
| 看服务日志 | `ssh root@<公网IP> 'journalctl -u nexus-os -n 50'` |
| **回滚上一版** | `ssh root@<公网IP> 'sudo /opt/nexus-os/bin/release.sh --rollback'` |
| 部署卡在 `Set up job` 好几分钟 | 多半不是我们的问题：runner 在下载 action 时超时重试（annotation 里是 `Failed to download action ... HttpClient.Timeout of 100 seconds` + `Back off … before retry`）。等它重试完就行，不用改代码 |

> 发布脚本是**幂等**的，可以手动重跑 —— 它就是排障入口：出问题时 SSH 进去跑同一条命令就能复现。

## 二、它现在长什么样

```
浏览器 ──► Nginx（80/443）──► 127.0.0.1:3000 ──► Next.js 服务（systemd 守护）
                                                      ▲
                                      current 软链接 ──┘──► releases/<时间戳>/
```

一次发布的数据流：

```
git push
  → GitHub Actions 机器：检查 → 构建 → 打发布包（12 MB）
  → SSH 传到服务器 incoming/
  → 服务器 release.sh：解到 releases/<时间戳>/ → 切 current → 重启 → 自检 → 清理旧版
```

服务器目录：

```
/opt/nexus-os/
├── releases/<时间戳>/    每次发布一个新目录，保留最近 5 个
├── current →            指向当前版本的软链接（切换是原子的）
├── incoming/            CI 传包的落点
├── bin/release.sh       发布 / 回滚脚本
└── shared/              跨版本保留：发布只解包进 releases/，从不碰这里
    ├── .env.production  环境变量（systemd 的 EnvironmentFile）
    └── data/nexus-os.db SQLite 数据库文件
```

> **`shared/data/` 不能少。** standalone 产物的进程工作目录是 `releases/<时间戳>/`，
> 数据库路径**不能**靠相对路径推导（原因见 `src/lib/auth/db.ts`）。不设 `DATABASE_PATH`，
> 数据库就会落在发布目录里——下一次发布换了目录，账号数据就直接消失，
> 而且要等第 6 次发布清理旧版本时才彻底丢掉。线上在 `shared/.env.production` 里指定绝对路径：
>
> ```
> DATABASE_PATH=/opt/nexus-os/shared/data/nexus-os.db
> ```
>
> 目录与文件属主都必须是服务运行用户 `nexus`，否则进程连建库都会失败。
> 域名备案完成、HTTPS 上线后再加一行 `SESSION_COOKIE_SECURE=true`（变量登记表见《技术栈说明》§4.3）。
>
> **实测（2026-10-15 17:34）：手动触发一次发布后，`current` 换了新版本目录，而库里的账号仍然在。**
> 这条设计到此不再只是"应该没问题"。

## 三、为什么这么设计

每条都是「选了 A，因为 B，否则 C」：

| 决策 | 选择 | 为什么 | 不这么做会怎样 |
|---|---|---|---|
| 在哪儿构建 | **CI 上构建** | 服务器只有 2 GiB，跑生产构建会 OOM | 构建被 OOM Killer 杀掉 |
| 产物形态 | **`output: "standalone"`** | 自带最小运行依赖，服务器不必装 pnpm、不必联网 | 每次发布都要联网装包，慢且可能失败 |
| 依赖布局 | **`.npmrc` 设 `node-linker=hoisted`** | Next 的追踪器在 pnpm 软链布局下会漏拷文件 | 产物缺文件，**启动即崩**（已实测） |
| 发布方式 | **新目录 + 软链接切换** | 新旧共存，切换原子，可秒级回滚 | 原地覆盖：发布失败即全站挂且退不回去 |
| 发布自检 | **重启后检查服务活着** | 「重启命令返回 0」≠「服务真的起来了」 | 脚本报成功，站点却是 502 |
| 进程守护 | **systemd** | 系统自带、开机自启、日志进 journald | 服务挂了不会自动拉起 |
| 运行身份 | 服务用 `nexus`（不可登录） | 服务不以 root 运行 | 服务被攻破等于整机被攻破 |
| 部署授权 | `deploy` **只被授权一条命令** | 密钥泄露的损失上限是「被发布一次」 | 泄露 = 交出整机 |

## 四、两个必须懂的安全概念

### 4.1 GitHub Secrets —— 密钥不能进仓库

**是什么**：仓库级的**加密变量**，只有流水线运行时才读得出来，日志里还会自动打码。

**为什么需要**：部署要连服务器，得有「地址 + 用户名 + 私钥」。这些**一旦写进仓库就永远留在 Git 历史里** —— 哪怕下一分钟删掉，checkout 到旧提交仍能捞出来。

**它保护什么、不保护什么**（关键）：
- ✅ 不进版本库、不出现在运行日志
- ❌ **不保护「能改 workflow 文件的人」** —— 所以还需要下一条

**本项目用了 3 个**：

| 名字 | 内容 |
|---|---|
| `SSH_HOST` | 服务器公网 IP |
| `SSH_USER` | `deploy` |
| `SSH_KEY` | 部署专用私钥全文 |

### 4.2 两把钥匙，各司其职

| 密钥 | 放在哪 | 能做什么 |
|---|---|---|
| `~/.ssh/nexus-os-deploy` | 你本机 | 登 `root`，做服务器管理 |
| `~/.ssh/nexus-os-ci` | GitHub Secrets | 登 `deploy`，**只有发布** |

**为什么必须分成两把**：如果 CI 用的就是能登 root 的那把，那「`deploy` 只授权一条命令」这道防线就白设了 —— 密钥一泄露，损失从「被发布一次」直接升级成「整机被拿走」。

服务器上的授权白名单只有一行（`/etc/sudoers.d/nexus-os-deploy`）：

```
deploy ALL=(root) NOPASSWD: /opt/nexus-os/bin/release.sh
```

## 五、已踩的坑

三条的共同点：**构建全绿，部署才炸**。

### 1. CI 里 `tsc` 必须排在 `next typegen` 之后

`LayoutProps` 这类类型由 Next 生成到 `.next/types/`，**不在仓库里**。本地因为跑过 dev 所以看不见，CI 干净环境必报 `Cannot find name 'LayoutProps'`。
→ 流水线里加一步 `pnpm exec next typegen`。

### 2. pnpm 默认布局会让 standalone 产物缺文件

实测同一个 `@swc/helpers@0.5.23`：真实包 **556** 个文件，产物里只有 **8** 个，整个 `esm/` 目录丢失 → 启动即崩（`Cannot find module .../_interop_require_default.js`）。
→ `.npmrc` 设 `node-linker=hoisted`。

### 3. 境内服务器拉不到 `raw.githubusercontent.com`

服务器上 `curl` 直接失败（HTTP 000 + TLS 错误），而同环境 `github.com`、`rpm.nodesource.com` **都正常** —— 是个别域名的问题。
→ 初始化时把 `deploy/` 推上去，用 `REPO_RAW=file:///tmp/nexus-boot` 运行初始化脚本，**脚本一行都不用改**。

> **一句话教训**：**「构建成功」不等于「产物能跑」。** 产物必须真的解包启起来点一次。

### 4. 能启动、页面能开，但一碰数据库就崩

**现象**：发布成功、页面返回 200，可一登录/注册就 500；`journalctl -u nexus-os` 里是
`ERR_DLOPEN_FAILED`，紧跟一句 `version 'GLIBC_2.33' not found`。

**机制**：原生模块的**预编译二进制是在比服务器更新的系统上编译的**，它要求的最低 glibc 比服务器高。
服务器是 Alibaba Cloud Linux 3（glibc **2.32**），而 `better-sqlite3@13` 随包分发的那份二进制要求 **2.34**。
本地与 CI 都测不出这个问题——两边的系统都比服务器新，这正是「本地全绿、线上全崩」的典型形状。

**对策**：把驱动锁在 12.x（那份预编译只要 2.29），并在 CI 里加一道自检步骤守这条线。
机制细节与查法见《技术栈说明》§3.5。
