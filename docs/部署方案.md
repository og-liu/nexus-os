## 二、最终架构

```
浏览器
  │  https://nexusos.work   (443)
  ▼
阿里云 ECS · 华东1（杭州）
  └─ Nginx                     反向代理 + HTTPS 证书终止 + 压缩 + 静态缓存
       │  http://127.0.0.1:3000
       ▼
     Next.js 生产服务（standalone 产物，node server.js）
       └─ systemd 守护：进程崩了自动拉起，开机自启
            └─ current 软链接 → releases/<时间戳>/   ← 每次发布一个新目录，可秒级回滚
```

**为什么中间要有 Nginx**：Next.js 自己跑在 3000 端口上，不直接对外。Nginx 负责 443、证书、压缩、静态资源缓存，再把请求转发给本地服务。这是标准生产形态。

## 三、CI/CD 概念速查

本地 `git push` 之后，GitHub 会临时借一台机器替你跑一串任务：

```
本地 git push origin main
   ↓
GitHub Actions 临时机器（ubuntu-latest）
   ① 拉代码  ② 装依赖  ③ 生成路由类型  ④ 类型检查  ⑤ 规范检查
   ⑥ 构建   ⑦ 组装发布包                                 ← 这一段叫 CI（持续集成）
   ⑧ 通过 SSH 把发布包传到服务器  ⑨ 触发服务器端切换发布      ← 这一段叫 CD（持续部署）
   ↓
ECS：解开新版本目录 → 切换 current 软链接 → 重启服务 → 验证活着 → 清理旧版本
```

| 名词 | 大白话 |
|---|---|
| **CI**（持续集成） | 每次提交自动跑检查与构建，防止坏代码进主干 |
| **CD**（持续部署） | 检查通过后自动发布到服务器 |
| **Workflow** | 一个 YAML 文件（`.github/workflows/deploy.yml`），描述「什么时候、做什么」 |
| **Runner** | GitHub 提供的临时执行机器，跑完即销毁 |
| **Job / Step** | 流水线里的阶段 / 阶段里的一步 |
| **Secrets** | 加密存放的密钥（服务器地址、SSH 私钥等），只有流水线能读，日志自动打码 |
| **push-to-deploy** | CD 的最简形态：推送即上线 |

**触发规则**：只有 `push` 到 `main` 才执行发布；其他分支只跑检查、不上线。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| **在哪儿构建** | **在 GitHub Actions 上构建**，服务器只跑产物 | 服务器只有 2 GiB 内存，`next build` 大概率 OOM；「构建并验证」本就是 CI 的职责 | 服务器上构建（否决：内存不足，且被迫在服务器装整套构建工具链） |
| **产物形态** | Next.js **`output: "standalone"`** | 产物自带运行所需的最小依赖，服务器**不需要装 pnpm、不需要 install**；发布包仅 12 MB | 传完整 `node_modules`（否决：体积大、3 Mbps 上传太慢）；服务器上 `pnpm install --prod`（否决：服务器要装 pnpm 且每次发布都要联网装依赖） |
| **依赖布局** | pnpm **`node-linker=hoisted`**（`.npmrc`） | 必须。默认的软链布局会让 standalone 追踪器漏拷文件（见「已踩的坑」第 2 条） | 保持默认软链布局（否决：产物缺文件，部署后启动即崩） |
| **发布怎么切换** | 每次发布解到 `releases/<时间戳>/`，用 `current` **软链接原子切换** | 新旧版本同时存在，切换瞬间完成，回滚只要把软链接指回上一个 | 原地覆盖（否决：发布失败即全站挂掉，且无法回滚） |
| **反向代理** | **Nginx** | 生产环境最通用、资料最多，学习价值高 | Caddy（否决：配置更简单但学到的东西更少） |
| **进程守护** | **systemd** | 系统自带、无额外依赖、开机自启天然支持、日志进 journald | pm2（否决：多一个全局依赖，还要额外维护它自己） |
| **运行身份** | 服务用 `nexus`（不可登录）；部署用 `deploy`（仅被授权跑发布脚本） | 服务不以 root 运行；CI 密钥即便泄露，也只能触发发布脚本，拿不到整机 | 全部用 root（否决：一旦密钥泄露等于交出整机） |
| **推进顺序** | ~~先手工部署再自动化~~ → **直接上 CI/CD** | 主人拍板直接上。为补上「手工基准」，发布脚本 `release.sh` 设计成**幂等、可手动重跑**，出问题时 SSH 进去手跑同一条命令即可复现 | 先手工部署一遍（否决：主人希望直接进入目标形态） |
| **部署形态** | 单机单体，不引入 Docker | 与当前规模匹配，减少需要同时消化的概念 | 容器化（否决：现阶段概念负担过重） |

## 六、分步计划

### 阶段 A · 打通部署链路（当前阶段）

1. **服务器初始化**（一次性，以 root 执行）
   - 装 Node.js 22、Nginx
   - 建 `nexus`（服务运行）、`deploy`（部署）两个用户
   - 建 `/opt/nexus-os` 目录结构，装发布脚本、Nginx 配置、systemd 单元
   - 只给 `deploy` 授权一条命令：`sudo /opt/nexus-os/bin/release.sh`
2. **打通 CI → 服务器**
   - 生成**部署专用** SSH 密钥对（不复用个人密钥）
   - 公钥写入服务器 `deploy` 用户
   - GitHub 仓库配置 Secrets：`SSH_HOST` / `SSH_USER` / `SSH_KEY`
3. **首次自动发布**：push 一次 → 观察流水线 → 确认线上服务起来
4. **验证**：`http://公网IP` 经 Nginx 能访问到服务

### 阶段 B · 域名与 HTTPS

1. **ICP 备案通过**（前置条件，**并行进行中**）
2. DNS 解析：A 记录指向 ECS 公网 IP
3. 申请证书（certbot / acme.sh）+ 配置 Nginx 443 + 自动续期
4. 80 端口跳转 443
5. 验证：`https://nexusos.work` 正常访问，证书链完整

> **阶段 B 依赖备案**，备案与阶段 A **并行推进**，不阻塞开发。备案期间用 `http://公网IP` 验证。

## 八、已踩的坑（实锤，两条）

### 1. CI 里 `tsc` 必须排在 `next typegen` 之后

**现象**：清空 `.next` 后直接跑 `pnpm exec tsc --noEmit`，报 `Cannot find name 'LayoutProps'`。

**根因**：Next 16 把路由/布局的类型（`LayoutProps` 等）生成到 `.next/types/`，这些文件**不在仓库里**。本地因为跑过 `dev` 或 `build`、`.next` 已存在，所以看不出问题；CI 是干净环境，必报。

**解决**：流水线里在 `tsc` 之前加一步 `pnpm exec next typegen`（只生成类型，不做完整构建，几秒完成）。

**一句话**：本地能过 ≠ CI 能过，干净环境才是真考验。

### 2. pnpm 默认软链布局会让 standalone 产物缺文件

**现象**：发布包在服务器/本地解包后启动即崩：`Cannot find module '.../@swc/helpers/esm/_interop_require_default.js'`。

**根因**：Next 的 standalone 文件追踪器在 pnpm 默认的软链（isolated）布局下**漏拷文件**。实测对比同一个 `@swc/helpers@0.5.23`：真实包 **556** 个文件，被追踪进产物的只有 **8** 个，整个 `esm/` 目录丢失。

**解决**：在 `.npmrc` 里设 `node-linker=hoisted`，让 `node_modules` 用扁平布局，追踪器即正常工作。改完重新验证：`esm/` 与关键文件都在，发布包启动后 HTTP 200。

**一句话**：`standalone` + pnpm 软链布局是已知不兼容组合，必须用扁平布局；而且**产物一定要真的启起来验证**，光看构建成功会漏掉这类问题。

### 3. 境内服务器拉不到 raw.githubusercontent.com

**现象**：服务器初始化脚本要从 GitHub 拉配套配置文件，在服务器上 `curl` 直接失败（`HTTP 000`，并伴随 TLS 连接错误）。

**根因**：境内网络对 `raw.githubusercontent.com` 的可达性差。同一次探测里 `github.com`、GitHub API、`rpm.nodesource.com` **全都正常**，只有这个域名不通 —— 是**个别域名**的问题，不是服务器断网。

**解决**：不让服务器去拉。把本地的 `deploy/` 目录直接推到服务器，再用 `REPO_RAW=file:///tmp/nexus-boot` 运行初始化脚本。`curl` 原生支持 `file://` 协议，所以**脚本一行都不用改**，同时保留了「配置只在仓库里存一份」的性质。

**一句话**：境内服务器别默认它拉得到 GitHub 的 raw 域名 —— **配置用推的，别用拉的。**

## 十一、为什么这么做：概念与工具详解

> 这一节写给「以后要能自己看懂、自己重做」的人。每一项都说清三件事：**它是什么、为什么需要它、不用它会怎样。**

### 11.1 gh CLI —— GitHub 的命令行客户端

**是什么**：GitHub 官方的命令行工具。本来要在网页上点击完成的事——建仓库、开 PR、配 Secrets、看流水线状态——都能在终端一条命令做完。

**这次为什么要用它**：用它**代为写入仓库的 Secrets**。网页上手动粘 3 次也能做，但：
- 私钥这类值不必在聊天窗、剪贴板里来回倒腾，少一次泄露机会
- 以后查流水线状态、拉失败日志，一条命令搞定，不用开浏览器

**不用它会怎样**：只能你手动在「仓库 → Settings → Secrets and variables → Actions」里逐个粘贴，私钥要过一次剪贴板。

**怎么装**：官方 macOS 安装方式有两种——Homebrew（`brew install gh`）或直接下载二进制包。本机**没有 Homebrew**，所以走二进制包（Apple Silicon 用 `macOS_arm64` 版）。

> **实测记录**：本机到 GitHub 的 **release 资源下载被限速**到约 19 KB/s，13.6 MB 的包预计要十几分钟。而 GitHub 的网页、API、`git push` 都正常 —— 只有 release 文件慢。这是国内访问 GitHub 的典型情况，不是网络坏了。
>
> 顺带一提：`gh --version` 会告诉你版本号；它只是一个**客户端**，本身不含任何权限，权限来自下一步的登录。

### 11.2 GitHub Secrets —— 加密存密钥的地方

**是什么**：仓库级别的**加密变量**。你在仓库设置里写入，GitHub 加密保存；只有流水线运行时才能读出来，并以环境变量的形式交给那一步用。

**为什么必须用它**：部署要连你的服务器，得有「服务器地址 + 用户名 + 私钥」——这三样**绝对不能写在仓库里**。原因是：
- 进了 Git 历史就**永远留在历史里**。哪怕下一分钟删掉，任何人 checkout 到旧提交都能捞出来。密钥一旦泄露等于作废，只能重新生成
- 仓库即使现在是私有的，也可能被协作者、第三方 App、或日后的「转为公开」操作扩散出去

**它还有一个你可能没注意的好处**：**日志自动打码**。就算脚本不小心把密钥打印出来，GitHub 会把日志里的值替换成 `***`。

**它保护什么、不保护什么**（这点很重要）：
- ✅ 保护：密钥不进版本库、不出现在运行日志里
- ❌ 不保护：**任何能改你 workflow 文件的人，都能让 workflow 把密钥发到别处**。所以密钥本身还不够，必须配合下一节的「服务器侧收权」才有意义

**这次要写入的 3 个**：

| Secret 名 | 内容 | 作用 |
|---|---|---|
| `SSH_HOST` | ECS 的公网 IP | 流水线该连哪台机器 |
| `SSH_USER` | `deploy` | 用哪个用户登录 |
| `SSH_KEY` | 部署专用**私钥**的全文 | 进门的钥匙 |

### 11.3 部署专用密钥对 —— 为什么不复用你本机那把

**是什么**：新生成的一对 SSH 密钥。**公钥**放服务器（等于告诉服务器「允许这把钥匙进来」），**私钥**放 GitHub Secret（等于 CI 手里拿着这把钥匙）。

**为什么不直接用你本机的 `~/.ssh/id_rsa`**：

1. 那把钥匙**能登进你所有用它的服务器**。把它复制到 GitHub，等于把「你所有机器的钥匙」交给一个会执行任意代码的地方
2. 万一泄露，你要补救的是「所有机器的所有授权」；而专用密钥泄露，只需在服务器上删掉一行

**第二道防线 —— 服务器侧收权**（这是让「密钥泄露」不致命的真正原因）：

即便私钥真的泄露了，`deploy` 这个用户在服务器上**只被授权跑一条命令**（发布脚本）。入侵者拿不到 shell、读不到别的文件、装不了任何软件、改不了任何配置。**损失被限制在「被发布一次」**，而不是「机器被拿走」。

**完整流程**：
1. 本机生成一对新密钥（**私钥不设密码** —— 因为 CI 无法交互输入密码）
2. 公钥追加到服务器的 `/home/deploy/.ssh/authorized_keys`
3. 私钥全文写进 GitHub Secret `SSH_KEY`
4. 本机的私钥副本用完即可删除 —— 它只需要存在于两个地方：服务器（公钥那半）和 GitHub（加密）

**实际落地时用了两把钥匙，各司其职**：

| 密钥 | 用在哪 | 能做什么 |
|---|---|---|
| `~/.ssh/nexus-os-deploy` | 本机运维，登 `root` | 服务器管理（装环境、看日志、排障） |
| `~/.ssh/nexus-os-ci`（写进 GitHub Secret） | CI 登 `deploy` 用户 | **只有发布**，拿不到 shell、装不了软件 |

分成两把的关键理由：如果 CI 用的就是能登 root 的那把，前面说的「收权」就白做了 —— 密钥一泄露，损失立刻从「被发布一次」升级成「机器被拿走」。

### 11.4 谁拿着什么：一张图看清边界

```
你的 Mac                  GitHub                      ECS 服务器
──────────               ──────────                  ──────────────
源码 ─────push──────────► 仓库
                          │
                          └─ Actions 运行时
                               读 Secrets ──► 拿到 IP / 用户 / 私钥
                                             │
                                             └──ssh(私钥)──► deploy 用户
                                                             │
                                                             └─ sudo 白名单
                                                                 仅 release.sh
                                                                 ├─ 解包新版本
                                                                 ├─ 切 current 软链接
                                                                 ├─ 重启服务 + 自检
                                                                 └─ 清理旧版本
```

三条边界：
- 仓库里**没有任何密钥**
- 私钥只存在于两处：GitHub Secrets（加密存放）与服务器上的公钥那一半
- CI 在服务器上能做的事**只有「发布」**，别的什么都不能

### 11.5 每一步为什么这么做

| 步骤 | 做什么 | 为什么 | 不这么做会怎样 |
|---|---|---|---|
| 构建放 CI | 在 GitHub 的机器上 build | 服务器只有 2 GiB 内存，跑生产构建会 OOM | 构建被 OOM Killer 杀掉或整机卡死 |
| 产物用 standalone | 自包含，自带最小运行依赖 | 服务器不必装 pnpm、不必联网装依赖 | 每次发布都要联网装包，慢，且可能因网络失败 |
| `node-linker=hoisted` | 改依赖目录布局 | Next 的文件追踪器在 pnpm 软链布局下会漏拷文件 | 产物缺文件，**启动即崩**（已实测） |
| `next typegen` 排在 `tsc` 前 | 先生成类型再类型检查 | 类型文件由框架生成，不在仓库里 | CI 干净环境**类型检查必报错** |
| 每次发布用新目录 | `releases/<时间戳>/` | 新旧版本同时存在，可秒级回滚 | 原地覆盖，发布失败即全站挂且退不回去 |
| 软链接切换 | 切换 `current` 指针 | 切换是**原子**的，瞬时完成 | 直接改文件会出现「半截状态」 |
| 发布脚本自检 | 重启后查服务是否活着 | 「重启命令返回 0」≠「服务真的起来了」 | 脚本报「发布成功」，但站点是 502 |
| 部署用户只授权一条命令 | sudoers 白名单 | 把密钥泄露的损失限制在「发布一次」 | 一旦泄露等于交出整台机器 |
| 产物先解包跑一遍 | 本地端到端验证 | 「构建成功」≠「产物能跑」 | 问题留到服务器上才暴露，且报错难以理解 |
| 用新目录而非覆盖 | 保留最近 5 个版本 | 出问题能立刻退回去 | 只能重发一次，赌它这次能成 |
