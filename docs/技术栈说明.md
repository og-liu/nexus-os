## 三、分层说明

### 3.1 运行时与工具链

**Node.js 22.23.2** —— 版本由 `.nvmrc` 固化，`package.json` 的 `engines` 声明下限
`>=22.0.0`。选 22 LTS 线的两个理由：原生模块所需的 NAPI 版本支持，以及稳定的 ESM 实现。

**pnpm 10.34.5** —— 通过 `package.json` 的 `packageManager` 字段锁定，`pnpm-lock.yaml`
随代码入库。**项目只使用 pnpm**，npm / yarn 会产生不一致的依赖树。

### 3.2 框架层：Next.js 16（App Router）

项目采用**全栈单体**形态：页面、后端接口、数据访问都在同一个仓库、同一个进程里，
不拆独立后端服务。

- **文件系统路由**：`src/app/**/page.tsx` 是页面，`src/app/**/route.ts` 是 HTTP 接口
  （导出 `GET` / `POST` / `PATCH` / `DELETE` 等函数）。
- **React Server Components 优先**：默认在服务端渲染；只有需要浏览器交互、状态或副作用的
  模块才在文件顶部写 `"use client"`。能在服务端拿到的数据，不必绕一圈走 API。
- **数据入口以 Server Action 为主**：表单提交、增删改查这类「一次性往返」的操作写成
  `"use server"` 的函数，前端直接 `await` 调用——自己不用写接口、不用写校验、不用防伪造。
  **唯一的例外是流式输出**：Server Action 的返回值必须整块序列化后才回传，做不到「边生成边显示」，
  所以流式走 Route Handler + SSE。目前全站只有 `/api/chat` 一个接口，取舍理由见《功能/Agent》§四。
- **构建**：dev 与 build 均走 Turbopack。

> ⚠️ **Next.js 16 相对早期版本有 breaking changes**，写代码前先查阅
> `node_modules/next/dist/docs/` 中的对应指南，不要依赖既有印象。

### 3.3 语言层：TypeScript

- 配置为 `strict: true`，`moduleResolution: "bundler"`，`noEmit`（类型检查与构建分离）。
- 路径别名 `@/*` → `./src/*`，测试配置中同步复用该别名。
- 原则：**不为通过编译而写 `any`**；外部返回的数据在边界处收窄类型。

### 3.4 视图层

**React 19** —— 服务端组件与现代 Hooks 并存。分工原则：

- 数据获取、静态渲染 → 服务端组件
- 用户输入、局部状态、浏览器 API → 客户端组件
- 客户端组件尽量下沉到叶子节点，避免整页变成客户端组件

**Tailwind CSS 4** —— 主题通过 CSS 变量集中定义，用 `@theme inline` 把变量映射成
Tailwind 工具类。色值用 `oklch()` 表达（感知均匀，便于做明暗与色调推导）。
圆角、间距等设计令牌同样走 CSS 变量派生，避免魔法数值散落在组件里。

**shadcn/ui** —— 不是依赖包，而是**生成器**：组件的源码直接写进项目目录，完全可控、
可改。项目配置固定为：

| 配置项 | 取值 |
|---|---|
| style | `base-nova` |
| baseColor | `neutral` |
| cssVariables | `true` |
| iconLibrary | `lucide` |
| 组件目录 | `@/components/ui` |
| 工具函数 | `@/lib/utils` |

**组件底座 Base UI** —— `base-nova` 风格基于 Base UI 提供无障碍语义与交互行为，
因此组件层不自行重造键盘导航、焦点管理等逻辑。

**样式工具两件套** —— `clsx` 负责条件拼接，`tailwind-merge` 负责消解冲突类名，
两者组合成项目统一的 `cn()` 工具函数（`src/lib/utils.ts`，测试见 `utils.test.ts`）。
`class-variance-authority`（声明式变体）是**已声明候选、尚未安装**——等组件真正需要
size / variant 时再登记启用（见 §二「当前实际安装的」）。

**字体** —— 通过 `next/font` 加载，中西文分工：

- 中文正文：自托管可变字体（`next/font/local`），保证中文渲染一致，且不依赖外部字体服务
- 西文与等宽：Google Fonts（`next/font/google`），构建期下载并自托管
- 字体以 CSS 变量形式注入根节点，由 Tailwind 的 `font-sans` / `font-mono` 引用

**响应式断点** —— 项目统一采用三档布局策略，以 Tailwind 的 `lg`（1024px）为分界基准：

| 档位 | 断点 | 典型布局 |
|---|---|---|
| 移动 | `< 1024px` | 单列，导航折叠 |
| 窄屏桌面 | `1024 – 1279px` | 两列，导航收窄 |
| 宽屏桌面 | `≥ 1280px` | 完整多列布局 |

### 3.5 数据层：SQLite

**选型理由** —— 无需独立数据库服务、单文件随项目走、进程内零网络开销，适合以本地
读写为主的应用。

使用 **better-sqlite3** 驱动，特点是**同步 API**：查询语句直接返回结果，不需要
`await`，事务用普通函数即可表达——代价是不能用在 Edge 运行时。

**连接配置**

- `journal_mode = WAL`：读写并发不互斥
- `foreign_keys = ON`：外键约束生效（SQLite 默认关闭）

**Schema 与迁移**

- Schema 定义抽成一个 `initSchema(connection)` 函数，生产库（文件）与测试库（`:memory:`）
  **共用同一份定义**，杜绝两边结构漂移。
- 建表语句全部 `CREATE TABLE IF NOT EXISTS`，可重复执行。
- 迁移方式为**幂等列检测**：用 `PRAGMA table_info` 检查列是否存在，缺则 `ALTER TABLE ADD COLUMN`。
  数据量不大时，这比引入迁移框架更轻。
- 需要多对多关系时用**独立关联表**，不用 JSON 数组列——关联表能走索引，JSON 列只能全表扫。
- 时间戳统一存 **INTEGER 毫秒**；**排序必须补 `rowid` 作为第二排序键**，因为毫秒级时间戳
  在同一毫秒内会撞车，而 SQL 不保证等值行的稳定顺序。

**全文检索** —— SQLite 内置 FTS5 虚拟表可提供关键词检索，配合触发器与主表同步。
需要注意分词器选择：不同分词器对中文与英文的切分行为差异很大。

**原生模块的工程注意**

- better-sqlite3 是含 C++ 内核的原生模块，**必须**加入 `next.config.ts` 的
  `serverExternalPackages`，否则打包器会在运行时把它转坏。
- 原生模块需要匹配的 **NAPI 版本**，Node 版本必须满足其要求。
- 编译依赖 node-gyp / make，**项目路径不能含空格**，否则编译命令会在空格处被截断。
- **预编译二进制有 glibc 下限，必须低于目标系统的 glibc。这是本项目把 `better-sqlite3`
  锁在 12.x、不用最新版的原因**：13.x 把预编译二进制塞进了包内（`prebuilds/`），但那份
  linux-x64 要求 **GLIBC_2.34**，而生产服务器（Alibaba Cloud Linux 3）只有 **2.32**——
  装上能启动、本地全绿，一碰数据库就在线上 `ERR_DLOPEN_FAILED`。12.x 改用
  `prebuild-install` 从 GitHub Releases 取，实测那份二进制只要求 **GLIBC_2.29**，可用。
  查法：`strings <那个 .node 文件> | grep -oE '^GLIBC_2\.[0-9]+$' | sort -V | tail -1`。
  CI 里有一道自检步骤专门守这条（见 `.github/workflows/deploy.yml`）。
- 12.x **有 `install` 脚本**，而 pnpm 10 默认拦截依赖的构建脚本：必须把 `better-sqlite3`
  写进 `package.json` 的 `pnpm.onlyBuiltDependencies`，否则预编译二进制根本不会被下载，
  运行时报「找不到 bindings」。

### 3.6 质量层

**Vitest** —— 配置要点：

- `environment: "node"`
- 用例文件与源码**同目录就近放置**，命名 `*.test.ts`，`include: ["src/**/*.test.{ts,tsx}"]`
- 复用 TypeScript 的 `@/` 路径别名
- 数据库相关测试使用**纯内存 SQLite**，不触碰磁盘上的真实数据文件

**ESLint 9** —— flat config 形式，继承 `eslint-config-next`。

**TypeScript** —— `tsc --noEmit` 作为类型门禁。

### 3.7 构建与打包

| 项 | 说明 |
|---|---|
| 打包器 | Turbopack（dev 与 build） |
| CSS 处理 | PostCSS + `@tailwindcss/postcss` |
| 原生模块 | 经 `serverExternalPackages` 白名单排除打包 |
| 启动钩子 | **预留、当前未建**：将来需要进程级初始化（如启动时校验数据库/环境）时用 `src/instrumentation.ts` 的 `register()`；建时须按 `NEXT_RUNTIME` 判断运行时，Edge 下不能加载 Node 专属模块 |

## 四、工程约定

### 4.1 目录结构

```
nexus-os/
├── src/
│   ├── app/                 # 路由层：页面与 HTTP 接口（只做接线，不写业务逻辑）
│   │   ├── **/page.tsx      # 页面
│   │   └── api/**/route.ts  # 接口
│   ├── components/
│   │   ├── ui/              # shadcn/ui 基础组件
│   │   └── ...              # 业务组件，按领域分目录，一组件一文件
│   └── lib/                 # 通用逻辑、数据访问、第三方适配
├── docs/                    # 项目文档
├── public/                  # 静态资源
└── data/                    # 本地数据文件（不入 Git）
```

**硬指标：单个文件超过约 300 行就拆。** 页面只负责组合与接线，逻辑下沉到 `lib/`。

> 每个目录、每个文件的职责与「新文件该放哪」的判断流程，详见《项目目录结构说明》。

### 4.2 命名与别名

- 组件文件：`kebab-case.tsx`（与 shadcn/ui 生成规则保持一致）
- 路径别名：`@/*` → `./src/*`
- 命名导出优先，减少默认导出

### 4.3 环境变量

- 密钥类配置**只放 `.env.local`**，该文件已在 `.gitignore` 中；代码通过 `process.env` 读取
- 仓库内维护 `.env.example`，只登记**键名与获取方式**，不写真实值
- 服务端与客户端变量严格区分：只有显式暴露的变量才能进入浏览器端

**变量登记表**（新增变量先登记到这张表，再写进代码）：

| 变量 | 用途 | 本地 | 线上 |
|---|---|---|---|
| `DATABASE_PATH` | SQLite 数据库文件的绝对路径 | 不设，代码回退到 `data/nexus-os.db` | `/opt/nexus-os/shared/data/nexus-os.db`（`shared/` 与代码版本解耦，发布不清库） |
| `SESSION_COOKIE_SECURE` | 会话 cookie 是否只在 HTTPS 下传输 | 不设（HTTP，设了会登录不上） | 已设 `true`（HTTPS 已上线，2026-10-29 实测核对） |
| `DEEPSEEK_API_KEY` | DeepSeek 开放平台的 API Key，Agent 调大模型的唯一凭证 | `.env.local`；到 platform.deepseek.com 申请 | `shared/.env.production` 同样要设 |

### 4.4 提交前门禁

以下五项全绿才算完成一次改动：

```
pnpm exec next typegen  # 生成路由 / 布局类型（typecheck 的前置，干净检出必跑）
pnpm typecheck          # 类型（= tsc --noEmit，别名写在 package.json）
pnpm lint               # 代码规范
pnpm test               # 单元测试
pnpm build              # 生产构建（构建能过，才算「真的能跑」）
```

> `typegen` 必须先跑：路由与布局的类型（如 `LayoutProps`）是**构建期生成物**，不在仓库里，干净检出直接 `typecheck` 会报 `Cannot find name 'LayoutProps'`。

5. **写 Next.js 16 代码前先读 `node_modules/next/dist/docs/`**。
6. **密钥永不硬编码、永不进 Git**。
7. **响应式以 `lg`（1024px）为分界**。

## 六、版本锁定与升级

- 所有依赖版本由 `pnpm-lock.yaml` 锁定，**随代码一起提交**。
- 运行时与包管理器版本由 `.nvmrc` + `engines` + `packageManager` 三处共同固化。
- 升级策略：一次只升一个主依赖，升级后先跑全部门禁（类型 / Lint / 测试），
  再更新本文对应行。

## 更新记录

- 2026-10-30：新增 **`@jsquash/jpeg@1.6.0`**（Apache-2.0，mozjpeg 的 WASM 封装），替换浏览器 canvas 自带的 JPEG 编码器——同画质通常更小（渐进式、优化 Huffman 表、trellis），低质量档差距更明显。用法要点：① 只 import `@jsquash/jpeg/encode.js`（不要引包入口，避免连带拉进解码器与两份 wasm）；② 跑在 `image-worker.ts` 里，它的 wasm（约 246 KB）由打包器发成静态资源；③ 「压不小就自动降一档质量重试」的逻辑在 Worker 里，主线程拿到 `effectiveQuality` 后同步滑杆并在结果区标注。
- 2026-10-30：新增 **`imagequant@0.1.2`**（**GPL-3.0**，libimagequant 的 wasm 绑定），用于 PNG 调色板量化（TinyPNG/pngquant 同源）。用法要点：① 包入口 `import * as wasm from "./imagequant_bg.wasm"` 是 wasm-bindgen 的 bundler 目标，**在 Worker 里打包器解析不了、运行时一直挂着**（实测点了「开始压缩」永远停在压缩中且无报错）；② 因此只 import 它的 JS 胶水 `imagequant/imagequant_bg.js`，wasm 从 **`public/codecs/imagequant_bg.wasm`** 手动 `fetch + WebAssembly.instantiate`（wasm 只从 JS 导入 2 个 wbindgen 函数），再 `__wbg_set_wasm(exports)`；③ 升级该包时同步替换 `public/codecs/` 里的 wasm；④ 它跑在 `image-worker.ts` 里，不占主线程。
- 2026-10-30：新增 **`@jsquash/oxipng@2.3.0`**（Apache-2.0），按《功能/图片压缩》联调需求登记——PNG 是浏览器 canvas 压不动的格式（无损重编码反而更大），改用 oxipng 的 WASM 对**原始 PNG 字节**做无损优化。用法要点：① 只在浏览器里动态 import（单独 chunk，不进首屏）；② **不要 import 包的主入口 `@jsquash/oxipng/optimise`**——它会连带拉进并行版 codec 与 `wasm-feature-detect`，实测 Turbopack 构建直接卡死；改用单线程 glue 子路径 `@jsquash/oxipng/codec/pkg/squoosh_oxipng.js`；**必须跑在 Web Worker 里**（`image-worker.ts`），它是同步 WASM，放主线程会把页面冻住；③ wasm 由 glue 里的 `new URL('…wasm', import.meta.url)` 引用，Turbopack 会把它作为静态资源发到 `/_next/static/media/…wasm`（已验证 200），不需要复制到 `public/`；④ 升级该包时重新跑一遍构建与浏览器验证即可。
