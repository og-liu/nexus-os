# Agent

| 项 | 内容 |
|---|---|
| 状态 | 🔨 实现中（第一版对话已跑通，工具与规划未做） |
| 开始日期 | 2026-10-29 |
| 最近更新 | 2026-10-29 |
| 一句话 | 能理解需求、调用工具、执行多步任务的个人助手——用户不用点按钮，说一句话就把事办了 |

> 这是本项目最重的一块，也是唯一一块「输出不确定」的功能：同样一句话，模型每次回答都可能不同。
> 因此它不能按前四个工具那套「同样输入必得同样输出」的思路来做，需要另立规矩。
> 本文按阶段推进：每期开工前先改本文，再改代码。

## 一、要什么

**一句话需求**：用户在 `/agent` 里用大白话说需求，它能自己拆解、调工具、把结果说出来。

### 第一版（2026-10-29 已交付）：先让它会说话

| 做 | 说明 |
|---|---|
| 单会话对话 | 一个页面、一串消息，关掉就散 |
| 流式输出 | 字一个个冒出来，不是等全部生成完才整段出现 |
| 思考过程 | 模型推理时的内心独白，折叠展示，点开才看 |
| token 用量 | 每条回答底部显示本轮消耗，知道花了多少钱 |
| 多轮上下文 | 同一串对话里记得上文 |

### 主动放弃（第一版不做），以及为什么

| 放弃项 | 为什么 |
|---|---|
| 会话落库 / 多会话列表 | 存储方案（表结构、状态机）还没定；先接存储会让这一版同时背两个没定好的问题 |
| 工具调用（便签 / 待办 / 日历） | 工具层怎么接 Server Action 数据入口还没定规矩，硬接会返工 |
| 任务规划（拆步执行） | 建立在工具调用之上，顺序在后面 |
| 人工补问（HITL） | 同上 |
| 停止与断点恢复 | 属于状态一致性，需要整套状态机设计 |
| 多模型选择器 | 先把一条路走通；注册表已经预留，接界面是纯加法 |
| 图片 / 语音输入 | 需要上传、存储、视觉模型三条链路，不属于第一版 |
| Markdown 渲染 | 纯文本已够看，样式留到体验层统一做 |

> 放弃项不是「忘了做」，是**按依赖顺序往后排**。每一项都写在下面的推进顺序里。

## 二、界面

**路由**：`/agent`（受保护页面，未登录跳 `/login`）

**三段式，占满页头以下的全部高度**：

| 区域 | 内容 |
|---|---|
| 标题条 | 左「新对话」、右「清空」按钮（无消息时禁用） |
| 消息流 | 空态是黑色图标 + 引导文案；有消息时是气泡列表，自己滚 |
| 输入区 | 多行输入框 + 发送/停止按钮；Enter 发送、Shift+Enter 换行 |

**消息形态**：

- 用户消息：右对齐、黑底白字
- 助手消息：左对齐、白底、左侧黑色头像块；内含（从上到下）思考过程折叠块 → 正文 → 错误红字（若有）→ token 用量小字

**当前没有**：左侧会话列表、模型选择器、图片上传、语音输入、计划进度面板。

样式细节以《界面设计规范》§7.23 为准。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 流式接口用什么承载 | **Route Handler + `ReadableStream`** | Server Action 的返回值必须先被序列化成一整块才能回传，天生做不到「边生成边显示」；Next 16 文档把这类场景明确指向 Route Handler | Server Action（做不到真流式）· 轮询（延迟高、请求风暴） |
| 传输格式 | **SSE（`text/event-stream`）** | 单向推送、就是普通 HTTP、Nginx 与浏览器天然认得，不需要额外握手 | WebSocket（双向、要握手、网关要支持，本项目用不到双向） |
| 前端怎么读 | **`fetch` + `response.body.getReader()` 手工解析** | 必须发 POST 带整段历史；原生 `EventSource` 只能发 GET、不能带请求体 | `EventSource`（发不了请求体） |
| 第一版做不做存储 | **不做** | 一次只背一个问题。「让这条线跑通」和「设计好状态机」是两件事，同时做会两头都不清楚 | 一起做（会变成又一个自己看不懂的大块） |
| 界面从哪里来 | **从旧项目搬右栏，不搬左栏** | 右栏是对话本体，搬过来立刻能看出「像不像」；左栏的全部意义是多会话切换，没存储时搬过来是个永远空的抽屉 | 整页搬（引入大量假数据与无用状态）· 重画（丢掉已验证过的视觉） |
| 系统提示词怎么写 | **写死三条限制，其中一条是「你没有工具能力，看不到个人数据」** | 模型会顺着「帮我看看我的待办」编出一份很像真的清单。幻觉比报错危险：报错用户会重试，幻觉用户会当真 | 不写限制（默认会编）· 含糊带过（模型会自行脑补） |
| `model` 参数怎么处理 | **白名单校验，非法值回落默认模型** | `model` 是前端传来的字符串，直接拼进请求体等于让浏览器决定用哪个模型 | 直接透传（可被用来探测模型或跑更贵的档位） |
| 思考（reasoning）默认开还是关 | **默认开，不做开关** | DeepSeek 接口默认就返回 `reasoning_content`；第一版少一个变量，且思考过程本身就是重要的教学材料 | 默认关（要多写一套参数、还要验证关得掉） |
| 中文解码 | **`TextDecoder` 带 `{ stream: true }`** | 一个汉字占 3 个字节，可能被切在两块之间；不带这个参数会解出乱码 | 每块单独 `decode`（随机出现「�」） |

## 五、文件落点

| 文件 | 职责 |
|---|---|
| `src/lib/agent/providers.ts` | 供应商适配层：供应商配置表、`streamChat()` 流式调用、SSE 解析、错误翻译 |
| `src/lib/agent/models.ts` | 模型注册表：可用模型、白名单校验、默认模型 |
| `src/app/api/chat/route.ts` | 对话接口（本项目**第一个 API 路由**）：鉴权、入参校验、拼系统提示词、把流式结果转成 SSE 推回 |
| `src/components/agent/agent-chat.tsx` | 客户端对话视图：消息状态、发请求、按 SSE 规矩读流、渲染 |
| `src/app/(app)/agent/page.tsx` | 页面接线：登录检查 + 页头 + 对话区容器 |

**分层原则不变**：页面只接线，逻辑在 `lib/`，界面在 `components/`。`route.ts` 只做「收请求 → 校验 → 调 `lib` → 转成 SSE」，不写业务逻辑。

| # | 操作 | 可观察的结果 |
|---|---|---|
| 1 | 未登录直接访问 `/agent` | 跳到 `/login` |
| 2 | 未登录直接 `POST /api/chat` | 返回 401 JSON，不消耗 token |
| 3 | 在输入框输入 `你好` 并回车 | 用户气泡立刻出现（黑底右侧），助手气泡开始逐字增长 |
| 4 | 观察首字延迟 | 1–2 秒内出现第一批字，不是等十几秒后整段出现 |
| 5 | 回答结束后 | 显示「本轮 N tokens · 输入 X / 输出 Y」 |
| 6 | 点击「思考过程」 | 展开灰色折叠块，内容与回答相关；再点收起 |
| 7 | 问 `我刚才问了什么` | 能准确复述上一轮的问题（上下文生效） |
| 8 | 问 `帮我看看我今天的待办` | **明确说做不到，不编造任何待办内容**（负面用例） |
| 9 | 发送过程中点停止按钮 | 立即停止接收，已生成的内容保留在气泡里 |
| 10 | 刷新页面 | 对话清空（第一版不落库，这是设计而非缺陷） |
| 11 | 清空 `.env.local` 里的 Key 后重启并发消息 | 气泡内红字提示「未配置 DEEPSEEK_API_KEY」，不是白屏或假死 |
| 12 | 用错误 Key 发消息 | 红字提示「鉴权失败：API Key 无效或已过期」 |
| 13 | 手机宽度（390px） | 页头变汉堡 + 短标题，气泡自适应，无横向滚动 |
| 14 | 中文输入法打「你好」选字时按回车 | **不发送**（组合态拦截生效） |
| 15 | 发送 `{"messages": []}` 直接打接口 | 返回 400「messages 必须是非空数组」 |

## 七、已知的坑

### 1. SSE 分帧：半行必须留着

**机制**：网络送来的数据块大小是随机的，`data: {...}` 这一行很可能被切成两半，前半块到达时 JSON 是不完整的。
**对策**：`buffer` 累积后按 `\n\n` 切，**最后一段永远不出解析，留到下一轮**。不留这一手，长 JSON 会随机丢内容，而且不报错。

### 2. 中文解码必须 `{ stream: true }`

**机制**：一个汉字 3 个字节，可能跨两个数据块。
**对策**：`decoder.decode(value, { stream: true })`。少了这个参数，界面上会时不时冒出「�」。

### 3. Nginx 默认会缓冲响应

**机制**：Nginx 的 `proxy_buffering` 会攒够一块再转发，流式在本地好看，一上线就变成「等半天然后一次性出现」。
**对策**：响应头带 `X-Accel-Buffering: no`。~~靠本地开发是发现不了这个问题的。~~ 这条在**上线后第一次实测**时才能真正确认，本地 dev server 没有 Nginx。

### 4. 中文输入法组合态按回车会误发送

**机制**：输入法选字时按回车，浏览器同样抛 `keydown`，不拦就会把半截拼音发出去。
**对策**：监听 `compositionstart` / `compositionend`，组合期间按回车不发送。

### 5. 思考比正文贵

**机制**：实测一轮 207 tokens 里，`reasoning_tokens` 往往占一半以上。多步 Agent 每步都思考，token 会成倍放大。
**对策**：目前默认开思考。到第 5 期（任务规划）时，「哪一步该开、哪一步不该」必须成为显式设计，不能沿用默认。

### 6. 前端失败原因不能吞掉

**机制**：非 2xx 响应时若只显示「请求失败」，用户只能靠猜（旧项目踩过：409 被误报成「API Key 没配」，越查越偏）。
**对策**：`route.ts` 一律返回 `{ error: "人话" }`，前端读出这句原文显示。

## 八、依赖变更

**不涉及。** 第一版没有新增任何依赖：模型调用直接用运行时自带的 `fetch`，流式解析用自带的 `TextDecoder` / `ReadableStream`。

> 刻意不引入 Vercel AI SDK 等封装：这一层要看懂的就是协议本身，套一层 SDK 会把 `messages` / `tool_calls` / SSE 分帧全藏起来，学习目的就落空了。
