# 用户密钥

| 状态 | 开始日期 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-11-02 | 2026-11-02 |

> 一句话：**每个用户填自己的 API Key**，站点不再替任何人付钱。
> 这是把「单用户自用」改造成「多用户可用」的那一刀，也是全站第一次**在数据库里存密文**。

---

## 一、要什么

**做：**

- 新增设置页 `/settings`（把现在的占位页换成真页面），分「模型」与「工具」两组，每个 Key 一行
- 每个 Key 一行三态：**未配置**（输入框可填）/ **已配置**（显示掩码 + 「更新」「清除」）
- 保存走 Server Action，密文入库；**页面上任何时候都不回传明文**
- 覆盖两个 Key：
  - `deepseek` —— Agent 调大模型
  - `tikhub` —— 抖音下载解析分享链接
- 两处消费方改造：**Agent 与抖音下载都从「当前登录用户的密文」取 Key**，取不到就返回一句指向设置页的人话
- 用自己的 Key 还是别人的，由 `user.id` 决定——同一个站点上两个人互相看不到对方的额度消耗

**主动放弃（本版不做，不是遗漏）：**

| 放弃项 | 原因 |
|---|---|
| 站点默认 Key（`.env` 兜底） | 那等于「管理员替所有人付钱」，与这次改造的目的相反。要专业就不留这个后门 |
| Key 使用量统计 / 额度告警 | 要知道每次调用花了多少，得先有调用记录表；那是另一个功能 |
| 多平台 Key（OpenAI / 通义 / 智谱…） | 现在只有 DeepSeek 一个模型供应商。Key 表按 `provider` 字符串存，加一家只是加一行注册，不用改表 |
| 找回 / 导出一份 Key 明文 | 密文只能解密给自己用，界面上永远只显示掩码。忘了就重填一个 |
| 两级密钥（每个用户一个数据密钥 + 主密钥加密） | 企业级做法，解决的是「主密钥泄露后全库沦陷」。个人站上收益极小，复杂度翻倍 |

## 二、界面

### 2.1 设置页 `/settings`

沿用外壳的 `PageHeader`（现在这个页面已经用了），内容是**一组设置卡**，本版只有一张「API 密钥」。

```
PageHeader（标题「设置」，描述不变）
内容区（px-4 py-4 md:px-6 md:py-6 space-y-4）
└─ 卡片「API 密钥」
    ├─ 说明一句：这些 Key 只属于你，加密后存在你自己的账号下；别人看不到、也用不到
    ├─ 页内 tab：[大模型] [工具 API]（下划线式，状态放 ?tab=）
    ├─ 该组说明一句（浅灰，告诉人这一组是给什么用的）
    └─ 该组下的 Key 行（大模型 → DeepSeek；工具 API → TikHub）
```

**为什么用 tab 而不是纵向堆叠**：模型以后会有多家（DeepSeek / OpenAI / 通义…），工具会有多个，
纵向堆下去这张卡会越来越长，而且一屏里同时摆着「跟你无关的那几组」。
分组用 tab 后，加一家只往注册表里加一行，界面自动多一项。

每个 Key 一行（`SecretRow`）：

```
┌───────────────────────────────────────────────┐
│ DeepSeek                          [已配置]     │
│ Agent 对话用的大模型                            │
│ 去向：<可点的新窗口链接> → 左侧「API keys」→ 新建 → 复制       │
│                                               │
│ 未配置：「sk-...」输入框 + [保存]                │
│ 已配置：sk-••••••••••••（掩码）+ [更新] [清除]    │
└───────────────────────────────────────────────┘
```

### 2.2 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列；每行内输入框与按钮**上下叠放**，按钮通栏 | 输入框字号 16px（防 iOS 聚焦放大） |
| 平板 md ~ lg（768–1023） | 单列；输入框 + 按钮**同一行**，按钮在右 | 一行装得下就不换行了 |
| 窄屏 PC lg ~ xl（1024–1279） | 单列，内容区铺满 | — |
| 宽屏 ≥ xl（1280） | 单列，卡片限宽 `max-w-[760px]` | 一行只有一条输入框，拉满一整屏会让视线横穿 |

- 设置页本来就是**一列清单**，不并排：两个 Key 之间没有对照关系，并排反而要左右看。

### 2.3 状态与边界

| 状态 | 界面 |
|---|---|
| 未配置 | 输入框可填，「保存」可点；状态标签是灰点「未配置」 |
| 保存中 | 按钮变「保存中…」并禁用 |
| 保存成功 | 该行切成「已配置 + 掩码」；Toast 一句「DeepSeek 的 Key 已保存」 |
| 保存失败（加密密钥没配） | 该行下方红字：「服务端还没配置 ENCRYPTION_KEY，现在存不了」 |
| 输入为空点保存 | 按钮置灰，不发请求 |
| 清除 | 二次确认后该行回到「未配置」；Toast「已清除」 |
| 抖音下载里没配 Key | 结果区：「你还没配置 TikHub 的 Key」+ 「去设置里填」链接 |
| Agent 里没配 Key | 对话区红字：「你还没配置 DeepSeek 的 Key，去设置里填一下」 |

## 三、数据模型

```sql
CREATE TABLE IF NOT EXISTS user_secrets (
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider   TEXT    NOT NULL,             -- 'deepseek' / 'tikhub'，与 lib/secrets/providers.ts 的注册表对应
  ciphertext TEXT    NOT NULL,             -- AES-256-GCM，格式 v1.<iv>.<tag>.<data>（各段 base64）
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (user_id, provider)
) WITHOUT ROWID;
```

**设计要点**

- **主键是 `(user_id, provider)`**：一个人一家只能有一条，天然去重，也让「覆盖保存」变成 `ON CONFLICT DO UPDATE`。
- **只存密文**：`ciphertext` 是完整的自描述串（版本 + iv + 认证标签 + 数据），换算法时靠开头的 `v1` 区分，不用改表。
- **GCM 的认证标签必须存**：它同时承担「防篡改」——有人手改数据库里的密文，解密会直接失败，而不是解出垃圾。
- **不存 `last4` / 掩码前缀**：掩码在运行时按需生成（`sk-••••`），存一份等于多一处可能过期的副本；而「显示前几位」本身就有泄露面，不做。
- **`created_at` 与 `updated_at` 都要**：这不是「谁先谁后都行」的冗余——界面上「已配置」的判断只看有没有行，但出问题时要知道这条是什么时候写的、什么时候换的。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 要不要保留 `.env` 里的全局 Key | **不保留** | 保底就等于「管理员替所有人付钱」，与「每个用户自己的 Key」直接冲突。要么不做，要么做干净 | 用户 Key 优先、全局兜底（新人能用，但花的是站长的钱，且这类兜底永远没人去关）；只对第一个用户兜底（同一件事换个说法） |
| 加密算法 | **AES-256-GCM** | Node 内置 `crypto` 就有；GCM 自带认证，篡改即解密失败。只需要一个 32 字节密钥，没有要调的参数 | AES-256-CBC + 手写 HMAC（要做的事一样，多一个易错点）；明文存库（库一泄露，所有人的 Key 一起送人） |
| 主密钥放哪 | **环境变量 `ENCRYPTION_KEY`** | 这是唯一必须留在配置里的东西，且它只保护「数据库里的密文」——库和配置分开保管，单拿一份没用 | 存在同一张表里（等于没加密）；从用户密码派生（改密码就得重加密全部 Key，还要处理忘记密码） |
| Key 怎么用 | **消费方拿 `user.id` 现读现解** | 不缓存、不放进 session：一次解密是微秒级，而放进 cookie/session 等于把明文又散出去一份 | 登录时解密塞进 session（明文多存在于一处，退出登录还得清） |
| 设置页形态 | 服务端渲染 + Server Action | 与便签 / 保险库同一套写法，不需要新接口；保存后 `revalidatePath` 直接刷新 | 再开一个 `/api/settings/*` 路由（本页面没有流式或大文件需求，多一条接口只是多一处鉴权） |
| 没配 Key 能不能吃缓存 | **不能。门槛排在查缓存之前** | 「有没有配 Key」是权限，「这次要不要花钱」是成本——两件事。先查缓存的话，同一个视频别人解析过，没配 Key 的人就能白嫖到结果（**实测踩过**：user 24 没配任何 Key，却成功解析并下载了 user 17 解析过的视频） | 缓存命中就放行（省钱，但等于没有门槛） |
| 保存时验活 | **验**（`verifySecret`，问上游「这 Key 能用吗」） | 只校验「有没有填」是不够的：乱码同样能通过，而抖音下载的缓存全站共享，于是「乱码 Key + 别人的缓存」照样能下成功，用户以为校验形同虚设。**保存的那一刻**是唯一合理的验证时机——有反馈、不打扰、只花一次免费调用 | 不验（省事，但错 Key 要等很久才暴露）；每次使用都验（多花钱、多一次延迟，且缓存路径本来不该碰上游） |
| 验活失败怎么办 | 分**三态**：`ok` 存；`invalid`（上游 401/403）**拒**；`unknown`（网络/超时/5xx）**照存** | `unknown` 是「我们没法判断」，不是「这 Key 是坏的」——不能因为 TikHub 挂了或用户网络抖一下，就让人存不了 Key | 两态（错就拒），会把上游的故障算到用户头上 |
| 没配 Key 时的行为 | **明确报错并指向设置页** | 「不能用」要让人知道为什么、去哪解决。静默降级或悄悄用别人的额度都是更坏的体验 | 回退到环境变量（见第一条）；干脆不报错（用户会以为工具坏了） |

## 七、已知的坑

1. **`ENCRYPTION_KEY` 必须长度正确**：AES-256 要 32 字节。给 hex（64 字符）或 base64，代码里统一转 Buffer 并校验长度；长度不对要报一句人话，不要让它变成运行时随机失败。
2. **改主密钥 = 所有密文作废**。这是有意为之（安全性换可维护性）：文档里写清「换 key 就让大家重填」，不要试图做自动迁移。
3. **`process.env` 的空串不是「没设置」**：`.env` 里 `ENCRYPTION_KEY=` 解析出来是 `""`，`??` 拦不住。一律 `?.trim() || null`。
4. **Server Action 里不能信客户端传来的 `user_id`**：只从 `getCurrentUser()` 取，客户端传什么都不看。
5. **保存后要 `revalidatePath("/settings")`**，否则页面还是「未配置」——而数据库里已经有了，看起来像没保存成功。
6. **不要在客户端组件里 import `lib/secrets/crypto`**：它读 `process.env` 并做解密，进了浏览器包就是灾难。设置页只传「配没配」这个布尔值。
7. **抖音下载取不到 Key 时要在调用上游之前返回**，不能先发请求再判断——那既费钱又会让「未配置」变成 502。
8. **两处消费方的函数签名变了**（`resolveVideo` / `streamChat` 多了 `apiKey` 参数），别只改一处——漏掉的那处会把 `undefined` 当 Key 发出去，报的是上游 401 而不是「未配置」。
9. **「有没有配 Key」的校验必须排在缓存查询之前。** 抖音下载的解析缓存是全站共享的（不分用户），顺序写反了，没配 Key 的人只要点一个别人解析过的视频就能白嫖——**实测踩过**：user 24 一个 Key 都没配，却成功解析并下载了 user 17 解析过的视频。校验用 `hasSecret()` 只查行、不解密，几乎零成本。
10. **只验「有没有填」还不够，必须验「对不对」。** 同一个缓存漏洞还有第二副面孔：填一串乱码进去，`hasSecret` 照样通过，命中缓存就放行，看起来校验形同虚设（**实测踩过**：用户填了一个 6 字符的乱码，一样能下载）。修法是保存时问上游一次（DeepSeek `/models`、TikHub `/tikhub/user/get_user_info`，都免费），`401/403` 当场拒。**注意别把上游的 5xx/超时也算成 Key 坏了**——那会让 TikHub 挂掉时没人能保存 Key。

## 八、依赖变更

- **npm 依赖**：不新增。加密用 Node 内置 `node:crypto`。
- **环境变量**：
  - 新增 `ENCRYPTION_KEY`（32 字节的 base64 或 hex）
  - **移除** `DEEPSEEK_API_KEY` 与 `TIKHUB_API_KEY` 的运行时读取（`\.env` 里可以留着当备份，但代码不再看它们）
- **外部服务**：不新增。
