## 二、什么时候写

**动手写第一行代码之前。**

「先改文档再改代码」是本项目的规则。对主人来说，这份文档不是流程paperwork，而是**评审件**：设计写清楚 → 他读完提出异议 → 定稿 → 才开始实现。代码写完再补文档，等于把评审这一步跳过了。

## 三、命名

- **工具**的文档不进本目录：写在 `src/features/<工具>/README.md`（与 `client/` `server/` `shared/` 并排）
- **非工具**（外壳、页签栏、工具中心、登录注册、用户密钥这类页面 / 能力）一个功能一个文件，
  **文件名 = 功能名**（中文），如 `登录注册.md`
- 不加序号、不加日期、不用英文名
- 新建一份文档后，**在同一处更新第一节的功能清单**

## 四、统一格式

每份功能文档都用下面这个骨架：**节次固定、顺序固定**。用不上的节写「不涉及」而不是删掉——同类功能并排看时才对得上位置。

每节的写作要求：

**头部元信息表** —— 状态、开始日期、最近更新日期，加一句「这个功能为谁解决什么问题」。状态与功能清单保持一致。

**一、要什么** —— 一句话需求，然后是明确的两面清单：做哪些，以及**主动放弃哪些**。放弃项必须单独成表并写明原因。被放弃的能力写了原因是决策，没写就变成遗漏，下次还会被重新翻出来讨论。

**二、界面** —— 路由 → 页面 → 它必须做到什么，写具体路径不画线框图。纯后端功能写「不涉及」。

**三、数据模型** —— `CREATE TABLE` 原文，之后跟一段「设计要点」，逐个解释不那么显然的列（为什么唯一键建在归一化列上、为什么某列存的是哈希而不是原文）。不涉及存储的功能写「不涉及」。

**四、关键决策** —— 四列表：决策点 / 选择 / 理由 / **否决的备选**。最后一列是重点：一个选择只有摆在被它击败的选项旁边才讲得明白。

**五、文件落点** —— 这个功能会新增哪些文件、放在哪。代码还不存在时就能评审这一刀切得对不对。
（工具文档里这一节就是「代码结构（三层）」：client / server / shared 三张表 + 从哪开始读。）

**六、验收标准** —— 编号行，格式是「操作 → 可观察的结果」，**必须包含负面用例**（错误的密码、被篡改的 cookie、直接翻数据库）。这张表就是实现阶段的测试清单。

**七、已知的坑** —— 已经知道的坑，每条给出机制与对策。**写在代码之前**，实现时才能绕开。

**八、依赖变更** —— 本功能引入的新依赖，并重申项目规则：**先登记进《技术栈说明》，再安装**。

**更新记录** —— 每次实质修改追加一行，不覆盖历史。

## 五、和其他文档的分工

| 文档 | 只回答 |
|---|---|
| 功能文档（本目录 + 各工具 README） | 这个功能要什么、怎么设计、怎么验收；工具的「代码在哪」也写在它的 README 里 |
| 《技术栈说明》 | 用什么技术、什么版本、为什么 |
| 《数据库设计》（`docs/数据库/`） | 库里有哪些表、每张表一行是什么、改表结构有什么规矩 |
| 《项目目录结构说明》 | 文件该放在哪 |
| 《界面设计规范》 | 界面长什么样 |
| 《部署方案》 | 怎么上线 |
| 《开发日志》 | 干过什么、为什么、踩了什么 |

同一个话题只在**一处**写详细，另一处留一行交叉引用——否则两份文档迟早互相矛盾。
