# 图片压缩

| 状态 | 开始日期 | 最近更新 |
|---|---|---|
| 🚧 设计中 | 2026-10-30 | 2026-10-30 |

> 一句话：选一张图、拖两个参数、看体积掉下来，然后把压缩结果下载走——全程在浏览器里完成，图片一个字节都不上传。

---

## 一、要什么

**做：**

- **工具页** `/tools/image-compress`：单张图片压缩。拖入 / 点选 / 粘贴把图载进来，两个参数（质量、最大边长），实时看到「原体积 → 新体积」，一键下载
- **落点方式三种**：拖拽到拖入区、点「选择图片」开系统文件框、页面里 `⌘/Ctrl + V` 粘贴（截图后直接粘是最顺的路径）
- **纯浏览器端处理**：`createImageBitmap` 解码 → `canvas` 重编码 → `toBlob` 出图。**不上传、不落库、不写服务器文件**——服务器在这条链路上完全不参与
- **参数**：质量滑杆（0.5–0.95，默认 0.8）+ 最大边长（原尺寸 / 2560 / 1920 / 1280）
- **结果**：原图与压缩后的体积对比、省下百分比、输出像素尺寸、下载按钮、「看原图 / 看压缩后」切换
- **目录同步**：`tool-catalog` 里 `image-compress` 的状态从「开发中」改为「可用」
- 三档响应式各自一套版式（见 §2.4）

**主动放弃（本版不做，不是遗漏）：**

| 放弃项 | 原因 |
|---|---|
| 批量（多张一次压） | 单张的界面是「大预览 + 参数面板」，批量是「列表 + 逐行体积」——两套版式拼在一起会互相拖累；先把手动压一张做到好用 |
| 目标体积模式（压到 200KB 以内） | 要二分试压 + 多轮编码，用户得到的还是一个他看不懂的滑块位置；直接给质量与边长，他自己拖两下更快 |
| 格式转换（JPG ↔ PNG ↔ WebP 自由选） | 与目录里另一个工具「图片格式转换」职责重叠；本工具的格式规则只为「压得动」服务 |
| 服务端压缩 / 图片上传 | 见 §4 第 1 条 |
| 压缩历史 / 最近处理 | 图片本身不留存，留一份「处理记录」也只是一堆文件名；要重压就再拖一次 |
| 裁剪 / 旋转 / 水印 / 去背景 | 都是独立工具的事，塞进来会让这个页面的参数面板失去边界 |
| 保存到「文件」页 / 云同步 | 「文件」页仍是占位；压缩完直接下载，不引入存储与清理策略 |

## 二、界面

### 2.1 工具页 `/tools/image-compress`

与便签 / 待办工具页同构：**没有 PageHeader**，工具名与状态在内容区的信息条里（`ToolHeader`，状态点「可用」）。手机上顶部是 `ToolMobileBar`（汉堡 + 「选择图片」，图标 `ImageUp`）。

```
移动端导航行（< lg）：汉堡 + 选择图片
内容区（px-4 py-4 md:px-6 md:py-6 space-y-4）
├─ 工具信息条（ToolHeader，状态「可用」）
└─ 工作区
   ├─ 预览区（左 / 上）
   │   ├─ 空态：拖入区（虚线框 + 图标 + 三行提示）
   │   └─ 已载入：图片预览 + 顶部状态条（文件名 · 尺寸 · 体积）+ 右上「换一张」
   └─ 参数面板（右 / 下）
       ├─ 分组标题「压缩参数」（§7.2）
       ├─ 质量滑杆
       ├─ 最大边长 chips
       ├─ 分组标题「结果」
       ├─ 体积对比（原 → 新 · 省了多少）
       └─ 下载按钮（CTA，通栏黑底）
```

**空态（还没载入图片）**

```tsx
<div className="flex min-h-[220px] flex-col items-center justify-center gap-3 rounded-[2px] border border-dashed border-[#D9D9D9] bg-white p-8 text-center md:min-h-[300px] xl:min-h-[360px]">
  <ImageUp className="h-7 w-7 text-[#C4C4C4]" />
  <p className="text-sm font-medium text-[#000000]">把图片拖到这里</p>
  <p className="text-xs text-[#8A8A8A]">或点击选择文件、按 ⌘/Ctrl + V 粘贴</p>
  <p className="text-[11px] text-[#A0A8B4]">支持 JPG / PNG / WebP，单张不超过 20 MB；图片不会上传到服务器</p>
</div>
```

整块拖入区**本身是按钮**（`role="button"` / 点击开文件框 / `Tab` 可达 / `Enter` 触发），不用再在里面塞一个「选择文件」按钮——同一件事两个入口，用户会犹豫。

拖拽悬停（`dragover` 且确实带文件）：边框 `border-[#000000]`、底色 `bg-[#F5F5F5]`；`dragleave` / `drop` 复原。**必须给 `dragover` 加 `preventDefault()`**，否则浏览器默认行为是「打开这张图片」，整页跳走。

**已载入（预览区）**

- 图片 `max-h-full max-w-full object-contain` 居中，底色 `bg-[#F5F5F5]`（透明 PNG 才看得出透明）。
- 顶部状态条一行：文件名（`truncate`）+ `text-[11px] text-[#999999]` 的「4000 × 3000 · 3.0 MB」；右侧「换一张」文字按钮（`text-xs text-[#8A8A8A] hover:text-[#000000]`）。
- 右上角「看原图 / 看压缩后」切换按钮：`h-7 rounded-[2px] bg-white px-2.5 text-[11px] text-[#666666]`，带 `aria-pressed`。**用点击切换，不用「按住看原图」**——手机长按图片会弹出系统的「存储图片」菜单（见 §7）。
- 换图 / 卸载时把上一张的 object URL `revokeObjectURL` 掉。

**参数面板**

- 白卡 `rounded-[2px] bg-white p-5`，分组标题用 §7.2（黑竖条）。
- **质量**：`input type="range"`，`min=0.5 max=0.95 step=0.05`，`accent-[#000000]`；右侧当前值 `text-[13px] font-medium tabular-nums`（显示成 `80%`）。下方一行 `text-[11px] text-[#8A8A8A]`：「越低体积越小，细节越容易糊」。
- **最大边长**：四个 chip（§7.9 桌面筛选 chip 形态，`rounded-[2px] px-3 py-1.5 text-xs font-medium`，激活 `bg-[#000000] text-white`，未激活 `text-[#8A8A8A] hover:text-[#000000]`）。选中值存的是「上限像素」，不是缩放比例——**只缩不放**：原图比上限小时保持原尺寸，绝不放大。
- **PNG 无透明时**质量滑杆置灰（`disabled`）并换一行说明：「PNG 是无损格式，质量参数无效——想更小请调小边长」。原因见 §7。
- 参数改动**立刻重压**（防抖 150 ms），不设「开始压缩」按钮：这是个参数型工具，不是提交型表单，多一个按钮只是多一次点击。

**结果区**

- 体积对比：`原图 3.0 MB → 620 KB`，右侧大字 `-79%`（省下时用 `text-[#000000]`；若压缩结果反而更大，写 `+12%` 用 `#B91C1C`，并补一句「这张再压就大了，调小边长试试」）。
- 输出信息一行 `text-[11px] text-[#8A8A8A]`：`1920 × 1440 · JPG`。
- 下载按钮：CTA 通栏黑底（§7.3），文案「下载压缩后图片」，图标 `Download`。文件名 `<原名>-compressed.<新扩展名>`。
- 处理中（首次编码 / 换参重编码）：预览图上盖一层 `bg-white/60` + 居中 `Loader2` 旋转；**不锁死参数面板**，用户拖动时新值直接覆盖旧任务。

### 2.2 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列纵向：拖入区 / 预览 → 参数 → 结果 → 下载 | 参数控件各占满一行，滑杆触控区加高（`h-6` 的点击带）；下载按钮**吸底**通栏（`sticky bottom-0` + `bg-white px-4 pb-4 pt-2`），结果出来就不用滚回去找 |
| 平板 md ~ lg（768–1023） | 单列，参数区横排 3 列网格 | 质量 / 边长 / 结果并排一行，预览 `min-h-[300px]`；下载回到结果卡内，不再吸底 |
| 窄屏 PC lg ~ xl（1024–1279） | **两栏**：预览 `flex-1` + 右栏 `w-[300px]` | 参数面板成为独立竖栏，图片与参数同屏可见——改参数不用上下滚 |
| 宽屏 ≥ xl（1280） | 两栏：预览 `flex-1` + 右栏 `w-[340px]` | 预览可视高度按视口给（`h-[calc(100vh-16rem)]` 之类），右栏内容多时自己滚，整页不滚 |

- 两栏的切换点是 **lg**（§六：栏位方向属于结构性布局）。
- 三段用互斥显隐（`hidden lg:flex` / `lg:hidden`），不用 JS 读视口——首屏 SSR 不闪。
- **预览区的具体高度不许手算**：`calc()` 里的常量实现时在真机上量一遍再定，验收按「图片完整可见、不被压成一条缝」判定（§六）。

### 2.3 状态与边界

| 状态 | 界面 |
|---|---|
| 初始 | 拖入区，参数面板可用但只显示默认值，结果区显示 `—` |
| 已载入 / 处理中 | 预览 + 状态条 + 结果区显示加载态 |
| 完成 | 体积对比 + 下载按钮可点 |
| 格式不支持（GIF / 动图） | 结果区不出来，预览区位置给虚线框提示：「GIF / 动图暂不支持——压缩会把动图变成单帧」 |
| 解码失败（HEIC 等） | 同上：「你的浏览器打不开这个格式」+ 建议先用系统「预览」导出成 JPG |
| 超过 20 MB | 立刻拒绝，Toast `图片超过 20 MB`（§7.13），不留半截状态 |

## 三、数据模型

**不涉及。** 无数据库表、无 Server Action、无服务器文件。

图片只活在页面的内存里：`File` → `ImageBitmap` → `canvas` → `Blob` → object URL。离开页面即释放。这正是本工具最重要的一条设计（§4 第 1 条），写在这里是为了让后来者一眼看到：**这个功能没有后端**。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 压缩在哪跑 | **全部在浏览器里**（`createImageBitmap` + `canvas` + `toBlob`） | ① 服务器是 2 核小机器，几张图并发重编码就能把它占满，还会拖慢别的页面；② 不上传就没有存文件、限流、清理过期文件这一整套脏活；③ 「图片不出本机」是能直接对用户说出口的承诺 | 服务端 `sharp`（要装原生依赖、走上传带宽、还要限流与清理）；传上去再返回也慢一步 |
| 参数给几个 | 质量 + 最大边长，两个 | 体积 ≈ 像素数 × 每像素字节。多数人只调质量，其实手机照片的大头在分辨率：边长 4000 → 2000，像素数掉到 1/4。两个参数正好对应这两个乘数 | 只给质量（漏掉最大的那块收益）；给「目标体积」自动逼近（用户拿不到可控感，还要多轮编码） |
| 载入方式 | 拖拽 + 点选 + **粘贴** | 截图 → `⌘V` 是最短路径，比「先存桌面再拖进来」少两步 | 只给点选（每次都要过一遍文件对话框） |
| 参数改了要不要重压 | 立刻重压（防抖 150 ms） | 用户调参时会反复试，中间夹一次「点击压缩」等于每次多一下 | 显式按钮（多一步，且按钮态与参数态容易不同步） |
| PNG 有透明时输出什么 | **WebP** | PNG → JPEG 会把透明区变成黑或白，是无声的破坏；WebP 既保留 alpha 又比 PNG 小 | 输出 JPEG（透明变黑）；输出 PNG（几乎不压小，用户以为工具坏了） |
| PNG 无透明时输出什么 | 仍是 **PNG** | 尊重「什么进什么出」的直觉：用户存的 PNG，不该换格式回去 | 一律转 WebP（压得更多，但用户可能就是要 PNG）；自行判断「无透明就转」（同前，替用户做他没要求的决定） |
| 质量滑杆对 PNG 有效吗 | 无效，置灰并说明 | `canvas.toBlob('image/png')` 忽略质量参数（PNG 无损）——滑杆留在那儿能动却什么都不变，是最坏的体验 | 让滑杆继续可动（骗人） |
| GIF / 动图 | 直接拒绝 | `canvas` 只画第一帧，压完动图变单张静图——静默毁图比拒绝更糟 | 静默按首帧处理 |
| 元数据（EXIF / GPS） | 重编码自然丢弃，**界面上说明一句** | `canvas` 不携带元数据；丢掉 GPS 是隐私上的加分，但拍摄参数也没了，摄影的人会在意 | 保留元数据（要额外解析与回写，且与「体积更小」相背）；不说（用户后来发现时间信息没了会当成 bug） |
| 尺寸是否等比 | 只按最长边等比缩，**只缩不放** | 放大不会增加信息，只会让体积变大、观感更糊 | 允许放大到指定边长 |
| 体积单位 | **1024 进制**（1 KB = 1024 B） | 与技术口径一致，和 `ls -l` / 开发者工具看到的一致 | 1000 进制（与 macOS Finder 一致，但和命令行对不上——验收时容易来回问，见 §7） |

## 五、文件落点

1. **不新增运行时依赖**（`package.json` 的 `dependencies` / `devDependencies` 都不变）。压缩全用浏览器原生 API，图标用已装的 `lucide-react`。
2. `src/lib/` 下不许 import React 组件；本工具的纯逻辑（体积格式化、输出方案决策、目标尺寸计算）放 `src/lib/image-compress/`，可单测。
3. 路由必须落在 `src/app/(app)/tools/image-compress/`，不另建别名路由；不改首页（总览）——本工具不进首页卡片。
4. 工具信息条复用 `ToolHeader`；移动端导航行复用 `ToolMobileBar`（`newLabel="选择图片"`、`icon={ImageUp}`）。

- `src/app/(app)/tools/image-compress/page.tsx` —— 服务端接线：`requireUser()` + `metadata.title = "图片压缩"`
- `src/components/tools/image-compress/compress-view.tsx` —— 客户端视图：状态机（空 / 载入 / 编码中 / 完成 / 拒绝）、防抖与竞态守卫
- `src/components/tools/image-compress/compress-dropzone.tsx` —— 拖拽 / 点选 / 粘贴
- `src/components/tools/image-compress/compress-preview.tsx` —— 预览 + 状态条 + 原图切换
- `src/components/tools/image-compress/compress-controls.tsx` —— 质量滑杆 + 边长 chips
- `src/components/tools/image-compress/compress-result.tsx` —— 体积对比 + 下载
- `src/lib/image-compress/format-bytes.ts` —— 1024 进制体积格式化（+ 单测）
- `src/lib/image-compress/plan-output.ts` —— 由源图信息（类型 / 有无透明 / 边长上限）决定输出格式、质量是否生效、目标尺寸（+ 单测）

`src/components/tools/tool-catalog.ts` 里 `image-compress` 的 `status` 从 `"开发中"` 改为 `"可用"`（该文件的 `ToolStatus` 就是这两个中文字面量，别自己发明英文值）。

## 六、验收标准

**正常路径**

1. 打开 `/tools/image-compress`：出现工具信息条（名称「图片压缩」、分类「图片」、状态「可用」）；工作区是虚线拖入区，含「把图片拖到这里」「图片不会上传到服务器」两句。
2. 把一张 4000 × 3000 的 JPG（约 3 MB）拖进拖入区 → 预览出现，状态条显示 `4000 × 3000` 与对应体积；结果区出现压缩后体积、节省百分比、输出尺寸、下载按钮。
3. 下载后用 `ls -l` 核对：**文件字节数与页面上显示的数字一致**（1024 进制换算回去等于原字节数）。
4. 质量从 0.8 拖到 0.5 → 下载两次，后者的字节数小于前者。
5. 最大边长选 1920 → 输出信息显示宽 ≤ 1920、且高宽比与原图一致（如 4000×3000 → 1920×1440）；再选 1280 → 输出宽 1280。
6. 原图比上限小（如 800×600 选 1920）→ 输出仍是 800×600，**没有被放大**。
7. 一张带透明背景的 PNG → 输出格式显示 WebP；下载后用 `file <文件名>` 看到 `WebP`，在浏览器里打开透明区仍透明。
8. 一张不透明 PNG → 输出仍是 PNG；质量滑杆置灰，旁边说明文字可见。
9. 截图后直接 `⌘V` / `Ctrl+V` → 图片同样被载入。
10. 「看原图 / 看压缩后」切换 → 图片在两版之间切换，按钮 `aria-pressed` 跟着变。
11. 点「换一张」→ 回到拖入区，参数保留上一次的选择，结果区清空。
12. 刷新页面 → 回到初始空态（不缓存上一张）。

**负面路径**

13. 拖入 GIF → 不给下载结果，出现「GIF / 动图暂不支持」提示；页面不跳走、不白屏。
14. 拖入 HEIC → 出现「你的浏览器打不开这个格式」提示，不留半截预览。
15. 拖入 25 MB 的图 → Toast 提示超过上限，预览区仍是空态。
16. 拖入一个 `.txt` 改名的假图片 → 走解码失败提示，不抛未捕获异常。
17. 未登录直接访问 `/tools/image-compress` → 跳 `/login`。
18. 网络面板里看不到任何把图片内容发出去的请求（DevTools → Network，过滤 `Fetch/XHR` 为空）——这是「不上传」的机械证据。
19. 连续快速拖动质量滑杆 20 次 → 最终显示的结果对应**最后一次**的值（不是中途某一次的快照），页面不卡死。

**响应式**

20. 375px：单列；拖入区高度约 220px；参数各占一行；结果出现后下载按钮吸底通栏可见。
21. 768px：单列；参数区横排 3 列；预览高度 ≥ 300px。
22. 1100px：两栏（预览 + 右栏 300px）；改参数时图片与结果同屏可见，不需要滚动。
23. 1440px：两栏（预览 + 右栏 340px）；图片完整可见，未被压成一条缝。

**门禁**

24. `pnpm exec next typegen` / `pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` 全过。
25. 单测覆盖：体积格式化（B / KB / MB 边界、1024 进制、0 字节）、输出方案（JPG → JPG + 质量生效；PNG 有透明 → WebP；PNG 无透明 → PNG + 质量不生效）、目标尺寸（超上限缩、未超上限不放大、等比取整）。

## 七、已知的坑

| 坑 | 机制 | 对策 |
|---|---|---|
| 拖拽文件时整页跳到那张图 | 浏览器对 `dragover` / `drop` 的默认行为是「打开文件」 | 两者都 `preventDefault()`；`drop` 里再取 `dataTransfer.files[0]` |
| 手机照片方向歪了 | 照片的方向存在 EXIF 里，解码时不应用就会横躺 | `createImageBitmap(file, { imageOrientation: "from-image" })` 显式指定，不依赖默认值 |
| 大图画出来是空白 | iOS Safari 的 canvas 面积有上限（约 1600 万像素），超了画布直接失效 | **canvas 按目标尺寸创建**（`canvas.width = targetW`），绝不先建一个原尺寸画布再缩；文件本身也限 20 MB |
| PNG 的质量滑杆骗人 | `toBlob('image/png')` 忽略 quality 参数 | 源是 PNG 且无透明时，滑杆置灰 + 说明；`plan-output` 里把「质量是否生效」算成显式字段 |
| 透明 PNG 转 JPEG 变黑底 | JPEG 没有 alpha 通道，透明像素被填成黑（或白） | 有透明像素 → 输出 WebP；判断方式：把图画到 canvas 后读 `getImageData` 的 alpha 通道，或解码前先用 `createImageBitmap` + 小画布抽样（整图 `getImageData` 太慢） |
| 拖动滑杆把主线程堵死 | 每次 change 都同步重编码 4000px 的图 | 防抖 150 ms + `requestAnimationFrame` 后再编码；编码中再改参数只覆盖「待办任务」，不排队 |
| 结果与参数对不上（乱序） | `toBlob` 是异步的，连续多次调用返回顺序不保证 | 每次任务带自增序号，回调里序号不等于最新就直接丢弃结果 |
| 内存泄漏 | 每次重压都生成一个 object URL，不 revoke 会一直占内存 | 换图 / 重压 / 卸载时 `revokeObjectURL` 旧 URL（在 `useEffect` 清理函数里成对处理） |
| 手机长按图片弹出系统菜单 | 「按住看原图」的交互在移动端会触发「存储图片 / 在新标签打开」 | 改成点击切换（`aria-pressed`），不做长按 |
| 体积数字和 Finder 对不上 | Finder 用 1000 进制，本工具用 1024 进制，同一文件差约 5% | 文档与验收都以**字节数**为准（§6 第 3 条），界面上不并列两套单位 |
| 粘贴事件只在页面内有效 | `paste` 监听挂在 window 上，焦点在别的应用时不触发 | 文案写「在本页按 ⌘V」，不承诺系统级快捷键 |
| 换了图但预览还是旧的 | object URL 变了而 `<img src>` 复用了同一节点 | `<img key={url}>` 强制重建 |
| HEIC 有时能开有时不能 | iOS Safari 原生解得了，桌面 Chrome 解不了 | 不按扩展名硬判，统一走「解码失败」提示，文案写「你的浏览器打不开这个格式」 |
| 输出比原图还大 | 大质量 + 小图 + PNG → PNG，重编码结果可能反而变大 | 结果区显示红色 `+N%` 并给一句建议；不静默让用户下载一个更大的文件 |
| 服务端组件里用了浏览器 API | `page.tsx` 是服务端组件，`document` / `canvas` 不存在 | 所有 DOM 操作只写在 `"use client"` 的视图组件里；页面只做 `requireUser()` 与渲染 |

无。压缩用浏览器原生 `createImageBitmap` / `canvas` / `toBlob`，图标用已装的 `lucide-react`（`Image`, `ImageUp`, `Download`, `Loader2`）。
