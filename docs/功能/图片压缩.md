# 图片压缩

| 状态 | 开始日期 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-10-30 | 2026-10-30 |

> 一句话：选一张（或一批）图、拖一下质量、看体积掉下来，然后把压缩结果下载走——**原尺寸压缩**，全程在浏览器里完成，图片一个字节都不上传。

---

## 一、要什么

**做：**

- **工具页** `/tools/image-compress`：单张 + **批量**图片压缩。拖入 / 点选 / 粘贴把图载进来，一个参数（质量），看到「原体积 → 新体积」，一键下载
- **批量模式**：一次多选 / 多拖（≥ 2 张）进入批量——列表逐张压、逐张下载，另有「下载全部（ZIP）」与「继续压缩」；1 张仍走单张流程。上限：单张 20 MB、每批 30 张 / 200 MB（超出逐条标「已跳过」）
- **输入白名单**：只收 **JPG / JPEG / PNG** 三种。其余格式（WebP / GIF / HEIC / BMP…）一律拒绝并说明原因
- **落点方式三种**：拖拽到拖入区、点「选择图片」开系统文件框、页面里 `⌘/Ctrl + V` 粘贴（截图后直接粘是最顺的路径）
- **纯浏览器端处理**：JPG 走 **mozjpeg 的 WASM**（`@jsquash/jpeg`）按质量重编码；PNG 走 **调色板量化（imagequant 的 WASM）+ oxipng 无损收尾**。两种格式都在 Worker 里编码，输出格式不变。**不上传、不落库、不写服务器文件**——服务器在这条链路上完全不参与
- **参数**：只有一个质量滑杆（0.5–0.95，默认 0.8）。**没有「最大边长」**：输出像素尺寸恒等于原图，只缩质量、不缩尺寸（2026-10-30 联调移除）。质量对两种格式都有效：JPG 是重编码质量，PNG 是**调色板颜色数**（0.95 ≈ 256 色、0.5 ≈ 16 色）
- **触发方式**：**手动点「开始压缩」才编码**。选图、拖质量都只更新参数，不会自动压；参数一改，上一份结果立刻作废（数字必须与滑杆严格对应）
- **结果**：原图与压缩后的体积对比、省下百分比、输出像素尺寸、精确字节数、下载按钮；画面上用**对比滑块**（左原图 / 右压缩后，中间竖线可拖）看两版接缝
- **继续压缩**：结果出来后可一键**降一档质量、从最初的原图重新压**（80% → 70% → 60%…），体积继续变小；到最低质量或没变小就提示，已有结果保留
- **目录同步**：`tool-catalog` 里 `image-compress` 的状态从「开发中」改为「可用」
- **页签栏登记**：`tab-routes.ts` 的 `TOOL_TAB_SLUGS` 加上 `image-compress`——页签栏是显式白名单，不登记就不会出现「图片压缩」标签（《功能/页签栏》§二）
- 三档响应式各自一套版式（见 §2.2）

**主动放弃（本版不做，不是遗漏）：**

| 放弃项 | 原因 |
|---|---|
| 目标体积模式（压到 200KB 以内） | 要二分试压 + 多轮编码，用户得到的还是一个他看不懂的滑块位置；直接给质量，他自己拖两下更快 |
| 格式转换（JPG ↔ PNG ↔ WebP 自由选） | 与目录里另一个工具「图片格式转换」职责重叠；本工具的格式规则只为「压得动」服务 |
| **按边长缩放** | 2026-10-30 联调决定整个移除：只做原尺寸压缩，界面上不再有「最大边长」这一组 chip，`targetSize` 一类的尺寸计算也一并删掉 |
| **WebP 作为输入** | 2026-10-30 联调决定收窄为白名单：只支持 JPG / PNG 这两种最常用的。WebP / HEIC / BMP 等交给格式转换工具 |
| 服务端压缩 / 图片上传 | 见 §四 第 1 条 |
| 压缩历史 / 最近处理 | 图片本身不留存，留一份「处理记录」也只是一堆文件名；要重压就再拖一次 |
| 裁剪 / 旋转 / 水印 / 去背景 | 都是独立工具的事，塞进来会让这个页面的参数面板失去边界 |
| 保存到「文件」页 / 云同步 | 「文件」页仍是占位；压缩完直接下载，不引入存储与清理策略 |

## 二、界面

### 2.1 工具页 `/tools/image-compress`

与便签 / 待办工具页同构：**没有 PageHeader**，工具名与状态在内容区的信息条里（`ToolHeader`，状态点「可用」）。手机上顶部是 `ToolMobileBar`（汉堡 + 「选择图片」，图标 `ImageUp`）。

```
移动端导航行（< lg）：汉堡 + 选择图片
内容区（px-4 py-4 md:px-6 md:py-6 space-y-4）
├─ 工具信息条（ToolHeader，状态「可用」）
└─ 工作区
   ├─ 预览区（左 / 上）
   │   ├─ 空态：拖入区（虚线框 + 图标 + 三行提示）
   │   └─ 已载入：图片预览 + 顶部状态条（文件名 · 尺寸 · 体积）+ 右上「换一张」
   └─ 参数面板（右 / 下）
       ├─ 分组标题「压缩参数」（§7.2）
       ├─ 质量滑杆
       ├─ 分组标题「结果」
       ├─ 体积对比（原 → 新 · 省了多少）
       └─ 下载按钮（CTA，通栏黑底）
```

**空态（还没载入图片）**

```tsx
<div className="flex min-h-[220px] flex-col items-center justify-center gap-3 rounded-[2px] border border-dashed border-[#D9D9D9] bg-white p-8 text-center md:min-h-[300px] xl:min-h-[360px]">
  <ImageUp className="h-7 w-7 text-[#C4C4C4]" />
  <p className="text-sm font-medium text-[#000000]">把图片拖到这里</p>
  <p className="text-xs text-[#8A8A8A]">或点击选择文件、按 ⌘/Ctrl + V 粘贴</p>
  <p className="text-[11px] text-[#A0A8B4]">支持 JPG / PNG，单张不超过 20 MB；可一次拖入多张，图片不会上传到服务器</p>
</div>
```

整块拖入区**本身是按钮**（`role="button"` / 点击开文件框 / `Tab` 可达 / `Enter` 触发），不用再在里面塞一个「选择文件」按钮——同一件事两个入口，用户会犹豫。系统文件框的 `accept` 也收窄成 `image/jpeg,image/png,.jpg,.jpeg,.png`。

拖拽悬停（`dragover` 且确实带文件）：边框 `border-[#000000]`、底色 `bg-[#F5F5F5]`；`dragleave` / `drop` 复原。**必须给 `dragover` 加 `preventDefault()`**，否则浏览器默认行为是「打开这张图片」，整页跳走。

**已载入（预览区）**

- 图片 `max-h-full max-w-full object-contain` 居中，底色 `bg-[#F5F5F5]`（透明 PNG 才看得出透明）。
- 顶部状态条：文件名（`truncate`）+ `text-[11px] text-[#999999]` 的尺寸与体积 + 右侧「换一张」文字按钮（`text-xs text-[#8A8A8A] hover:text-[#000000]`）。
  - 还没出结果：`4000 × 3000 · 3.0 MB`。
  - 出结果后**两版并列**：`4000 × 3000 · 原图 3.0 MB → 压缩后 1.4 MB`——画面上同时摆着两版（左原图 / 右压缩后），只写一个数会让人以为另一侧也是那个体积。
  - 手机上尺寸体积另起一行（`md:hidden` 的第二行），否则文件名会被挤成「p…」。
- **对比滑块（2026-10-30 联调，替掉原来的「看原图 / 看压缩后」按钮）**：出结果后画面中间出现一条竖线 + 中间一个抓手，**左边原图、右边压缩后**；按住左右拖（鼠标 / 触屏 / 触控笔都行），分割线到哪，两版就在哪接缝。
  - 抓手上带左右箭头图标（`ChevronsLeftRight`），`h-7 w-7` 白底圆 + 细边框 + 阴影；竖线 `w-0.5` 白色 + 柔和阴影（深浅底图上都看得见），只在图片显示范围内、上下贴住图片边缘。
  - **点击画面任意位置直接跳过去**；**双击画面回到 50%**（默认位置）。
  - 键盘：抓手 `role="slider"`、可 Tab 聚焦，`←/→` 每次 2%（`Shift` 10%）、`Home`/`End` 到两端；`aria-valuenow` 0–100。
  - 位置按**图片实际显示矩形**换算，不按容器：竖图在宽容器里左右留白，按容器算会拖到留白区还在动、图片本身却不变。显示尺寸不放大（与 `max-w/max-h` 行为一致），保证上层压缩后与底图逐像素对齐。
  - 触屏 `touch-action: pan-y`：左右拖归滑块，上下滑仍然滚页面；容器再加 `select-none` + `-webkit-touch-callout: none`，挡掉长按弹出系统「存储图片」菜单。
- 换图 / 卸载时把上一张的 object URL `revokeObjectURL` 掉。

**批量模式（≥ 2 张）**

- 左侧预览位换成**文件列表**（`BatchList`）：白卡，头部「批量压缩 · N 张」+ 右侧「清空」；每行「序号 / 文件名 / 原始体积 → 压缩后体积 / 下载或状态」。
  - 状态：待压缩（灰字）、压缩中（`Loader2`）、已跳过（红字 + 原因：超过 20 MB / GIF / 非 JPG-PNG）、压不动、失败。
  - 每行成功后给一个「下载」按钮（`<a download>`），文件名 `<原名>-compressed.<ext>`。
- 右侧参数面板与单张共用：质量滑杆 + 「开始压缩」+ 结果区（`BatchSummary`）：
  - 压缩中显示「正在压缩第 N / M 张…」（串行，进度真实）；
  - 完成后「合计 X MB → Y MB / -Z%」「N 张可下载 · K 张跳过或压不动」；
  - 「下载全部（ZIP）」把成功的结果打成一个 `compressed-images.zip`（store 模式，不二次压缩）；
  - 「继续压缩」= 质量降一档、整批重压（和单张同一套语义）。
- 移动端不额外吸底：结果区的「下载全部（ZIP）」已经是主操作，列表与它同屏可见（2026-10-30 联调：吸底那条是重复入口，删掉）。
- 批量是**串行**压缩：WASM 编码 CPU 密集，并行只会互相拖慢并顶高内存；串行还能给出真实进度。
- 压缩中改质量 / 换一批 / 清空：当前这一轮**整体作废**（列表回到「待压缩」、旧结果与 object URL 一起释放），不会出现「前几张是旧质量、后几张是新质量」的混合结果。
- 准入：单张 20 MB、每批 30 张、整批原始总量 200 MB；超出的文件留在列表里标「已跳过」并写明原因，不占名额、不影响同批其它张（规则在 `src/lib/image-compress/batch-rules.ts`，有单测）。

**参数面板**

- 白卡 `rounded-[2px] bg-white p-5`，分组标题用 §7.2（黑竖条）。
- **质量**：`input type="range"`，`min=0.5 max=0.95 step=0.05`，`accent-[#000000]`；右侧当前值 `text-[13px] font-medium tabular-nums`（显示成 `80%`）。下方一行 `text-[11px] text-[#8A8A8A]`：「越低体积越小，细节越容易糊」。
- **没有最大边长**：2026-10-30 联调把这一组 chip 整个删掉，输出尺寸恒等于原图（不缩小、也不放大）。
- **质量滑杆对两种格式都有效**：JPG 是重编码质量；PNG 是**调色板颜色数**（滑杆越低颜色越少、体积越小，渐变/细节可能出现色带）。下方说明：「越低体积越小，画质损失越明显（PNG 会做调色板量化，颜色变少）」。
- **「开始压缩」按钮**（通栏黑底 CTA，§7.3）：滑杆下方，是页面唯一会触发编码的入口。没载入图片时置灰；编码中换成「压缩中…」+ `Loader2` 并禁用（防连点排队）。
- **编码进度**：预览图上盖一层 `bg-white/80` 遮罩，里面有 `Loader2`、「正在压缩… 已用 N 秒」、一条**进度条**（`role="progressbar"`）和一句「大图可能要几秒到十几秒，请不要关闭页面」。oxipng 拿不到真实进度，进度条按「已用时间 / 预计时间」推进、封顶 95%——它只回答「还在动、大概要多久」，秒数是真实的。**编码跑在 Web Worker 里**，主线程不阻塞，动画与页面交互都正常（2026-10-30 联调：之前同步 WASM 跑在主线程，页面直接冻住，看着像卡死）。
- **改质量会让已有结果作废**：结果区回到虚线占位「点『开始压缩』生成结果」，下载按钮一起消失——不允许出现「滑杆在 50%、结果却是 80% 压出来的」。要新结果就再点一次。

**结果区**

- 空态**不摆一排破折号**（`原图 — → —` 和右侧孤零零的大 `—` 会被读成一根横线，2026-10-30 联调指出太丑）：换成和拖入区同语言的虚线占位块，一句话说明下一步——没载入时「载入图片后，这里显示压缩后的体积与下载」；已载入但没点按钮时「点『开始压缩』生成结果」；编码中「压缩中…」。占位块里不出现任何数字。
- 体积对比：`原图 3.0 MB → 620 KB`，右侧大字 `-79%`（省下时用 `text-[#000000]`）。
- **压不动**（优化后没有变小）：**不显示百分比、不出下载、不出对比滑块**，只写一行来源 + 一句原因：「原图 10 MB · 1632 × 2912 · PNG」「重编码后反而变大了（X MB）——这张 PNG 已经压到极限了，原图就是最优结果，直接用原图就行。」；若质量参数本来生效（JPG），原因换成「把质量调低一点，再点一次『开始压缩』试试」。
  - 为什么会有这种情况：PNG 用 oxipng 做无损优化，本身已经优化过的图确实再压不小；JPG 在极高质量 + 小图时也可能涨回来。**绝不把更大的文件递给用户**——没变小就判定压不动。
- 自动降过质量时补一行 `text-[11px]`：「质量 95% 会压得更大，已自动降到 65%」。
- 输出信息两行 `text-[11px] text-[#8A8A8A]`：`1920 × 1440 · JPG`，下面一行是**精确字节数**（`6985523 字节`）——`MB / KB` 带小数必然被舍入，而验收要拿 `ls -l` 逐字节核对，所以单独显示不加工的原值。
- 下载按钮：CTA 通栏黑底（§7.3），文案「下载压缩后图片」，图标 `Download`。文件名 `<原名>-compressed.<新扩展名>`。
- **「继续压缩」按钮**（灰底次要操作，`RefreshCw` 图标）：下载按钮下方。点一下**把质量降一档（-10%）、从最初的原图重新压**——不是在上一次结果上级联，避免叠代际画质损失；更小才提交（滑杆跟着变），到 50% 或没变小就提示「已经到最低质量了 / 再降也小不了了」，已有结果保留。
- 处理中（首次编码 / 换参重编码）：预览图上盖一层 `bg-white/60` + 居中 `Loader2` 旋转；**不锁死参数面板**，用户拖动时新值直接覆盖旧任务。

### 2.2 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列纵向：拖入区 / 预览 → 参数 → 结果 → 下载 | 参数控件占满一行，滑杆触控区加高（`h-6` 的点击带）；**单张模式**下载按钮**吸底**通栏（`sticky bottom-0` + `bg-white px-4 pb-4 pt-2`），结果出来就不用滚回去找；**批量模式不吸底**——结果区的「下载全部」和列表同屏，吸底是重复入口 |
| 平板 md ~ lg（768–1023） | 单列，参数区横排 **2 列** | 质量 / 结果并排一行，预览 `min-h-[300px]`；下载回到结果卡内，不再吸底 |
| 窄屏 PC lg ~ xl（1024–1279） | **两栏**：预览 `flex-1` + 右栏 `w-[300px]` | 参数面板成为独立竖栏，图片与参数同屏可见——改参数不用上下滚 |
| 宽屏 ≥ xl（1280） | 两栏：预览 `flex-1` + 右栏 `w-[340px]` | 预览可视高度按视口给（实测 `xl:h-[calc(100vh-22rem)]`：1440×900 下图片完整可见、整页不滚），右栏内容多时自己滚，整页不滚 |

- 两栏的切换点是 **lg**（§六：栏位方向属于结构性布局）。
- 三段用互斥显隐（`hidden lg:flex` / `lg:hidden`），不用 JS 读视口——首屏 SSR 不闪。
- **预览区的具体高度不许手算**：`calc()` 里的常量实现时在真机上量一遍再定，验收按「图片完整可见、不被压成一条缝」判定（§六）。

### 2.3 状态与边界

| 状态 | 界面 |
|---|---|
| 初始 | 拖入区，参数面板可用但只显示默认值，「开始压缩」置灰，结果区是虚线占位说明（不显示数字） |
| 已载入 / 等待压缩 | 预览 + 状态条；结果区占位「点『开始压缩』生成结果」；下载按钮不出现 |
| 压缩中 | 预览图上盖遮罩：`Loader2` + 「正在压缩… 已用 N 秒」+ 进度条 + 提示语；按钮换「压缩中…」并禁用；结果区占位显示「压缩中…」。**主线程不阻塞**（编码在 Worker 里） |
| 批量（≥ 2 张） | 列表逐行显示 待压缩 / 压缩中 / 完成 / 压不动 / 跳过；结果区给合计、节省百分比、ZIP 下载与继续压缩 |
| 继续压缩 | 结果区出现「继续压缩」按钮；点了质量降一档、从原图重压，体积继续变小（滑杆同步变化）；到 50% 或没变小则提示，已有结果与下载都保留 |
| 完成 | 体积对比 + 精确字节数 + 下载按钮可点 |
| 压不动（重编码没变小） | 结果区只说明原因（原图多大、试出来多大、为什么），不出百分比、不出下载、不出对比滑块 |
| 参数已改（结果作废） | 结果区退回「点『开始压缩』生成结果」，下载按钮消失；再点一次才出与当前参数对应的结果 |
| 不在白名单（WebP / HEIC / BMP 等） | 结果区不出来，预览区位置给虚线框提示：「只支持 JPG / PNG 图片」+「WebP、HEIC、BMP 等格式暂不支持——请先转成 JPG 或 PNG 再拖进来。」 |
| GIF / 动图 | 同上，但文案更具体：标题「GIF / 动图暂不支持」，说明「压缩会把动图变成单帧静图，所以这里不做——请换一张 JPG 或 PNG。」 |
| 解码失败（改名成 `.jpg` 的 txt 等） | 同上：「你的浏览器打不开这个格式」+ 建议先用系统「预览」导出成 JPG |
| 超过 20 MB | 立刻拒绝，Toast `图片超过 20 MB`（§7.13），不留半截状态 |

---

## 三、数据模型

**不涉及。** 无数据库表、无 Server Action、无服务器文件。

图片只活在页面的内存里：`File` → `ImageBitmap` → `canvas` → `Blob` → object URL。离开页面即释放。这正是本工具最重要的一条设计（§4 第 1 条），写在这里是为了让后来者一眼看到：**这个功能没有后端**。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 压缩在哪跑 | **全部在浏览器里**（`createImageBitmap` + `canvas` + `toBlob`） | ① 服务器是 2 核小机器，几张图并发重编码就能把它占满，还会拖慢别的页面；② 不上传就没有存文件、限流、清理过期文件这一整套脏活；③ 「图片不出本机」是能直接对用户说出口的承诺 | 服务端 `sharp`（要装原生依赖、走上传带宽、还要限流与清理）；传上去再返回也慢一步 |
| 参数给几个 | **只有一个质量** | 2026-10-30 联调定的：只做原尺寸压缩。少一个控件少一次犹豫，质量是唯一能直接看到体积变化的杠杆 | 质量 + 最大边长（原设计，联调移除）；「目标体积」自动逼近（要二分试压，用户拿不到可控感） |
| 要不要缩放 | **不缩放**：输出像素尺寸恒等于原图 | 联调决定：用户要的是「同一张图小一点」，不是改尺寸；也省掉「只缩不放」「等比取整」这一整套规则 | 按边长档位缩（2560 / 1920 / 1280），已删 |
| 载入方式 | 拖拽 + 点选 + **粘贴** | 截图 → `⌘V` 是最短路径，比「先存桌面再拖进来」少两步 | 只给点选（每次都要过一遍文件对话框） |
| 压缩一次之后还能不能再压 | **「继续压缩」= 质量降一档、从最初的原图重压**（能更小才提交，否则保留原结果） | 2026-10-30 联调要求「继续压缩」。从原图重压而不是在结果上级联：JPG 不叠代际画质损失，PNG 调色板颜色数也能一档档降；先试压再决定是否提交，避免点一下反而把可下载的结果弄丢 | 在上一次结果上级联（画质越压越差、收益也小）；重复点「开始压缩」（质量不变，等于重来） |
| 批量怎么压 | **串行逐张压**（不是并行） | WASM 编码 CPU 密集，并行只会互相拖慢、顶高内存；串行还能给「第 N / M 张」的真实进度。单张与批量的边界是「1 张走单张流程，≥ 2 张进列表」 | 并行 Promise.all（快一点但容易把内存和主线程顶满）；只做单张（联调要求批量） |
| 批量怎么下载 | **逐张下载 + 全部打包 ZIP** | 一次触发多个下载会被浏览器拦（弹「允许多个下载」或直接只给第一个），ZIP 是一步到位的做法 | 循环触发 `<a download>`（被拦截、体验不可控）；用现成 zip 库（待打包的已是压缩产物，store 模式自己写 ZIP 更轻，见 §五） |
| 编码跑在哪 | **Web Worker**（PNG 的 oxipng）；JPG 的 canvas 编码很快，留在主线程 | oxipng 是同步 WASM，放主线程会把页面连同动画一起冻住——联调实测「点开始压缩就卡死」，放 Worker 后进度条、秒数、按钮都正常 | 主线程同步跑（卡死，已踩过） |
| 原图 / 压缩后怎么对比 | **对比滑块**：同一块画面上左原图、右压缩后，中间竖线 + 抓手可拖（点击跳转 / 双击复位 / 方向键微调） | 2026-10-30 联调定的：切换按钮要点两次才能比出差别，分割线一眼就能看到两版的接缝；拖动还能停在任意位置逐块比对 | 「看原图 / 看压缩后」切换按钮（要点两次，且手机上长按会弹系统菜单）；并排两张缩略图（太占空间、细节看不清） |
| 什么时候压缩 | **点「开始压缩」才压**；改参数会让旧结果作废、要再点一次 | 2026-10-30 联调定的：要一个明确的开始动作。作废旧结果是为了让「滑杆上的数字」与「结果区的数字」永远严格对应——按钮态与参数态不同步正是显式按钮最容易踩的坑，这里直接把它堵掉 | 载入即压、改参防抖重压（原设计，联调改掉）；保留旧结果只加一句「参数已改」（用户会下载到与参数不符的文件） |
| 收哪些输入格式 | **白名单：只收 JPG / JPEG / PNG** | 2026-10-30 联调定的：只支持最常用的两种。格式规则少一半，提示语也简单——不支持就直说，不留「浏览器有时能解有时不能」的模糊地带 | 收 WebP（原设计，联调改为不支持）；按扩展名猜格式（改名文件会被误判） |
| GIF / 动图 | 直接拒绝 | `canvas` 只画第一帧，压完动图变单张静图——静默毁图比拒绝更糟 | 静默按首帧处理 |
| 白名单判断依据 | **MIME 或扩展名任一命中即放行** | 拖拽路径下 `File.type` 可能是空串；而改名成 `.jpg` 的 txt 要走到解码那一步才报「打不开」，不能按扩展名提前判死 | 只看 MIME（空串会误杀 JPG）；只看扩展名（改名文件提示不准确） |
| PNG 输出什么 | **仍是 PNG，但做调色板量化 + oxipng 收尾**（imagequant 的 WASM） | 2026-10-30 联调定：PNG 必须还是 PNG（不能换成 WebP）。canvas 没有 PNG 优化能力，oxipng 无损只能再紧几个百分点；调色板量化才是 PNG 的「市面水平」——实测 1.5 MB → 419 KB（−73%）、10 MB → 1.7 MB（−83%），代价是颜色变少（有损） | 换 WebP（联调否决）；只做无损优化（几乎压不动，用户以为工具坏了）；canvas 重编码（会变大） |
| 质量滑杆对 PNG 有效吗 | **有效：控制调色板颜色数**（0.95 ≈ 256 色、0.5 ≈ 16 色） | PNG 靠调色板量化压体积，颜色数就是「质量」；滑杆对两种格式语义一致（越低越糊/颜色越少） | 置灰（那 PNG 就只剩无损的 3–5%，等于没压）；只给固定 256 色（用户没法继续往下压） |
| 元数据（EXIF / GPS） | 重编码自然丢弃，**界面上说明一句** | `canvas` 不携带元数据；丢掉 GPS 是隐私上的加分，但拍摄参数也没了，摄影的人会在意 | 保留元数据（要额外解析与回写，且与「体积更小」相背）；不说（用户后来发现时间信息没了会当成 bug） |
| 体积单位 | **1024 进制**（1 KB = 1024 B） | 与技术口径一致，和 `ls -l` / 开发者工具看到的一致 | 1000 进制（与 macOS Finder 一致，但和命令行对不上——验收时容易来回问，见 §7） |
| 优化没变小怎么办 | **判定「压不动」**：不显示百分比、不提供下载，只说明原因 | 工具的意义是把图变小，给一个更大的文件等于帮倒忙；PNG 用 oxipng 已经压到极限、JPG 在极高质量下都可能出现，用户看到 `+35%` 只会怀疑工具坏了 | 给红色 `+N%` 让用户自己判断（还是给了更大的文件）；强行输出 WebP（替用户改了格式，违反「什么进什么出」） |
| 精确字节数 | 结果区**额外显示不加工的字节数** | `MB / KB` 带一位小数就必然被舍入，而验收要拿 `ls -l` 逐字节核对；字节和 KB/MB 是同一套 1024 口径，不算「并列两套单位」 | 只显示 MB/KB（数字对不上 `ls -l`，验收时来回解释） |

## 六、验收标准

**正常路径**

1. 打开 `/tools/image-compress`：出现工具信息条（名称「图片压缩」、分类「图片」、状态「可用」）；工作区是虚线拖入区，含「把图片拖到这里」「图片不会上传到服务器」两句，且只提「支持 JPG / PNG」。
2. 把一张 4000 × 3000 的 JPG 拖进拖入区 → **预览出现，但结果区不出数字**（占位「点『开始压缩』生成结果」、没有下载按钮）；状态条显示 `4000 × 3000` 与对应体积；点「开始压缩」→ 结果区出现压缩后体积、节省百分比、输出尺寸、下载按钮。
3. 下载后用 `ls -l` 核对：**文件字节数与页面上显示的精确字节数完全相等**（`MB / KB` 那行按 1024 进制换算也能对上）。
4. 质量从 0.8 拖到 0.5 → 旧结果立刻作废（下载按钮消失）；再点「开始压缩」→ 下载两次，后者的字节数小于前者。
5. 输出尺寸恒等于原图：4000×3000 进 → 4000×3000 出；800×600 进 → 800×600 出（**不放大、也不缩小**）。
6. 一张带透明背景的 PNG → 输出格式**仍是 PNG**（不换格式），下载后用 `file <文件名>` 看到 `PNG image data`，透明区仍透明；体积至少小一半（调色板量化）。
7. 一张不透明 PNG（如 UI 截图）：质量滑杆可用、说明里提到「PNG 会做调色板量化」；点「开始压缩」后体积大幅变小（通常 −50%~−80%）、可下载、可对比；滑杆调低后颜色更少、体积更小。
8. 截图后直接 `⌘V` / `Ctrl+V` → 图片同样被载入。
9. 出结果后出现对比滑块：左边原图、右边压缩后，默认停在 50%；拖动抓手 → 分割线跟手、右侧裁切跟着变；点击画面任意位置 → 直接跳过去；`Home` / `End` 或拖到两端 → 整张看某一版；双击画面 → 回 50%；抓手可 Tab 聚焦、方向键每次 2%。
10. 点「换一张」→ 回到拖入区，质量保留上一次的选择，结果区清空。
11. 刷新页面 → 回到初始空态（不缓存上一张，参数复位 0.8）。

**批量**

- 一次多选 / 多拖 4 张（含 1 张 GIF）→ 进入批量：列表 4 行，GIF 那行标「已跳过 / GIF / 动图暂不支持」。
- 点「开始压缩」→ 逐行变压缩中、结果区显示「正在压缩第 N / 3 张…」；完成后 3 行各有「下载」，结果区「合计 X MB → Y MB / -Z%」「3 张可下载 · 1 张跳过」。
- 「下载全部（ZIP）」→ 得到一个 `compressed-images.zip`，`unzip -t` 无错误、里面 3 个文件与逐张下载的字节一致。
- 「继续压缩」→ 质量降一档（滑杆同步）、整批重压、合计更小。
- 「清空」→ 回到空态拖入区，URL 全部释放。
- 压缩中把质量从 80% 拖到 50% → 整批回到「待压缩」、无下载按钮、无混合质量的旧结果；再点「开始压缩」按 50% 重压。
- 压缩中点「清空」→ 直接回空态，不会在几秒后冒出半截结果。
- 一次塞 31 张 / 超过 200 MB → 超出的行标「已跳过」并写明原因，合法的那批照常能压。
- 手机照片（EXIF 方向 6）：状态条的尺寸与下载产物的像素尺寸一致（800 × 1200），不是横躺的 1200 × 800。

**负面路径**

12. 拖入 GIF → 不给下载结果，出现「GIF / 动图暂不支持」提示；页面不跳走、不白屏。
13. 拖入 WebP / HEIC / BMP → 出现「只支持 JPG / PNG 图片」提示，不留半截预览。
14. 拖入一个 `.txt` 改名的假图片 → 走解码失败提示「你的浏览器打不开这个格式」，不抛未捕获异常。
15. 拖入 25 MB 的图 → Toast 提示超过上限，预览区仍是空态。
16. 未登录直接访问 `/tools/image-compress` → 跳 `/login`。
17. 网络面板里看不到任何把图片内容发出去的请求（DevTools → Network，过滤 `Fetch/XHR` 里只有应用外壳的 RSC 预取，与图片无关）——这是「不上传」的机械证据。
18. 连续快速拖动质量滑杆 20 次 → 结果区作废（不显示任何中途快照），页面不卡死；再点一次「开始压缩」→ 结果对应**最后一次**的值。

**响应式**

19. 375px：单列；拖入区高度约 220px；参数各占一行；结果出现后下载按钮吸底通栏可见。
20. 768px：单列；参数区横排 **2 列**（质量 / 结果）；预览高度 ≥ 300px；下载回到结果卡内。
21. 1100px：两栏（预览 + 右栏 300px）；改参数时图片与结果同屏可见，不需要滚动。
22. 1440px：两栏（预览 + 右栏 340px）；图片完整可见，未被压成一条缝，整页不滚。

**门禁**

23. 载入图片后不点按钮等 3 秒：结果区仍是占位、没有下载按钮（证明不会自动压缩）。
24. 点「开始压缩」压一张较大的 PNG：预览区出现遮罩、进度条在推进、「已用 N 秒」在涨，**期间页面不卡顿**（按钮变禁用、滑杆仍可见）；压完后遮罩消失、结果出现。
25. 一张**已经压过**的 JPG（如 q28 存出来的），质量拉到 95% 点「开始压缩」：结果仍比原图小、滑杆自动降到实际质量、结果区标注「质量 95% 会压得更大，已自动降到 X%」。
26. 结果出来点「继续压缩」：质量自动降一档（滑杆同步），JPG 与 PNG 都会再变小、原图基准仍是同一张；连点到 50% 后再点 → 提示「已经到最低质量了」，原有结果与下载按钮都还在。
27. 手机上（375px）拖动分割线时页面不跟着横向晃、上下滑仍能滚页面；长按画面不弹系统「存储图片」菜单。
28. `pnpm exec next typegen` / `pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` 全过。
29. 单测覆盖：体积格式化（B / KB / MB 边界、1024 进制、0 字节、省百分比）；输出方案（JPG → JPG + 质量生效；PNG → PNG + 质量不生效）；输入白名单（JPG / JPEG / PNG 放行，WebP / GIF / HEIC / BMP / txt 拒绝）；文件名与 GIF 判定。

## 七、已知的坑

| 坑 | 机制 | 对策 |
|---|---|---|
| 拖拽文件时整页跳到那张图 | 浏览器对 `dragover` / `drop` 的默认行为是「打开文件」 | 两者都 `preventDefault()`；`drop` 里再取 `dataTransfer.files[0]` |
| 手机照片方向歪了 | 照片的方向存在 EXIF 里，解码时不应用就会横躺；编码搬到 Worker 后有两处解码，任何一处漏掉都会让产物横躺、尺寸和状态条对不上 | 主线程读尺寸与 Worker 编码**都**显式 `createImageBitmap(..., { imageOrientation: "from-image" })`，不依赖浏览器默认值；验收里用一张方向 6 的照片钉住 |
| 大图画出来是空白 | iOS Safari 的 canvas 面积有上限（约 1600 万像素），超了画布直接失效 | 画布按**源尺寸**创建（取消了边长档位，没有更小的目标尺寸可用）。桌面 Chrome 无碍；**手机上的超大图（> 约 1600 万像素）仍有画不出来的风险**，20 MB 上限不等于像素上限。要彻底消除只能对超大图自动降采样——那等于恢复缩放，联调已否决，先记为已知限制 |
| PNG 的质量滑杆骗人 | PNG 走 oxipng 无损优化，没有 quality 参数 | 源是 PNG 时滑杆置灰 + 说明「PNG 走无损优化」；`plan-output` 里把「质量是否生效」算成显式字段 |
| oxipng 的 wasm 把构建卡死 | `@jsquash/oxipng/optimise` 入口会连带把并行版 codec 与 `wasm-feature-detect` 拉进构建，Turbopack 解析时直接卡住（实测 10 分钟无进展） | 只 import 单线程 glue 子路径 `@jsquash/oxipng/codec/pkg/squoosh_oxipng.js`；wasm 由 glue 的 `new URL(…, import.meta.url)` 交给打包器发成静态资源（实测 200） |
| JPG 自动降档可能编码多次 | 每次 -5%、最多 10 次；4000×3000 一次 mozjpeg 编码约 0.5 s，极端情况会跑几秒 | 在 Worker 里跑（不冻页面），进度条与秒数照常；只降必要的次数（一旦变小就停） |
| 大 PNG 压缩耗时、页面像卡死 | 量化与 oxipng 都是 CPU 密集的**同步** WASM，单线程跑；1.1 MP 约 1 s，4.8 MP 约 3 s。放在主线程会冻住动画与交互 | 放进 Web Worker（`png-worker.ts`），主线程照常画进度；遮罩里给进度条 + 真实秒数 + 「不要关闭页面」提示；oxipng 级别取 2（量化后只需轻度收尾） |
| 调色板量化的画质代价 | 真彩 PNG 被压成 256/较少颜色的调色板，渐变色可能出现色带；透明边缘可能略有锯齿 | 质量滑杆默认 0.8（约 200 色）、最高 0.95（256 色）；「继续压缩」每次降一档时提示质量在下降；PNG 仍保留透明 |
| imagequant 的 wasm 在 Worker 里加载不了 | 包入口是 `import * as wasm from "./imagequant_bg.wasm"`（wasm-bindgen bundler 目标），打包器在 Worker 里解析不了，运行时会**一直停在压缩中**、无报错 | 只用它的 JS 胶水 `imagequant/imagequant_bg.js`，wasm 从 `public/codecs/imagequant_bg.wasm` 手动 `fetch + WebAssembly.instantiate`（它只从 JS 导入 2 个 wbindgen 函数），再 `__wbg_set_wasm` |
| 继续压缩没有尽头 | JPG 级联重编码会累积代际损失（每次都在上一代上再压） | 只在「更小」时提交；PNG 无损再压是幂等的，直接给结论；说明书里写清「继续压缩 = 在上一代结果上再压」 |
| 透明 PNG 转 JPEG 变黑底 | JPEG 没有 alpha 通道，透明像素被填成黑（或白） | 现在 PNG 一律输出 PNG（oxipng 无损优化），根本不经过 JPEG 编码器，这条坑不再存在；早先「探测 alpha 再决定输出 WebP」的那套代码已随方案一起删掉 |
| 连点开始压缩 / 编码途中改参数 | 每次编码都要重画一张 4000px 的图，排队会把主线程和内存拖垮 | 编码中按钮禁用（第一道）；回调里带自增序号，换图 / 改参数 / 连点都会让旧任务的结果被丢弃（第二道） |
| 结果与参数对不上（乱序） | `toBlob` 是异步的，连续多次调用返回顺序不保证 | 每次任务带自增序号，回调里序号不等于最新就直接丢弃结果 |
| 内存泄漏 | 每次重压都生成一个 object URL，不 revoke 会一直占内存 | 换图 / 重压 / 卸载时 `revokeObjectURL` 旧 URL（在 `useEffect` 清理函数里成对处理） |
| 手机上拖滑块时页面跟着滚 / 长按弹系统菜单 | 触屏默认把横向拖动当滚动；长按图片还会弹「存储图片 / 在新标签打开」 | 对比层 `touch-action: pan-y`（左右交给自己、上下留给页面）+ `select-none` + `-webkit-touch-callout: none`；交互只做「拖分割线」，不给图片本身绑长按 |
| 体积数字和 Finder 对不上 | Finder 用 1000 进制，本工具用 1024 进制，同一文件差约 5% | 文档与验收都以**字节数**为准（§六 第 3 条），界面上另给一行精确字节数；MB/KB 与字节是同一套 1024 口径，不并列两套单位 |
| 粘贴事件只在页面内有效 | `paste` 监听挂在 window 上，焦点在别的应用时不触发 | 文案写「在本页按 ⌘V」，不承诺系统级快捷键 |
| 换了图但预览还是旧的 | object URL 变了而 `<img src>` 复用了同一节点 | `<img key={url}>` 强制重建 |
| 白名单外格式的提示语 | 白名单判断看 MIME 或扩展名，两者都可能被「名字」骗过 | 改名成 `.jpg` 的 txt 会通过白名单、在解码时失败 → 报「你的浏览器打不开这个格式」，这个分工是有意的：格式不支持与文件坏了给不同提示 |
| HEIC 有时能开有时不能 | iOS Safari 原生解得了，桌面 Chrome 解不了 | **现在按白名单直接拒绝**，提示只支持 JPG / PNG——不再依赖「浏览器能不能解」这种平台差异 |
| 输出比原图还大 | PNG 无损，`toBlob` 忽略质量；把调色板 / 优化过的 PNG 用 canvas 重编码成真彩 PNG，体积反而涨（实测 6.9 MB → 9.3 MB）。JPG 在极高质量 + 小图时也可能涨 | 编码完先比字节数：**没变小就判定「压不动」**，结果区只说明原因，不生成下载、不出对比滑块（2026-10-30 联调）；绝不把更大的文件递给用户 |
| 批量一次触发多个下载会被浏览器拦 | 浏览器对「同一手势触发多次下载」有限制，可能只给第一个或弹权限提示 | 批量给「逐张下载」+「下载全部（ZIP）」两个出口，ZIP 由 `<a download>` 一次触发；ZIP 用 store 模式自己写（待打包的已经是压缩产物，再 deflate 没收益） |
| 批量把内存顶满 | 十几张 4000×3000 的图同时解码 + 编码，内存会炸；ZIP 打包还会把全部结果再读进内存拼一遍 | 串行压缩 + 准入上限（30 张 / 200 MB）；换批 / 清空 / 卸载时逐个 revoke；ZIP 的峰值是「压缩后总量 × 2」，上限内可接受 |
| 只在 Chromium 内核上做过完整验收 | Playwright/CDP 跑的是 headless Chromium；Firefox / Safari 没有真机回归，`OffscreenCanvas`、WASM、`<a download>` 的行为可能有差异 | 关键 API 都做了存在性判断与失败提示；发版后建议在 Safari / 微信内置浏览器各点一次单张 + 批量；iOS 上 ZIP 若被当成预览打开，逐张下载仍可用 |
| 批量压缩到一半改参数 / 清空 | 循环还在跑，结果会写进已经重置的列表：前几张旧质量、后几张新质量，甚至给已删除的行创建 object URL 再也释放不掉 | 每次列表/参数变化递增 `runId`：循环在每个检查点比对，过期就整轮退出；创建 URL 前再确认这一行还在；结果与 URL 一起随行替换 |
| 服务端组件里用了浏览器 API | `page.tsx` 是服务端组件，`document` / `canvas` 不存在 | 所有 DOM 操作只写在 `"use client"` 的视图组件里；页面只做 `requireUser()` 与渲染 |

## 八、依赖变更

无。压缩用浏览器原生 `createImageBitmap` / `canvas` / `toBlob`，图标用已装的 `lucide-react`（`Image`, `ImageUp`, `Download`, `Loader2`）。

（项目规则：任何新依赖必须先登记进《技术栈说明》，再安装。）
