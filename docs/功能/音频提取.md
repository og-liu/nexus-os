# 音频提取

| 状态 | 开始日期 | 最近更新 |
|---|---|---|
| 🚧 设计中 | 2026-11-02 | 2026-11-02 |

> 一句话：把一个视频丢进来，把里面的音轨**原样**拿出来给你——能拷就拷（无损、几秒、体积不变），只有容器放不下的时候才转一次码。
> 这是「媒体」分类的第一个工具，也是全站第一个**在服务器上处理文件**的工具。

---

## 一、要什么

**做：**

- 工具页 `/tools/audio-extract`，分类「媒体」，工具目录与页签栏各登记一处
- **一个视频进、一个音频出**：拖入 / 点选一个视频 → 点「提取音频」→ 等几秒 → 下载
- **输出规则：能拷就拷**。按**源音轨的编码**决定输出容器，不按输入文件的扩展名猜：

| 源音轨编码 | 输出文件 | 处理方式 | 界面标注 |
|---|---|---|---|
| AAC | `.m4a` | 流拷贝，一次解码都不做 | 无损提取 |
| MP3 | `.mp3` | 流拷贝，一次解码都不做 | 无损提取 |
| ALAC | `.m4a` | 流拷贝，一次解码都不做 | 无损提取 |
| FLAC | `.flac` | 流拷贝，一次解码都不做 | 无损提取 |
| Opus / Vorbis / AC3 / E-AC3 / DTS / AMR / 其它 | `.m4a`（AAC 192 kbps） | 转码一次 | 已转为 AAC |

- **单文件上限 500 MB**，一次一个文件，不批量
- **不落库、不留存**：服务器只用一份临时文件，响应结束立刻删除
- 失败要说人话：没有音轨 / 超过上限 / 不是视频 / 打不开
- 三档响应式各自一套版式（§2.2）

**主动放弃（本版不做，不是遗漏）：**

| 放弃项 | 原因 |
|---|---|
| 「转成 MP3」的开关 | 2026-11-02 需求定稿时定的：主人要的是「无损提取」。MP3 是有损格式，从 AAC 转过去必然是解码再编码——一首 4 分钟的歌，无损提取是 4 MB / 2 秒，转 MP3 变成 7 MB / 10 秒，质量还退一代。能无损就不给这个开关 |
| 只提取某一段（填开始 / 结束时间） | 他要的是「比剪映的音频分离更简单」：整段提取，不引入时间轴与区间校验 |
| 批量 | 音频提取是一次性动作；批量会拖出队列、并发控制、逐个清理三套东西 |
| 试听 / 波形预览 | 提取完下载到本地听，比在网页里解码播放更快；音频不进浏览器内存，也不用为它引解码器 |
| 多音轨选择 | 有多条音轨时只取第 1 条（`-map 0:a:0`）。真实场景几乎全是单音轨，加选择器等于为一个几乎不存在的情况造一套 UI |
| 提取历史 / 结果留存 | 结果直接下载走；留历史就要建表、定清理策略，而这个工具的价值就是「过一下就完」 |
| 客户端处理（ffmpeg.wasm / 浏览器解封装） | 见 §四第 1 条 |

## 二、界面

### 2.1 工具页 `/tools/audio-extract`

与图片压缩同构：**没有 PageHeader**，工具名与状态在内容区的信息条里（`ToolHeader`，状态点「可用」）；手机上顶部是 `ToolMobileBar`（汉堡 + 「选择视频」，图标 `FileVideo`）。

```
移动端导航行（< lg）：汉堡 + 选择视频
内容区（px-4 py-4 md:px-6 md:py-6 space-y-4）
├─ 工具信息条（ToolHeader，状态「可用」）
└─ 工作区
   ├─ 主区（左 / 上）
   │   ├─ 空态：拖入区（虚线框 + 图标 + 三行提示）
   │   ├─ 已选中：文件卡（文件名 · 体积 ·「换一个」）+ 通栏黑底「提取音频」
   │   └─ 进行中：文件卡上盖进度层（上传 N% → 提取中 + 已用秒数）
   └─ 结果区（右 / 下）
       ├─ 空：虚线说明「提取完成后，这里出现下载按钮」
       ├─ 成功：源音轨编码 + 无损 / 已转码 + 时长 + 输出体积 + 通栏「下载音频」
       └─ 失败：虚线框 + 一句人话 + 「换一个视频」
```

颜色与控件一律照《界面设计规范》：虚线框 `rounded-[2px] border border-dashed border-[#D9D9D9] bg-white`，主按钮黑底直角（§7.3），空态文案用 `text-[#A0A8B4]`。

### 2.2 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列纵向：拖入区 → 文件卡 → 提取按钮 → 结果卡 | 提取按钮通栏、触控高度 `h-11`；空态内边距收到 `p-8`；结果卡紧跟按钮，不再单独占一屏 |
| 平板 md ~ lg（768–1023） | 单列，但「文件卡」与「结果卡」并排两列（`md:grid-cols-2`） | 提取完结果就出现在右边，不用往下滑；空态占满整行 |
| 窄屏 PC lg ~ xl（1024–1279） | 两栏：主区 `flex-1` + 右栏 `w-[300px]` | 右栏固定结果与「能无损就无损」的规则说明，改文件不用上下滚 |
| 宽屏 ≥ xl（1280） | 两栏：主区 `flex-1` + 右栏 `w-[340px]` | 内容区 `max-w-[1360px]` 居中，空态垂直居中于首屏 |

- 两栏的切换点是 **lg**（栏位方向属于结构性布局，《界面设计规范》§六）。
- 三档用互斥显隐（`hidden lg:grid` / `lg:hidden`），不用 JS 读视口——首屏 SSR 不闪。
- 断点的实际高度**实现时在真机上量**，不许手算（踩过：`calc()` 里手填常量，1440×900 下内容被压成一条缝）。

### 2.3 状态与边界

| 状态 | 界面 |
|---|---|
| 初始 | 虚线拖入区：`Upload` 图标 +「把一个视频拖到这里」+「或者点击选择文件」+ 小字「MP4 / MOV / MKV / AVI / WEBM / TS 等，单个不超过 500 MB」；「提取音频」置灰 |
| 已选中 | 文件卡：文件名（过长中间截断）+ 体积 +「换一个」；「提取音频」可点 |
| 上传中 | 文件卡上盖进度层：`Loader2` +「正在上传 42%」+ 进度条；按钮禁用 |
| 提取中 | 同一层换文案「正在提取音频…」+ 已用秒数（`3 秒`）；**不给假进度条** |
| 完成 | 结果卡：`源音轨 AAC` +「无损提取」+ `03:42` + `5.2 MB` + 通栏「下载音频」 |
| 已转码 | 结果卡：`源音轨 Opus` +「已转为 AAC」+ 时长 + 体积 |
| 没有音轨 | 结果区虚线框：「这个视频没有声音」+「文件里没有音轨，换一个试试」+「换一个视频」 |
| 不是视频 | 选中即拒（Toast）：「只支持视频文件」——进不了文件卡 |
| 超过 500 MB | 选中即拒（Toast）：「超过 500 MB」——不发起请求 |
| 打不开 | 结果区虚线框：「这个视频打不开」+「文件可能损坏，或者编码 ffmpeg 认不出来」 |

## 三、数据模型

**不涉及。** 视频与音频都不进数据库、不在服务器留文件：唯一的磁盘痕迹是提取期间的一份临时文件，响应结束即删（§四）。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 在哪跑 | **服务器上的 ffmpeg**（Route Handler 里 spawn 子进程） | 输入是一个**容器**（mp4 / mkv / ts / mov …），要从里面取出音轨，浏览器没有任何 API 能做；ffmpeg 一条命令就完成 | ffmpeg.wasm（首次加载约 30 MB、单线程慢十倍、文件要整个塞进 32 位地址空间，真 MV 直接内存墙）；浏览器里用 mp4box.js 手工解封装（只认 mp4 / mov，mkv / avi / ts 全废） |
| 二进制从哪来 | **npm 包 `@ffmpeg-installer/ffmpeg`**（二进制随平台子包一起发布） | ① CI 构建时二进制就进了产物，服务器**不需要联网装包**；② 版本跟着 `package.json` 走，回滚就是回滚依赖；③ 本地（macOS arm64）与线上（linux-x64）各取对应平台包，同一份代码两边都能跑 | `dnf install ffmpeg`（**实测：Alibaba Cloud Linux 3 + 已启用的 EPEL 8 源里没有 ffmpeg 包**）；下载静态包手工放服务器（脱离发布流水线，换机器就丢）；RPM Fusion（境外源，国内服务器基本不可用） |
| 默认输出什么 | **能拷就拷**：按源音轨编码选容器（§一 的表） | 「提取」的正确语义是把音轨搬出来，不是重新编码；拷贝路径一次解码都不做，几秒完事，体积与质量都与源一致 | 一律转 MP3（白丢一代音质、多等十几秒、体积更大——2026-11-02 需求阶段专门讨论并放弃） |
| 转码什么时候发生 | 只在源编码放不进播放友好的容器时（Opus / AC3 / AMR 等） | 这类编码塞进 `.m4a` 大多数播放器不认，转成 AAC 才是「拿回去能听」 | 原样输出 `.opus`（安卓能放，Windows 与部分车机不能放，用户会以为文件坏了） |
| 单文件上限 | **500 MB** | MV 通常 50–200 MB；服务器磁盘 33 GB 可用，500 MB 峰值安全 | 不设上限（一个 4 GB 文件能把磁盘与上传时间一起拖垮）；100 MB（长一点的 1080p 视频就超） |
| 上传怎么进服务器 | **请求体直接流式写进临时文件**；`Content-Length` 超限立刻 413，边写边累计字节数 | 服务器内存只有 1.8 GB，把 500 MB 读进内存会让整个 Next 进程被系统杀掉——连带所有页面一起挂 | `await request.arrayBuffer()`（最省事，正是上面那个后果）；`multipart/form-data`（要额外解析器，流式解析更麻烦；单文件用 `application/octet-stream` + 文件名走自定义请求头就够） |
| 临时文件怎么清 | 请求结束（含异常路径）`unlink`；每次请求开头顺手删掉目录里超过 1 小时的孤儿 | 进程被杀这类情况 `finally` 不会执行；一条扫描把累积的孤儿收掉，不需要常驻定时任务 | 定时任务清理（为一个私人工具多一个常驻进程）；不清理（磁盘迟早被占满） |
| 返回方式 | ffmpeg 写临时文件 → 以流式响应回给浏览器 → 流结束后删 | 浏览器拿到的就是文件本身，不需要再发一次「取结果」请求 | 生成一个可下载 URL 让前端再取一次（多一次请求，多一个生命周期要管） |
| 进度给到几分 | 上传阶段给真实百分比；提取阶段只给「已用秒数」 | 上传是浏览器知道的（XHR 的 `upload.onprogress`），提取是服务器黑盒；编个假进度条比不给更糟 | 服务端把 ffmpeg 的 `-progress` 转发给浏览器（要 SSE + 两段式接口，为一个几秒的操作用不上） |
| 并发 | **不排队**：前端按钮锁死，服务器不设队列 | 私人工具，两个请求同时来的概率极低；真撞上就是 2 核各跑一半，慢一点但不崩 | 进程内队列（多一套状态与超时，收益为零） |
| 鉴权 | 页面 `requireUser()` **加**接口二次校验 | 接口能被直接 POST，页面鉴权管不住它；这个接口吃 CPU 与磁盘，必须自己确认是登录用户 | 只靠页面（等于把上传接口敞开） |
| 输出文件名 | 源文件名去扩展名 + 新扩展名；路径分隔符与非法字符换成 `-` | 抖音下载的文件名常带 emoji、井号、空格；直接用会拼出坏路径或被截断 | 固定 `download.m4a`（用户下载一堆同名文件，分不清哪首是哪首） |

## 七、已知的坑

| 坑 | 机制与对策 |
|---|---|
| Nginx 默认只放行 1 MB 请求体 | `client_max_body_size` 默认 **1 MB**，任何真视频都是 413，且返回的是 Nginx 的 HTML 错误页——前端 `.json()` 直接抛。对策：`deploy/nginx/nexus-os.conf` 加 `client_max_body_size 520m;`，前端把 413 也翻译成「文件太大」 |
| **`ffmpeg` 必须带 `-nostdin`** | 子进程没有 TTY 时 ffmpeg 会读 stdin 做交互（问是否覆盖），于是**永远不返回**，接口挂到超时。对策：所有调用都带 `-nostdin -y` |
| 用 `ffmpeg -i` 探测时退出码是 1 | 只给输入不给输出时，ffmpeg 打印完流信息就以非 0 退出。对策：探测那一步**不按退出码判失败**，按 stderr 里有没有 `Audio:` 判 |
| 容器与编码不匹配 | AAC 塞进 `.mp3` 写不了头（`Could not write header`），报错看着像文件坏了。对策：`plan-output` 按**源编码**选容器，不按输入扩展名 |
| 裸 `.aac`（ADTS）不要用 | 没有时间戳，部分播放器拖动进度条会错乱。对策：AAC 一律装进 `.m4a` |
| Next 的 standalone 产物不会自动带上 `node_modules` 里的二进制 | 发布包里没有 `ffmpeg`，本地能跑、线上 `spawn ENOENT`。对策：`next.config.ts` 里 `outputFileTracingIncludes` 把 `node_modules/@ffmpeg-installer/**` 打进 `/api/tools/audio-extract` 路由 |
| `@ffmpeg-installer` 被打包器内联 | 它靠 `require` 定位 `node_modules/.../ffmpeg`，一旦被合进 chunk，路径就指向产物内部。对策：`serverExternalPackages: ["@ffmpeg-installer/ffmpeg"]`，与上一条一起配 |
| 响应流没读完就删临时文件 | 用户下到一半的文件被截断。对策：在响应流的 `close` / `finish` 之后再 `unlink`，不要在 `finally` 里提前删 |
| 中文文件名 | `Content-Disposition` 的中文要按 RFC 5987 写成 `filename*=UTF-8''…`，否则浏览器存下来是乱码或 `download` |
| 不要把文件交给 shell | `spawn("ffmpeg", args)` 直接传数组，不要 `exec` 拼字符串——文件名里有引号或空格就会被当成命令的一部分 |
| 前端 `accept` 不是强制 | 用户可以选任意文件，iOS 还会给 `video/quicktime` 或空 MIME。对策：MIME 或扩展名任一命中白名单即放行，真正认不出的交给服务器报「打不开」 |
| `proxy_request_buffering` 默认开着 | Nginx 会把 500 MB 先落盘再转发给 Node，等于写两遍磁盘、还慢一拍。对策：这个 location 加 `proxy_request_buffering off;` |
| 转码时忘了剥掉其它流 | 视频、字幕、章节流混进音频文件会让 ffmpeg 报错或产出奇怪的东西。对策：`-vn -sn -dn -map 0:a:0` 只留第一条音轨 |
