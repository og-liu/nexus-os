# 登录注册

| 状态 | 开始 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-10-15 | 2026-10-15 |

> 一句话：让用户拥有一个**属于本系统自己的账号**——用户以「用户名 + 密码」注册并登录，登录后才能进入应用。

---

## 一、要什么

**用户以「用户名 + 密码」注册并登录，登录后才能进入应用。**

做：

- 注册（用户名 + 密码 + 确认密码）
- 登录、登出
- 登录态校验：每次请求都能确认「你是谁」
- 一个受保护页面（首页），未登录时跳转登录页
- 登录失败限流：防止密码被在线暴力试凑

不做（第一版主动放弃，不是遗漏）：

| 放弃项 | 原因 |
|---|---|
| 找回密码 / 改密码 | 没有邮箱手机号就没有自助通道；忘记密码由管理员直接改库。这是**主动放弃**的代价 |
| 邮箱 / 手机号 | 发信、发短信才是真正的外部依赖，会引入持续成本与资质审核 |
| 第三方登录（微信 / GitHub） | 微信开放平台要企业主体 + 300 元/年认证 + 已备案域名；且 OAuth 的核心机制与本地登录不是一回事，复杂度高出一档 |
| 记住我 / 多设备管理 / 角色权限 | 第一版不需要 |

## 二、界面

| 路由 | 页面 | 要点 |
|---|---|---|
| `/login` | 登录页 | 用户名、密码、提交按钮、错误提示、去注册的链接 |
| `/register` | 注册页 | 用户名、密码、确认密码 |
| `/` | 首页（受保护） | 未登录跳 `/login`；登录后直接看到应用第一屏（当前是 Hello world 占位），右上角一枚次要的「退出登录」 |

注册成功与登录成功都直接进入 `/`。反过来，**已登录时访问 `/login` 或 `/register` 直接跳回 `/`**——检查写在两个页面里，不写在 `(auth)/layout.tsx`（理由见第四节）。

## 三、数据模型

本功能新增两张表：`users`（账号）与 `sessions`（登录会话）。

**表结构、每个字段的含义与理由、索引、列命名约定 → 全部在《数据库设计》**（§2.1 / §2.2）。表结构以那份文档为唯一权威，本文不重复；数据层的通用规矩（幂等建表、加列的迁移方式、排序补 `rowid`）也在那里，选型与连接配置见《技术栈说明》§3.5。

本功能与数据有关的取舍见下一节（会话形态用数据库会话而不是 JWT、密码用 scrypt 而不是 md5 等）。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 自己写 vs 用现成库（Auth.js / NextAuth） | **自己写** | 本项目是学习项目，用库会把「会话怎么建、密码怎么存」整个藏进黑盒；本版需求简单，手写代码量可控 | Auth.js（否决：省掉了正是要学的部分。将来需要多 provider、MFA、角色权限时再评估） |
| 会话形态 | **数据库会话** | 可随时撤销、可查活跃会话 | JWT / 加密 cookie（否决：无法即时登出） |
| 表单提交方式 | **Server Actions + `useActionState`** | Next 官方推荐做法；天然支持无 JS 降级；函数只在服务端执行，密钥与数据库不经过浏览器 | 自建 `/api/auth/*` 接口 + `fetch`（否决：多一层手工接线，本版无此必要） |
| 路由保护放在哪 | **受保护页面自己校验**（页面里读会话，无则 `redirect('/login')`） | Next 16 官方文档明确：Proxy 只能做「乐观检查」，**不能**当作完整的会话与授权方案；且 Proxy 跑在 Edge 运行时，读不了本地 SQLite | 用 `proxy.ts` 兜住全部（否决：官方不建议，且查不了库，只会造成「假安全」） |
| 登录失败提示 | **统一提示「用户名或密码不正确」** | 若分开提示「用户不存在 / 密码错误」，等于给攻击者一个免费的用户名探测器 | 精确提示（否决：泄露账号是否存在） |
| 业务代码放哪 | **逻辑进 `src/lib/auth/`**，`src/app/` 只留页面与接线 | 遵守《项目目录结构说明》的分层红线 | 逻辑写进页面（否决：违反红线） |
| 已登录访问 `/login`、`/register` | **页面里检查，有会话就 `redirect('/')`** | 已登录再看到登录页没有意义，也容易被当成「登录没生效」 | 放在 `(auth)/layout.tsx` 里（否决：Next 16 文档明确 layout 在客户端导航时不重新渲染，拦不住子页面；检查要贴着路由本身） |
| 登录后回跳到原页面（`?next=`） | **不做** | 本版只有一个受保护页，收益为零；而回跳参数是开放重定向的经典入口，校验成本大于价值 | `?next=` / `?from=` 回跳（否决：多一个必须校验的参数面） |
| 会话有效期 | **30 天**，cookie `maxAge` 与库中 `expires_at` 一致 | 个人工作空间，30 天内不必重复登录；两处取值必须同源，否则会出现「莫名其妙掉线」 | 7 天 / 永久（否决：前者过短，后者无法回收） |

### 输入校验规则（实现阶段定稿）

界面静态阶段只定了密码长度，用户名的规则一直是空的。实现必须给服务端一个确定的答案，故在此定稿：

| 字段 | 规则 | 理由 |
|---|---|---|
| 用户名 | 长度 3–20；只允许**汉字、字母、数字、下划线、连字符** | 允许汉字是给中文用户的实际便利（归一化只影响大小写，不影响汉字）；排除空格与符号，避免出现「看不见的账号」 |
| 密码 | 长度 8–128 | 下限 8 位是本文档已定的规则；上限 128 是防滥用——scrypt 的开销与长度无关，但允许上传 1 MB 「密码」就是白送一次哈希计算 |
| 确认密码 | 必须与密码一致 | 服务端也要校验，不能只靠浏览器 |

校验是**纯函数**（`validate.ts`），前端提示与服务端拒绝共用同一份规则，避免两边不一致。

## 五、文件落点

```
src/
├── lib/
│   └── auth/
│       ├── db.ts            # 连接与建表（生产库与测试库共用同一份 schema）
│       ├── password.ts      # 哈希与校验
│       ├── session.ts       # 会话记录增删查（纯函数：只碰数据库，不碰 cookie）
│       ├── user.ts          # 用户查询与创建
│       ├── current-user.ts  # 请求级封装：读写 cookie、取当前用户、requireUser / requireGuest
│       ├── validate.ts      # 输入校验规则（纯函数）
│       ├── rate-limit.ts    # 登录失败限流
│       └── actions.ts       # Server Actions（'use server'）
├── app/
│   ├── (auth)/
│   │   ├── login/page.tsx
│   │   └── register/page.tsx
│   └── page.tsx             # 改为受保护首页
└── components/
    └── auth/
        ├── login-form.tsx   # 'use client'
        └── register-form.tsx
```

`session.ts` 与 `current-user.ts` 为什么要分成两个文件：**前者是纯数据库逻辑，后者依赖 `next/headers`**。单元测试要驱动「会话能建、能查、篡改后失效、登出后删行」，如果这些函数和 `cookies()` 长在一起，测试就得伪造一个请求环境；拆开后测试拿内存库直接调前者即可，后者留给真实请求。

首页**不在 `(auth)` 分组里，也暂不建新的路由分组**：应用外壳（侧边栏 / 页头 / 页脚）还没实现，等它落地时再决定受保护页面归到哪个分组——现在就建一个空分组属于提前布局，多一个没人用的目录。

## 六、验收标准

实现完成后逐条实测：

| # | 操作 | 期望 |
|---|---|---|
| 1 | 未登录访问 `/` | 跳转到 `/login` |
| 2 | 注册 `alice` / `12345678` | 自动登录并进入 `/`，显示 `alice` |
| 3 | 刷新页面 | 仍处于登录状态 |
| 4 | 再注册 `Alice` | 被拒绝，提示用户名已被使用 |
| 5 | 用 `alice` + 错误密码登录 | 提示「用户名或密码不正确」 |
| 6 | 用不存在的用户名登录 | 提示与 #5 **完全一致** |
| 7 | 密码填 7 位去注册 | 被拒绝，提示长度要求 |
| 8 | 手动改掉 cookie 中一个字符后刷新 | 会话失效，回到登录页 |
| 9 | 点「退出登录」后再访问 `/` | 跳登录页；数据库中该会话行已删除 |
| 10 | 连续输错密码超过阈值 | 被临时锁定，提示稍后再试 |
| 11 | 直接翻数据库 | `password_hash` 列看不到任何明文；同一密码在两个账号中的哈希不同 |
| 12 | 已登录状态下访问 `/login` 或 `/register` | 直接跳回 `/`，看不到表单 |
| 13 | `pnpm typecheck` / `pnpm lint` / `pnpm test` | 三项全绿 |

单元测试覆盖：密码哈希与校验（同一密码两次哈希不同、错误密码不通过、畸形哈希不抛未捕获异常）、校验规则、会话生命周期（用内存数据库）。

## 七、已知的坑

| 坑 | 说明与对策 |
|---|---|
| `cookies()` 在 Next 16 是**异步**的 | 必须 `await cookies()`，旧写法已不适用 |
| Server Component 里**不能**写 cookie | 只能读。写（`.set` / `.delete`）只允许在 Server Action 或 Route Handler 中进行 |
| `redirect()` 靠**抛异常**实现跳转 | 若写在 `try/catch` 里会被 catch 吞掉，表现为「点了没反应」。要在 try 之外调用，或识别出重定向错误后原样抛出 |
| scrypt 的默认内存上限 | `crypto.scrypt` 默认 `maxmem` 为 32 MB，而所需内存约为 `128 × N × r` 字节。本项目 N=16384、r=8 时约 16 MB，安全；一旦把 N 调高到 2^15 以上就必须显式传 `maxmem`，否则直接抛错 |
| better-sqlite3 是原生模块 | 必须加入 `next.config.ts` 的 `serverExternalPackages`，否则打包后运行时加载失败 |
| 生产是 `output: "standalone"` | 运行时目录与项目根不同，数据库文件**不能靠相对路径推导**，须由环境变量（如 `DATABASE_PATH`）指定，本地与线上各配一份 |
| 开发模式热重载 | 数据库连接要挂在 `globalThis` 上复用，否则每次热更新都新建连接、句柄泄漏 |
| 限流是进程内计数 | 当前阈值：**15 分钟窗口内连续失败 5 次 → 锁 15 分钟**，按「用户名 + IP」两把钥匙各记一份，任一被锁即拒绝（成功登录后清零）。锁定期内**连哈希都不算**，否则限流只是「慢速暴力破解」。进程重启即清零，且只在单实例下准确；当前部署形态（单机单进程）够用，将来多实例需换成共享存储 |
| 未知用户名必须也走一次哈希 | 「用户名不存在就提前返回」会让失败响应明显更快——统一提示文案挡不住这种**时序泄漏**。对策：拿一个固定的「陪跑」哈希把校验走完（`actions.ts` 的 `getDummyHash()`） |
| `'use server'` 文件**只能导出 async 函数** | 导出状态**类型**没问题（类型在编译期就被抹掉），但导出**对象常量**会在构建期直接报错。表单的初始状态因此各自定义在客户端组件里 |
| 校验规则必须前后端同源 | 前端提示与服务端拒绝若各写一套，迟早出现「浏览器放过了、服务端却拒绝」。规则只写在 `validate.ts`，两边都取自它 |
| 用户名首尾空白会被裁掉 | 「 alice 」与「alice」是同一个账号（归一化前先 `trim`）；中间的空格仍然拒绝。这是有意的，不是漏了 |
| 单元测试跑的是纯逻辑，不是页面 | 会话逻辑与 cookie 读写分家（`session.ts` / `current-user.ts`），否则测试得伪造请求上下文。页面级行为靠第六节验收表实测，不靠单测 |
| 服务端返回的错误是**上一次提交的快照** | `useActionState` 只在提交后更新状态，用户改了输入它也不会自己消失——「把 7 位密码改成 8 位，提示还挂着」就是这么来的。对策：字段被编辑后隐藏该字段的旧错误、任意字段被编辑后隐藏表单级错误，提交时清空（`src/hooks/use-dirty-fields.ts`）。**浏览器端校验只能改善体验，服务端仍然每次都重新校验** |

### 附：密码与登录态的实现原理

**密码怎么存** —— 用 Node 内置的 `crypto.scrypt`，不引入任何第三方加密库。存进库的是一个**自描述**字符串：

```
scrypt$16384$8$1$<salt-base64>$<hash-base64>
  算法   N   r p   随机盐 16 字节     派生密钥 64 字节
```

- 每个账号注册时生成**独立的随机盐**，因此同一个密码在两个账号里的哈希完全不同——彩虹表与撞库比对失效。
- 参数写进字符串本身，将来调整参数或更换算法时，老密码仍能按它自己的参数校验通过，可以逐个平滑升级。
- 校验用 `crypto.timingSafeEqual`，不用 `===`。`===` 会在第一个不同的字节处提前返回，理论上可被逐字节试探出正确值（时序攻击）；`timingSafeEqual` 耗时恒定。
- 为什么不能用 `md5` / `sha256`：它们**设计目标就是快**，现代显卡每秒能算几十亿次，密码库泄露后暴力破解只是时间问题。scrypt 是**故意慢且吃内存**的算法，把每次尝试的成本抬高几个数量级——慢，在这里正是功能。

**登录态怎么维持** ——

```
注册/登录成功 → 生成 32 字节随机 token
              → cookie 存 token 原文（httpOnly），数据库存 sha256(token)
每次请求      → 读 cookie → sha256 → 查 sessions 是否有效且未过期 → 得到用户
退出登录      → 删除数据库对应行 + 清除 cookie（立刻失效）
```

| Cookie 属性 | 取值 | 作用 |
|---|---|---|
| `httpOnly` | `true` | 浏览器 JS 读不到，XSS 也偷不走 |
| `sameSite` | `lax` | 跨站请求不携带该 cookie，挡掉大部分 CSRF |
| `secure` | **由环境变量控制**，上了 HTTPS 再打开 | 只经 HTTPS 传输。当前线上还是 HTTP，若现在写死 `true`，浏览器会直接丢弃这个 cookie，表现为「登录成功但一刷新就掉线」 |
| `path` | `/` | 全站生效 |
| `maxAge` | 30 天 | 与数据库 `expires_at` 保持一致 |

为什么不用 JWT（无状态会话）：token 一旦签发就无法撤回，用户点「退出登录」也只是删掉浏览器本地的那份副本，若副本已被复制走仍然有效。数据库会话每次请求多一次查询，换来**随时可撤销**——数据库就在同一个进程里，这次查询的代价可以忽略。
