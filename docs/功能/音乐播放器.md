# 音乐播放器

| 状态 | 开始日期 | 最近更新 |
|---|---|---|
| ✅ 已完成 | 2026-11-03 | 2026-11-03 |

> 一句话：把自己的音乐文件传上来，攒成一份只属于自己的曲库，在站点里点开就能听。
> 「媒体」分类的第三个工具，也是全站第一个**需要持久文件存储**的工具。
> 首页还有一块「正在播放」卡，是同一个播放器的遥控器，不是第二个播放器。

---

## 一、要什么

**做：**

- 工具页 `/tools/music-player`，分类「媒体」，工具目录与页签栏各登记一处
- **上传（多选）**：拖入或点选一批音频文件，串行逐个上传，每条显示进度与结果
- **曲库列表**：歌名 / 歌手（有就显示）/ 时长 / 体积 / 上传时间，点一行就开始播
- **曲目编辑**（2026-11-03 追加）：每首歌都能改歌名、歌手，并勾选它属于哪些歌单
- **歌单**（2026-11-03 追加）：建歌单、改名、删歌单；把歌加进歌单 / 从歌单移除；点歌单只看该歌单里的歌，播放队列也跟着切
- **删除**：曲库里的歌能删掉（连磁盘文件一起删）
- **批量操作**（2026-11-03 追加）：列表头「批量」进入选择模式，每行变成复选框，可选多首一次删掉、或一次加进某个歌单；带全选 / 取消全选
- **播放**：上一首 / 下一首 / 播放暂停 / 拖动进度 / 音量 / 顺序与随机
- **切页面歌不停**：全站只有一个真正的播放器，挂在应用外壳上；从首页点进工具页、再点去保险库，歌一直在放
- **首页「正在播放」卡**：形态照旧原型（黑胶 + 歌名 + 进度 + 三按钮），内容接真实播放状态
- **右下角悬浮球**（2026-11-03 追加）：一颗黑圆 + 白色 Logo 的球，固定在右下角，**去哪个页面都跟着**；点一下向上弹出小播放面板，随手就能暂停 / 切歌
- **手机锁屏控制**：Media Session，锁屏 / 耳机线控能看到歌名并能切歌
- 空曲库时说人话，并给一个「去添加」的出口
- 三档响应式各自一套版式（§2.2）

**主动放弃（本版不做，不是遗漏）：**

| 放弃项 | 原因 |
|---|---|
| 歌单 / 收藏夹 | ~~不碰~~ **2026-11-03 推翻，已实现**。当时的判断是「曲库够小的时候整库顺序播就是歌单」——曲目攒到几十上百首之后这条不成立了：想听某一类歌只能从头翻。现在的做法见 §2.1 的「歌单栏」，多对多、不复制歌曲 |
| 歌单内拖拽排序 | ~~不碰~~ **2026-11-03 推翻，已实现**。当时的判断是「加入时间已经能表达顺序」——真正用起来才发现，脑子里想的顺序（先放主打、再放尾声）跟加进来的顺序完全对不上。现在曲库和歌单都能拖，顺序落在 `position` 列（§2.1.5） |
| 歌单封面 / 描述 | 第一版没有图片与富文本的需求；封面还要多一套上传与裁剪 |
| 曲库搜索 | 同上：几十首用滚轮比搜索快。搜索框一旦存在，键盘焦点、空结果、高亮都得跟着做 |
| 在线搜歌 / 抓第三方音乐平台 | 版权与反爬双重问题：国内平台的接口要么要登录态、要么随时改签名，做出来也是一周就坏的工具 |
| 转码 / 统一格式 | 要是有损转码，音质掉一代还占双倍 CPU；原样存，收的范围就是浏览器原生能放的格式（§四第 2 条） |
| 封面 / 歌词 | 封面要从文件里提内嵌图并另存一份，歌词要时间轴对齐——两件都是「有更好、没有也能听」的事 |
| 重命名 / 编辑元数据 | ~~不碰~~ **2026-11-03 推翻，已实现**。当时的判断是「上传前在本地把文件名改好更符合直觉」——实际上传完之后才发现标签写错了（专辑名塞进 title、歌手为空）才是常态，而重新上传要再传一遍几百 MB。现在点行尾的铅笔就能改歌名 / 歌手 / 所属歌单（§2.1.1） |
| 播放进度记忆 | ~~不碰~~ **2026-11-03 推翻，已实现**。当时的判断是「重开从头放就行，存进度还要想多设备冲突」——用起来才发现这是个真实需求：刷一下页面就回到 0，跟原生音乐 App 差得太远。现在一人一行存在服务端（`music_playback`），刷新 / 换设备都能接上（§2.1.6） |
| 单曲循环 | 顺序与随机之外再加一档，模式按钮就要点三下才循环。真需要时再加 |
| 统计 / 听歌排行 | 没有消费场景的统计只是数字 |

## 二、界面

### 2.1 工具页 `/tools/music-player`

没有 PageHeader，工具名与状态在 `ToolHeader` 里（状态点「可用」）；手机上顶部是 `ToolMobileBar`（汉堡 + 「添加音乐」）。

```
内容区（px-4 py-4 md:px-6 md:py-6）
├─ 工具信息条（ToolHeader）
└─ 工作区
   ├─ 顶部播放条（通栏）：当前歌名 · 进度条（可拖）· 时间 · 上一首/播放暂停/下一首 · 模式 · 音量
   └─ 三栏（≥ xl）
      ├─ 左：歌单栏
      │   ├─ 「全部歌曲」+ 曲库总数
      │   ├─ 每条歌单：名字 · 曲目数 · hover 出「改名 / 删除」
      │   └─ 底部「+ 新建歌单」
      ├─ 中：曲目列表
      │   ├─ 表头「<当前范围>」+ 右侧「N 首 · 已用 X / 5 GB」+「添加歌曲」（仅歌单）+「批量」
      │   ├─ 批量模式下：「已选 N 首」+「全选 / 取消全选」+「加入歌单」「删除（N）」「取消」
      │   └─ 每行：播放态指示 | 歌名 + 歌手 | 时长 | 体积 | 上传时间 | hover 出「编辑 / 删除」
      └─ 右：上传区 + 配额
```

- 点列表里的一行 = 立刻播这一首。**点正在播的那一行 = 暂停 / 继续**（不是「什么也不发生」）：在「全部歌曲」里点 → 队列是全库；在某个歌单里点 → 队列就是那个歌单（顺序 / 随机都只在队列内走）
- 正在播的那一行左侧显示跳动的等化器图标，不是序号
- 行尾两个图标（hover 才显形）：**编辑**（弹框改歌名 / 歌手 / 所属歌单）、**删除**（点一下直接删，不确认——歌能重传）
- **批量模式**（点表头右侧「批量」进入）：
  - 每行左侧换成复选框，**点整行 = 勾选/取消，不再触发播放**（这个模式下唯一的行为改变，界面上要有「退出」随时能回去）
  - 表头：「已选 N 首」+「全选 / 取消全选」+「加入歌单」（下拉选一个歌单，把选中的歌都加进去）+ 红字「删除（N）」+「取消」
  - 点「删除」弹 `ConfirmDialog`（一次删多首，误触代价比单删大）；确认后一串删完、退出批量模式
  - 切页面 / 刷新后批量模式自动结束（它是临时态，不落库、不进 URL）

### 2.1.1 编辑弹框

```
┌ 编辑歌曲 ────────────────────────┐
│ 歌名   [ 晴天                    ] │
│ 歌手   [ 周杰伦                  ] │
│ 所属歌单                            │
│   ☑ 通勤   ☐ 收藏   ☐ 深夜         │
│   （一首歌都没有建过歌单 → 写「还没有歌单」，不给一个空框）│
│                    [取消] [保存]   │
└─────────────────────────────────┘
```

- 两个输入框 + 一组复选框，保存一次把三样一起提交（`PATCH /tracks`）
- **歌名不能为空**（空了退回原值并提示）；歌手可以留空（留空就是不显示那一段）
- 勾选变化也可以单独保存——但为了让「保存」只有一个语义，统一在点保存时提交

### 2.1.2 歌单栏

- 「全部歌曲」永远在第一条，选中态是黑底白字（跟侧边栏导航同款）
- 每条歌单右侧显示曲目数；hover 出现「改名」「删除」两个小图标
- **删除歌单要确认**（`ConfirmDialog`，文案写明「歌不会被删除」）
- 新建歌单：点「+ 新建歌单」就地出现一个输入框（回车确认 / Esc 取消），不弹框——建一个歌单只差一个名字，弹框太重
- **建完自动选中新歌单**：用户建歌单的下一步永远是「往里放歌」，停在全库视图会让他以为「建了但没生效」。空歌单进去显示的是「这个歌单里还没有歌」，正好告诉他还差一步
- **选中态活在全站，不是活在这个页面里**：左栏高亮的是「当前播放队列的来源」（`PlayerContext.queueSource`）。正在放「DJ」里的歌时，去总览再回来、从首页卡点进来、从页签栏切回来，「DJ」都是选中的。**歌单被删掉时自动回退到「全部歌曲」**，不用手写清理逻辑
- 重名会被拒绝并提示「已经有同名歌单了」

### 2.1.3 空态

| 场景 | 文案 |
|---|---|
| 曲库一首歌都没有 | 「曲库还是空的」+「把 mp3 之类的音频传上来」 |
| 歌单是空的一个歌单 | 「这个歌单里还没有歌」+「点上面的『添加歌曲』，从曲库里挑几首放进来」 |
| 一个歌单都没建 | 歌单栏只有「全部歌曲」+「+ 新建歌单」 |

### 2.1.4 空间与配额

每人 **5 GB**（`USER_QUOTA_BYTES`），单文件 **200 MB**（`MAX_TRACK_BYTES`）。

**三处都能看见，不靠「用户自己去找」**（2026-11-03 补）：

| 位置 | 显示什么 | 为什么放这 |
|---|---|---|
| **曲目列表表头右侧** | `2 首 · 已用 231 KB / 5.0 GB` | **主入口**。手机、平板、桌面都在同一个位置——上传区在 `md` 以下是整块不渲染的，配额不能跟着它一起消失 |
| 上传区底部 | `曲库已用 X / 5 GB` + 进度条 + `还能传 Y` | 桌面右栏；传之前最直观的参照 |
| 上传被拒时 | 413 +「曲库已满（5 GB），删掉一些再传」 | 服务端兜底 |

- 用到 **80%** 就开始提醒：数字与进度条变红 `#B42318`、文案换成「空间快用完了」。等到 100% 才说，那时用户已经传不进去了
- 表头的**分子是全库已用**，不是当前视图的合计——在歌单里看到「3 首 · 已用 4.8 GB / 5 GB」才对。拿歌单的合计去比 5 GB 会让人以为「还早着呢」
- 数字用 `formatBytes`（`231 KB` / `5.0 GB`），不用裸字节

### 2.1.5 拖拽排序（2026-11-03）

**两个地方都能拖**：曲库列表（「全部歌曲」视图）拖出来的是**全库顺序**，歌单视图拖出来的是**歌单内顺序**。两者互不影响——在歌单里排顺序，不会把「全部歌曲」也搅乱。

```
[♫ 晴天                 0:08 ]  ← 按住拖动
[♫ 第二首               0:05 ]
╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍╍  ← 松手后插到这里（顶部一条黑线）
[♫ 第三首               0:12 ]
```

- **拖哪儿松手就插哪儿**：被拖的那行取出来、插到目标行的位置，其余行顺次移动
- 拖动中那行 `opacity-40`，目标行顶部一条 2px 黑线（`inset 0 2px 0 #000000`）
- 行尾有一个 `GripVertical` 拖拽手柄（只在 `md` 以上显示）——**触摸设备上 HTML5 拖拽根本不触发**，所以手机上不显示这个入口，免得用户按半天没反应
- 批量模式下**不能拖**：那时「拖动」会被理解成「再勾选一行」
- 松手后立刻把**完整的新顺序**交给服务端（`PATCH .../order`），服务端全量重写 `position` 并回一份最新列表——前端不相信自己刚算的那份

**为什么是全量覆盖而不是「把第 3 首挪到第 7 位」**：拖拽一次会影响中间所有行的位置，前端手里本来就有完整列表。让服务端去推算「移动了谁」等于让两份状态各算一遍，出了「拖了没动」根本查不出是谁算错。


### 2.1.6 接着上次播（2026-11-03）

刷新页面、关掉重开、换台设备——都接着上次的地方。

**恢复的是什么**：哪首歌、当时在哪个歌单（决定「下一首」往哪儿走）、播到第几毫秒、**上次离开时是不是正在播**。
界面上就是「那首歌停在那儿，进度条在 4:17」。

**暂停刷新保持暂停、播放中刷新才接着播**（2026-11-04 补 `is_playing`）：
原来的判断是「浏览器不许无手势自动播，记了也用不上」——但恢复路径借道了「切歌就播」的 effect，
结果**暂停着刷新，页面自己响起来**。现在：

- 上次是**暂停** → 只把歌和进度摆好，**一次 `play()` 都不调**；
- 上次**在播** → 尝试接着播。浏览器允许就继续（这个站点有足够的媒体参与度时 Chrome 会放行），
  不允许就静默停在暂停态——这是浏览器的自动播放策略，网页绕不过去（§七第 21 条）。

**存在服务端**（`music_playback`，一人一行），不用 localStorage：按用户隔离是天然的，
换设备也能接上。详见《数据库/音乐播放状态表》。

**上报时机只有四个**（`timeupdate` 每秒四次，全写能把库写爆）：

| 时机 | 为什么 |
|---|---|
| 播放中每 15 秒 | 兜底：崩了最多丢 15 秒，不是整首 |
| 暂停那一刻 | 「听到这儿先停」是最常见的离开方式 |
| `pagehide` | 关页面 / 刷新，用 `fetch(keepalive)` 把请求送出去 |
| `visibilitychange` → hidden | 手机切后台多数不触发 `pagehide` |

每次上报都带 `playing`（用 `audio.paused` 的真实状态，不看 React state）。

**恢复期间禁止上报**：从拿到进度到 `loadedmetadata` 那几十毫秒里 `audio.currentTime` 还是 0，
这时写一次就把服务端的 45 秒覆盖成 0。用 `restoringRef` 拦住，seek 完才放开；
另外加一条 **3 秒时间兜底**——音频一直加载不出来时 `loadedmetadata` 永远不来，不能让上报被永久拦死。

### 2.2 首页「正在播放」卡

总览第七块，位置在**便签之后、每日一句之前**：它是陪伴类内容，和每日一句同类；但它可操作，所以排在每日一句前面。

```
┌ 正在播放            [♪ 夜跑] 顺序 ⟳ ┐
│            ●（黑胶，播放时转）        │
│              歌名                    │
│            歌手 · 格式               │
│   ──────●────────────────           │
│   1:24                        3:52   │
│        ⏮    ▶/⏸    ⏭                │
└────────────────────────────────────┘
```

- **标题行右侧显示「正在放哪一摊」**（2026-11-03 追加）：一个浅灰底小标签（`ListMusic` 图标 + 名字，`bg-[#F5F5F5] text-[10px]`，最长 7.5rem 截断）。**「全部歌曲」也算一个歌单**——全库播放时这枚标签写「全部歌曲」，不给空框也不隐藏；没有「正在播放」时才不渲染
- 名字读的是 `queuePlaylistName`——**每次从 `playlists` 现查**，所以歌单改名后这里立刻是新名字


- 卡片宽度与其他卡一致（430px 上限）
- 黑胶：`h-24 w-24` 黑底圆 + 白色 Logo，`isPlaying` 时 `animate-[spin_8s_linear_infinite]`
- 歌名 / 歌手 / 时间都是真实数据；进度条可拖
- 右上角模式按钮：文字「顺序」或「随机」，点一下切换（与工具页顶部的模式是同一个状态）
- **空曲库**：黑胶静止（不转）、歌名位置写「曲库还没有歌」、副标题写「去音乐播放器添加」、三按钮置灰；整张卡点进去到 `/tools/music-player`

### 2.3 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列纵向：播放条 → 歌单 **横滑条** → 上传按钮（顶部栏） → 曲目列表 | 歌单栏收成一条横向滚动的 chip（「全部歌曲」+ 各歌单 + 「+」），跟工具中心的分类条同款；列表每行只留「歌名 + 时长」，体积与上传时间隐藏；行尾图标常显（没有 hover）；三栏全部纵向堆叠。**配额看列表表头**——上传区不渲染了，不能指望用户滑到别处找 |
| 平板 md ~ lg（768–1023） | 两栏：歌单栏 `w-[180px]` + 曲目列表 | 上传区在列表**上方**通栏（先把歌放进来，才谈得上分类）；歌单栏回到竖列表 |
| 窄屏 PC lg ~ xl（1024–1279） | 三栏：歌单 `w-[180px]` + 曲目 `flex-1` + 上传 `w-[300px]` | 上传区固定在右栏；曲目列表自己滚，页面不滚 |
| 宽屏 ≥ xl（1280） | 三栏：歌单 `w-[200px]` + 曲目 `flex-1` + 上传 `w-[340px]` | 内容区铺满、不设 max-width（《界面设计规范》§5.3） |

颜色与控件一律照《界面设计规范》：白卡 `rounded-[2px] bg-white`、主按钮黑底直角（§7.3）、次要文字 `text-[#8A8A8A]`、虚线框 `border-dashed border-[#D9D9D9]`。

### 2.4 右下角悬浮球

跟首页卡、工具页播放条是**同一个播放器的第三个遥控器**，也是最方便的那个：不管在看哪一页，它都在右下角。

**视觉是照抄 Next 开发指示器那颗球的**（2026-11-03 直接从它的 DOM 里量出来的，不是凭眼睛估）：

| 项 | 值 |
|---|---|
| 尺寸 | 36 × 36（`h-9 w-9`） |
| 底色 | `rgba(0, 0, 0, 0.8)` + `backdrop-filter: blur(48px)` |
| 圆角 | 全圆（`rounded-full`），`overflow: hidden`（里面 SVG 是 40×40、比球大） |
| 阴影 | 三层：`0 0 0 1px rgb(23,23,23)`（外描边）+ `inset 0 0 0 1px rgba(255,255,255,0.14)`（内高光）+ `0 16px 32px -8px rgba(0,0,0,0.24)`（下方柔影） |
| 图标 | 描边式 `N`：**整段 SVG 从 Next 的 DOM 里原样抄下来、以 HTML 字符串注入**（`orb-mark.tsx` 里的 `MARK_SVG` + `dangerouslySetInnerHTML`）。两条 path + 两段 linearGradient + 一个 `5×1.5` 的缺口 `mask`。**不要翻译成 JSX 再手写属性**——每翻译一次就漏一样东西 |
| 图标摆放 | 36px 圆里居中一个 32×32 的方格，40×40 的 svg 在方格内**水平靠左、垂直居中**（照 Next 的 `display:flex; align-items:center`，没有 justify）。直接用 flex 居中会把 N 推歪 |
| 线条显隐 | path 上写着 `stroke-dashoffset="29.6"`（等于线长，**线条是藏起来的**），靠 `.orb-mark .paused { stroke-dashoffset: 0 }` 才显示——这条类和原版同款，写在 `globals.css`。别自己改成行内 0，那样跟原版就只剩「像」而不是「一样」 |
| 悬停 | 变亮的是**内层 32×32 的圆**（原版的 `:hover` 写在 `[data-next-mark]` 上），球最外 2px 那圈保持深色；颜色是叠在黑底上的白色 13%（`hsla(0,0%,100%,.13)`），不是把背景换成白色 13% |

```
                              ┌──────────────────┐
                              │ 正在播放      ✕  │
                              │ 歌名              │
                              │ 歌手 · 格式        │
                              │ ──●────────       │
                              │ 1:24       3:52   │
                              │   ⏮   ▶   ⏭  顺序 │
                              │ 打开曲库 →        │
                              └──────────────────┘
                                        ●  ← 悬浮球（36px，深色圆 + 白色 N）
```

- **`fixed` 在右下角**（`bottom-5 right-5`）；手机加 `bottom: max(20px, env(safe-area-inset-bottom))`，避开 iOS 的底部横条。
- **悬停**：底色从 `rgba(0,0,0,0.8)` 换成 `hsla(0,0%,100%,0.13)`——注意这是**叠在黑底上的白色 13%**，在浅灰页面上呈现为中灰。直接把 `background` 换成白色 13% 会让整颗球"消失"在背景里（实测踩过），所以实现上是一层绝对定位的白膜盖在黑底上、只让它的 alpha 变化。
- **按下**：`scale: 0.95`，150ms。
- **播放时线条做极轻的呼吸**（opacity 0.7 ↔ 1，2.8 秒一轮），暂停时静止。**不用旋转**——转一个字母认不出是什么字。
- **点球展开面板**（向上弹，宽 300px，右边缘与球对齐，`bottom-12`）；再点球、点面板外、按 `Esc` 都收起。
- 面板里：歌名 / 歌手 / **所属歌单标签** / 可拖进度条 / 上一首 · 播放暂停 · 下一首 / 模式 / 「打开曲库 →」。
- **面板也显示正在放哪一摊**（2026-11-03 追加）：歌手行下面一个浅灰底小标签（`ListMusic` + 名字，全库时写「全部歌曲」），跟首页卡同一个 `queuePlaylistName`。面板只有 300px 宽，所以它单独占一行、超长截断，不跟歌手挤在一起。
- **空曲库**时球照样在，点开只写「曲库还没有歌」+「去音乐播放器添加 →」——不给一个点了没反应的球。
- 层级 `z-40`：低于手机抽屉（`z-50`），抽屉拉开时球被盖住，不会飘在遮罩上面。

**Next 那边的开发指示器关掉了**（`next.config.ts` 的 `devIndicators: false`）。它是另一颗「深灰圆 + 白色 N」，跟这颗球几乎一模一样，留着就有两颗球摆在页面上；试过用 `devIndicators.position` 把它挪到别处，**在 Next 16.3.1 上不生效**（配置合法、重启、硬刷新都试过，它始终在左下角，正好压住侧边栏的用户菜单）。生产环境本来就不渲染它，关掉没有视觉损失。

## 三、数据模型

```sql
CREATE TABLE IF NOT EXISTS music_tracks (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title       TEXT    NOT NULL,          -- 展示名；优先文件自带标签，没有就用文件名去扩展名
  artist      TEXT,                      -- 文件自带的歌手标签；没有就是 NULL
  file_name   TEXT    NOT NULL,          -- 磁盘上的名字：<uuid>.<ext>，不含任何路径
  codec       TEXT    NOT NULL,          -- ffmpeg 探到的真实音频编码，如 mp3 / flac / aac
  size_bytes  INTEGER NOT NULL,          -- 落盘后的真实字节数
  duration_ms INTEGER,                   -- 探不出就 NULL（界面显示 --:--）
  created_at  INTEGER NOT NULL           -- 毫秒时间戳；列表按它升序（先传的在上，即播放顺序）
);

CREATE INDEX IF NOT EXISTS idx_music_tracks_user_id ON music_tracks(user_id);

-- 歌单：一行 = 一个歌单；歌单里的歌在关联表，不复制歌曲
CREATE TABLE IF NOT EXISTS playlists (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name       TEXT    NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  UNIQUE (user_id, name)                 -- 同一个人不能有两个同名歌单
);

CREATE INDEX IF NOT EXISTS idx_playlists_user_id ON playlists(user_id);

CREATE TABLE IF NOT EXISTS playlist_tracks (
  playlist_id INTEGER NOT NULL REFERENCES playlists(id) ON DELETE CASCADE,
  track_id    INTEGER NOT NULL REFERENCES music_tracks(id) ON DELETE CASCADE,
  position    INTEGER NOT NULL,          -- 歌单内顺序（升序）；跟曲库的 position 互不影响
  added_at    INTEGER NOT NULL,
  PRIMARY KEY (playlist_id, track_id)    -- 同一首不会被加进同一个歌单两次
) WITHOUT ROWID;

CREATE INDEX IF NOT EXISTS idx_playlist_tracks_track ON playlist_tracks(track_id);

-- 上次播到哪：一人一行（《数据库/音乐播放状态表》）
CREATE TABLE IF NOT EXISTS music_playback (
  user_id     INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  track_id    INTEGER REFERENCES music_tracks(id) ON DELETE SET NULL,
  playlist_id INTEGER REFERENCES playlists(id) ON DELETE SET NULL,
  position_ms INTEGER NOT NULL DEFAULT 0,
  updated_at  INTEGER NOT NULL
);
```

**设计要点：**

- **`file_name` 存的是 `<uuid>.<ext>`，不是原文件名。** 原文件名可能是 `../etc/passwd`、可能带 `?` `%` `\`，直接拿来拼路径就是路径穿越；两个同名文件还会互相覆盖。用户看到的歌名放在 `title` 列，两者分开——磁盘上的名字只负责唯一，展示名只负责好看。
- **`codec` 是 ffmpeg 探出来的，不是扩展名推的。** `.mp3` 改名成 `.m4a` 上传，扩展名会撒谎，编码不会。浏览器的播放能力跟的是编码，这个字段决定「这首到底能不能播」。
- **不存 `mime`**：它完全由 `codec` 决定（一张映射表在两个地方用：流接口的 `Content-Type`、列表页的格式标签），存一列等于让同一件事有两个真相。
- **`duration_ms` 可空**：探不出时长不该拦住上传——能播就行，列表上显示 `--:--`。
- **不存播放状态**：当前播哪首、播到第几秒，全在浏览器内存里。它是「此刻」的状态，不是资产；落库就要处理多端冲突（见 §一放弃项）。
- 磁盘路径不进库：库里只有文件名，目录由代码推导（§四第 4 条）。换机器、换目录时库不用改。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 1. 歌存哪 | **存服务器磁盘**，按用户分目录 `<music>/<userId>/<uuid>.<ext>` | 需求是「换设备也能听」。存本地（IndexedDB / File API）换台机器就空了，刷新也可能没 | 浏览器本地播：零后端成本，但「曲库」这个词就不成立了 |
| 2. 存进去要不要转码 | **原样存**，只收浏览器原生能放的格式 | 转码有损（AAC→MP3 掉一代）、费 CPU（一首歌几秒到几十秒）、占双倍空间（临时输入 + 输出）。而用户传的本来就是他愿意听的版本 | 统一转 mp3：兼容性最好，但等于把用户的无损文件降级；统一转 opus：体积小，但 Safari 上不稳 |
| 3. 播放器放在哪 | **一个，挂在 `AppShell`**（`(app)/layout` 那层）；首页卡与工具页都是它的遥控器 | 需求写明「切页面歌不停」。`<audio>` 一旦挂在页面级组件里，路由一变就跟着卸载，歌必停 | 每个页面各挂一个：切页面必断，且两处状态无法同步 |
| 4. 文件夹在哪 | **从 `DATABASE_PATH` 的目录推导**：`<db 所在目录>/music/` | 两者都是「必须活过部署」的持久数据，天然同源：本地 `data/music`，线上 `shared/data/music`。**不新增环境变量**——少一个上线失败点 | 新增 `MUSIC_PATH` 变量：更灵活，但线上要在 `shared/.env.production` 补一行，漏了就是「传了文件不知道去哪」 |
| 5. 时长怎么来 | 上传时**服务端 ffmpeg 探一次**，存进库 | 列表在点播之前就要显示时长；浏览器的 `loadedmetadata` 只有播过才知道。项目里本来就有 ffmpeg 二进制，探一次几十毫秒 | 前端懒探：要逐首加载才能凑齐时长，几十首就是几十个请求 |
| 6. 音频怎么鉴权 | **同源 `<audio src>` + 会话 cookie**，接口里 `getCurrentUser()` | `<audio>` 发的是普通同源 GET，cookie 自动带上，与页面同一套登录态；不需要为它发明一套签名 URL | 签名 URL / token query：多一套密钥与过期逻辑，收益只是「链接分享出去别人能听」——而这里恰恰不想让人分享 |
| 7. 上传进度 | 前端用 **`XMLHttpRequest`** 的 `upload.onprogress` | `fetch` 至今没有上传进度事件。200 MB 的文件没有进度条，用户会以为卡死并重传 | `fetch` + 假进度（按已耗时估）：骗人，重传时更糟 |
| 8. 首页卡进不进「常用工具」 | **不进** | 常用工具卡的规矩是「只放总览没有自己卡的真工具」。音乐在总览有自己的卡，再列一次就是同一个入口说两遍 | 列进去：卡上已经能点了 |
| 9. 悬浮球放在哪一层 | **挂在 `AppShell`**，跟 `PlayerProvider` 同一层，`fixed` 定位 | 需求是「不管去哪个页面一直悬浮着」。放进页面里任何一层都会被路由切走；放进 `PlayerProvider` 里会让「播放器」和「播放器的遥控器」耦合，将来只想换球的样子还得动播放器 | 放在 `(app)/layout` 的 JSX 里单独一层：效果一样，但要多传一次 Context 之外的 props |
| 10. 批量操作怎么进 | **表头一个「批量」按钮切进选择模式**，不是每行常显复选框 | 曲库日常动作是「点一行就播」。常显复选框会让每行多一块可点区域，误点一次就是「想播却选中了」；选择模式把两种意图彻底分开，退出成本也低 | 常显复选框（邮件列表式）：少一次点击，但每行的误触率翻倍 |
| 11. 删除要不要确认 | **全部都要**（2026-11-03 改）。单首、批量、删歌单，一个不落，并且文案必须写清「音频文件也会一起删掉」与「它还在 N 个歌单里」 | 原来的做法是「单首不确认，反正删错了重传一次就行」——这句话在歌单出现之后不成立了：删一首歌会同时把它从好几个歌单里抽走，重传回来的是一首「不在任何歌单里的新歌」，歌单里那个位置永远补不回来。**删除是不可逆的，确认框是唯一能拦一下的地方** | 只在批量时确认：省一次点击，代价是「一按就没了」 |
| 12. 一首歌能不能属于多个歌单 | **能**，多对多（`playlist_tracks` 关联表） | 「通勤」和「收藏」同时收同一首歌是常态。单归属一旦定死，想同时归两类就只能复制一份，而复制会产生两份元数据、删一份另一份还在 | 单归属（`music_tracks` 加一列 `playlist_id`）：查询简单，但「一首歌只能在一个歌单里」很快就会逼着人建重复歌单 |
| 13. 播放队列跟谁走 | **跟当前视图走**：在某个歌单里点歌 → 队列 = 该歌单；在「全部歌曲」里点 → 队列 = 全库。**切左栏也算换队列**：点某个歌单时队列立刻换成它，但**正在播的那首不打断**。**左栏的选中态由队列来源派生**，不是页面局部状态——正在放「DJ」时从任何入口进来，DJ 都是选中的。 | 用户在歌单里点歌，期待的就是「在这个歌单里往下放」。队列固定成全库的话，「下一首」会跳到歌单外的歌，等于歌单只做了筛选没做组织。切左栏不同步队列的话，会出现「列表是 DJ、播的却是全库下一首」这种自相矛盾的画面。选中态若是局部 state，一离开页面就丢，回来变成「全部歌曲」，跟耳朵听到的对不上 | 队列永远是全库：实现最省，但歌单变成纯过滤器，播放行为跟用户的意图对不上；切歌单时顺手换歌：会打断正在听的歌，更糟；选中态存本地：跨页面必丢 |
| 14. 顺序怎么存 | **显式的 `position` 列**，曲库与歌单各一套（2026-11-03 改）。曲库的 `music_tracks.position` 与歌单的 `playlist_tracks.position` 互不影响 | 用户能拖之后，顺序就不能再靠 `created_at` 推导——推导不出一条他手动排过的序列。两份 position 分开，是为了「在歌单里排顺序」不把「全部歌曲」也搅乱 | 一份 position 全库共享：歌单一拖全库跟着变，等于没有歌单顺序；间隙法（1000 递增 + 定期重排）：省一点写放大，但多一套「什么时候重排」的判断 |
| 16. 播放进度存哪 | **服务端**（`music_playback`，一人一行），不用 localStorage（2026-11-03 新增） | 三个理由：按用户隔离天然正确（localStorage 是「这台浏览器」的，换账号就串）、换设备能接上、数据量极小。写只在四个时机上报，不是每帧都写 | localStorage：零后端，但要自己解决「浏览器的哪个用户」，而且换设备就没了；记播放历史：那是另一个功能，要多一张表和一个列表页 |
| 17. 记不记「是否正在播」 | **记**（`music_playback.is_playing`，2026-11-04 补） | 原来的判断是「浏览器不许无手势自动播，记了也用不上」，结果恢复路径借道了「切歌就播」的 effect：**暂停着刷新会自己响**。记下来之后，暂停态一次 `play()` 都不调，播放态才尝试接着播（被浏览器拒绝就停在暂停） | 不记、恢复时一律不播（满足不了「播放中刷新接着播」）；用 localStorage 记（换设备就丢，而且和进度分住两地） |
| 15. 改歌名会不会动磁盘文件 | **不会**，只改 `music_tracks.title` | 磁盘文件名是 `<uuid>.<ext>`，只负责唯一、不承载语义（§三第 1 条）。改名去改文件，既要做重命名事务，又会在「改名成功、文件改名失败」时对不上 | 连带重命名文件：多一次失败面，收益为零 |

## 七、已知的坑

1. **`<audio>` 只能有一个，且必须在 `AppShell` 里。** 放在首页卡里，用户从首页切到任何页面它就被卸载，歌立刻停——而「切页面歌不停」正是这个功能的核心。首页卡、工具页播放条都只读 Context，不许自己写 `<audio>`。
2. **Safari 不支持 Range 就完全不播。** Safari 对音频发 `Range: bytes=0-`，服务端返回 200 全量时它会自己放弃播放（Chrome 能容忍，Safari 不能）。所以流接口必须实现 206 + `Content-Range` + `Accept-Ranges: bytes`，这条在 Chrome 上测不出来。
3. **拖动进度条会被 `timeupdate` 拽回去。** `timeupdate` 每秒触发四次，拖动期间它仍在写 `position`。必须有一个 `isSeeking` 标志：按下时置真、松手请求 `seek` 后再置假，期间不把 `position` 回写到滑块。
4. **`fetch` 没有上传进度。** 前端必须用 `XMLHttpRequest` 才能拿到 `upload.onprogress`；用 `fetch` 的话 200 MB 文件全程只有「处理中」三个字。
5. **文件必须落在 `shared/` 那一层。** 线上是 `releases/<时间戳>` + `current` 软链，部署只切软链、不搬数据。写进发布目录的文件下一次上线就被换掉——而这个功能的全部价值就是「歌一直在」。
6. **两个标签页同时开着会同时播。** 两套 `<audio>` 各放各的。本版不处理（要做就得用 `BroadcastChannel` 或 localStorage 抢锁），写在这里是为了不再被当成 bug 报一次。
7. **`Content-Length` 可以是假的。** 体积检查必须两道：先看声明的 `Content-Length`，再在流式写盘时边写边数（音频提取已经踩过这个坑，照它的做法）。
8. **iOS 的自动播放限制。** `play()` 必须由用户手势触发。点行、点按钮都是手势，没问题；但「一首播完自动接下一首」在部分 iOS 版本上会被拒——被拒时不要报错弹窗，静默停在「暂停」态即可。
9. **删歌要删两处。** 先删数据库行、再删磁盘文件：反过来一旦中间失败，库里会留下一条指向不存在文件的记录，界面点播放就是 404。文件删失败只留垃圾文件，不影响使用。
10. **按用户分目录，但 `ON DELETE CASCADE` 不删文件。** 删账号（目前没有这个功能）时数据库行会级联删掉，磁盘文件不会——真要支持删账号时得先删目录。
11. **悬浮球跟 Next 开发指示器长得一模一样。** 两者都是「深灰圆 + 白色 N」。`devIndicators.position` 在 Next 16.3.1 上**不生效**（试过 top-right，它始终在左下角、压住侧边栏用户菜单），所以直接 `devIndicators: false` 把它关了。生产环境本来就不渲染指示器，没有视觉损失；想开回来删掉那行配置即可。
12. **点面板外关闭不能用「整页遮罩」。** 用一层透明遮罩去接点击，会把球本身也盖住（第二次点球就变成点遮罩），而且遮罩会吞掉页面上其它交互的 hover。正确做法是监听 `document` 的 `pointerdown`，判断点击目标是否在球或面板内部。
13. **三层 `box-shadow` 别用 Tailwind 的 `shadow-[...]` 任意值写。** 阴影值里夹着 `rgba(255,255,255,0.14)` 这种带逗号的函数，Tailwind 会按逗号拆成多个 shadow 段、每段都解析失败，**生成的是一串空 shadow**——球看上去是一张没有描边的扁圆，而且不报任何错（`getComputedStyle` 才看得出来是 `rgba(0,0,0,0) 0 0 0 0` ×4）。写在 `style={{ boxShadow }}` 里。
14. **批量模式下「点整行」的含义必须换掉。** 平时点一行是播放，选择模式里点一行是勾选——同一个手势两种结果，如果不写清楚，用户会连着放歌又取消勾选。所以：行内不再渲染播放按钮（换成 `role="checkbox"` 的按钮 + `aria-checked`），并且表头必须有一个明显的「取消」出口。
15. **改歌名只改 `title`，不动磁盘文件。** 磁盘上是 `<uuid>.<ext>`，本来就不承载语义。有人会担心「那文件名叫什么？」——答案是不重要，界面永远显示 `title`，`file_name` 只给流接口拼路径用。真去重命名文件，就多出一段「改名成功、改文件失败」的失败面。
16. **删歌单不删歌。** 歌单表只是关联，`ON DELETE CASCADE` 删的是 `playlist_tracks` 里的行。写这个功能的任何时候都别在 `DELETE FROM playlists` 附近顺手写 `DELETE FROM music_tracks`。
17. **`UNIQUE (user_id, name)` 的报错要翻译成人话。** SQLite 抛的是 `UNIQUE constraint failed: playlists.user_id, playlists.name`，直接冒到界面上没人看得懂。数据层捕获后抛 `PlaylistNameTakenError`，接口回 409 +「已经有同名歌单了」。
18. **切歌单不能打断正在播的歌，但必须同步队列，而且选中态要跟着活。** 点左栏只换「列表显示什么 + 后续队列是什么」，当前 `<audio>` 里的歌继续播——如果顺手 `pause()` 或重设 `src`，用户正在听的歌会断。但**只换列表不换队列也是错的**：切到「DJ」再点「下一首」会走到全库的下一首，用户看到的列表和听到的歌对不上。正确做法是 `switchQueue`（只改队列来源、不换歌），跟 `playPlaylist`（换队列 + 换歌）分成两个方法——「我要看这个歌单」和「我要播这个歌单」是两种意图。**另外：左栏的选中态必须直接由 `queueSource` 派生，不能存成 `MusicView` 的 `useState`** ——局部 state 会随页面卸载，用户去一趟总览回来就变回「全部歌曲」，而歌还在放 DJ 的。同一个事实（在放哪个歌单）只该有一个家。
19. **HTML5 拖拽在触摸屏上根本不触发。** `draggable` 是桌面浏览器的 API，iOS / Android 上按住拖动只会滚动页面。所以拖拽手柄 `hidden md:flex`——手机上不渲染这个入口，比渲染出来按不动好。要真上移动端排序，得换 pointer 事件手写，那是另一套东西。
20. **Firefox 不在 `dragstart` 里 `setData` 就不会开始拖。** Chrome 里不设也能拖（所以只在 Chrome 测会漏），Firefox 则完全没反应。`effectAllowed = "move"` 和 `setData("text/plain", id)` 两行都要写。
21. **浏览器不许网页无手势自动播。** 恢复「上次在播」时调 `play()` 会被拒（`NotAllowedError`）。两层兜底（2026-11-04 加）：① **静音自动播是允许的**——被拒时先 `muted = true` 播起来，成功后再恢复原静音状态；② **不许把「上次在播」写回 0**——那不是用户暂停，写回去下次刷新就再也不尝试了（`resumePendingRef`，播成功后由 `onPlay` 清掉）。反过来，恢复「上次是暂停」时一次 `play()` 都不该调。
22. **恢复期间千万别上报进度。** 从服务端拿到位置到 `loadedmetadata` 之间，`audio.currentTime` 还是 0；这期间只要跑一次「暂停就上报」，库里的 45 秒就被写成 0，用户下次打开从头开始。`restoringRef` 就是这道闸，`loadedmetadata` 里 seek 完才放开，`error` 时也要放开（否则这个会话永远记不上）；再加一条 3 秒时间兜底——音频一直加载不出来时那个事件根本不来。
23. **`GET /tracks` 一次要把歌单归属带回来。** 编辑弹框要勾选「这首歌在哪些歌单里」，如果每个弹框再发一次请求，就会出「打开弹框时歌单还没回来、复选框一片空白」。列表与归属同一份响应，前端不会有中间态。
24. **`Readable.toWeb` 在客户端断开后会抛 `ERR_INVALID_STATE: Controller is already closed`**（2026-11-04 线上事故）。`<audio preload="metadata">` 只关心文件头，浏览器拿完前几 KB **就断开连接**，而 `createReadStream` 还在继续读——adapter 把数据往已关闭的 controller 里写，Node 抛 uncaughtException，**那个请求会一直挂着**（页面 `load` 事件不来，线上实测刷新要等 15 秒）。修法：`request.signal` abort 时 `destroy()` 文件流、`cancel()` 里同样 destroy、吞掉关闭后的那一次写入。**别用 `Readable.toWeb` 直出**，用 `stream/route.ts` 里的 `toWebStream`。
25. **M4A 的 `moov`（时长、seek 表）默认在文件末尾——大文件不重排就没法播。** 浏览器要下完整个文件才知道多长：线上 46MB 的歌实测 7 秒只下了 532KB、`readyState` 一直是 0，刷新既不恢复位置也播不起来（主人怀疑「跟文件大小有关」，对）。上传时统一 `-movflags +faststart` 重排（`-c copy` **不转码**，只挪 atom，体积几乎不变）。坑：输出临时名没有 `.m4a` 后缀时 ffmpeg 猜不出容器、直接报 `Invalid argument`，必须显式 `-f ipod`；重排失败要静默退回原文件，不能因为重排失败就让上传失败。
