<summary><b>2026-10-15 · 阶段 1 · 项目骨架初始化</b> —— 项目可本地启动，根路由展示 Hello world</summary>

<br>

**目标**

搭起项目骨架并跑通启动链路：本地 `pnpm dev` 能起来，根路由 `/` 展示一个 Hello world。
**本阶段范围**：只到「能启动 + Hello world」，不引入 shadcn/ui、数据库、测试框架等其他依赖。

**进展**

- 用 `create-next-app@16.3.1` 初始化项目，实测落定版本：

  | 包 | 版本 |
  |---|---|
  | next | 16.3.1 |
  | react / react-dom | 19.2.8 |
  | tailwindcss / @tailwindcss/postcss | 4.3.3 |
  | typescript | 5.9.3 |
  | eslint / eslint-config-next | 9.39.5 / 16.3.1 |
  | pnpm / Node.js | 10.34.5 / 22.23.2 |

- 目录形态：`src/` + App Router，路径别名 `@/*` → `./src/*`，ESLint 9 flat config
- 根布局 `src/app/layout.tsx`：`lang="zh-CN"`、标题 `Nexus OS`、`h-full antialiased`
- 根页面 `src/app/page.tsx`：居中一行 `Hello world`，用 Tailwind 工具类实现（同时验证样式管线通了）
- `.gitignore` 补充：`!.env.example`（环境变量模板需入库）、`/data`（本地数据不入库）
- 脚手架自动初始化了 Git 仓库

**验证（全部真实执行）**

| 项 | 命令 / 方式 | 结果 |
|---|---|---|
| 类型 | `pnpm exec tsc --noEmit` | 通过 |
| 规范 | `pnpm lint` | 通过 |
| 启动 | `pnpm dev` | 启动成功 |
| 响应 | `curl http://localhost:3001/` | HTTP 200 |
| 内容 | HTML 中检索 | `<h1>Hello world</h1>`、`<title>Nexus OS</title>`、`lang="zh-CN"` |
| 样式 | 拉取产出的 CSS chunk | `.text-2xl` / `.min-h-screen` / `.items-center` / `.tracking-tight` 均已产出 |
| 视觉 | 浏览器截图 | 页面居中显示 Hello world |

**决策**

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 初始化方式 | `create-next-app` CLI + `--empty` | 官方脚手架产出的配置与官方约定一致；`--empty` 去掉示例样板，只留最小页面 | 手工逐文件搭建（否决：易漏配置且对学习无增益） |
| 目录形态 | `--src-dir`（`src/app`） | 与《技术栈说明》的目录约定一致 | 根级 `app/`（否决：与既定约定冲突） |
| 本次范围 | 只做到可启动 + Hello world | 明确要求收敛范围，避免一次引入过多变量 | 一次装齐全套依赖（否决：超出本次要求） |
| 版本 | 锁 next `16.3.1`、react `19.2.8` | 与《技术栈说明》基线逐字对齐 | 用脚手架默认的 latest（否决：会漂移到 16.4.1 / 19.3.1） |

**问题**

| 现象 | 根因 | 处理 |
|---|---|---|
| 首次 `curl localhost:3000` 返回的**不是**本项目的页面 | 端口 3000 已被本机另一个正在运行的 `next-server` 占用，Next 自动把本项目切到了 3001，而 `curl` 打到的是 3000 上那个陌生服务 | 用 `lsof` 确认监听进程与各自的 cwd，改到 3001 验证；未去动那个不属于本项目的进程 |

> 教训：**验证「服务起来了」之前，先确认自己打的是哪个端口、哪个进程。** 端口冲突时 Next 会静默换端口，若不做归属校验，很容易把别的服务的响应当成本项目的结果。

**产出**

- 项目骨架：`package.json` / `tsconfig.json` / `next.config.ts` / `eslint.config.mjs` / `postcss.config.mjs` / `pnpm-workspace.yaml`
- 应用入口：`src/app/layout.tsx` / `src/app/page.tsx` / `src/app/globals.css`
- 开发服务器运行中：`http://localhost:3001`

<summary><b>2026-10-15 · 阶段 0 · 立项与技术栈基线</b> —— 确立通用技术栈基线</summary>

<br>

**目标**

确立项目的技术选型基线，形成后续所有开发的地基。

**进展**

- 建立 `docs/` 文档体系，首篇落地《技术栈说明》
- 敲定九项技术栈基线及其版本：

  | 层 | 技术 | 版本 |
  |---|---|---|
  | 运行时 | Node.js | 22.23.2 |
  | 包管理 | pnpm | 10.34.5 |
  | 框架 | Next.js | 16.3.1 |
  | 界面 | React | 19.2.8 |
  | 语言 | TypeScript | 5.x |
  | 样式 | Tailwind CSS | 4.x |
  | 组件 | shadcn/ui | 4.18.0 |
  | 存储 | SQLite（better-sqlite3） | ^13.0.3 |
  | 测试 | Vitest | ^4.1.11 |

- 同步登记配套依赖（Base UI、CVA、clsx、tailwind-merge、Lucide、tw-animate-css、ESLint）与候选技术（Zod、Playwright、GitHub Actions、ORM、虚拟列表、PWA）

**决策**

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 文档边界 | 《技术栈说明》只写通用技术选型，不掺业务设计 | 业务会独立演进，若混入技术文档，每次业务调整都要回头改技术文档，两份文档互相污染 | 技术 + 业务合并成一份大文档（否决：职责混淆，改一处动全身） |
| 全栈形态 | 单体：页面、接口、数据访问同一仓库同一进程 | 与当前规模匹配，无分布式开销；后期若需拆分，Route Handlers 边界本身就是天然的拆分线 | 前后端分仓 / 独立后端服务（否决：当前无此复杂度） |
| 文档数量 | 先只建必要文档，随阶段增补 | 文档先于内容膨胀会变成负担，也没人看 | 一次性铺开全套文档（否决：无内容支撑，必然空转） |
| 版本锁定 | `.nvmrc` + `engines` + `packageManager` 三处共同固化 | 三处缺一都可能被不同入口绕过，导致环境漂移 | 只在 README 里写一句"用 Node 22"（否决：无强制力） |

**问题**

无

**产出**

- `docs/技术栈说明.md`
- `docs/开发日志.md`（本文件）
