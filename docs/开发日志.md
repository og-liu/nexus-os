<summary><b>2026-10-16 15:08 · 重写《数据库设计》，并复盘「他是怎么搞懂的」</b> —— 文档写成了字段参考，而他要的是"这东西是什么"</summary>

<br>

**目标**

反馈：《数据库设计》写得有点难懂，优化一下；并要求分析他实际是怎么搞懂的。

**进展**

- 文档按他实际搞懂的顺序重排：**这两张表分别是什么（§一）→ 没有它会怎样（§1.5）→ 常见误解（§1.3）→ 一行的一生（§1.4）→ 字段表（§二，往后放）**
- 每个字段的「含义」列改成人话（原来是"用术语解释术语"）；新增「你可以自己验证」（cookie 原文算 sha256 = 库里那列；expires_at − created_at 恒等于 30 天）
- 新增常用查询（现在几个人登录着 / 每人几处登录 / 把毫秒时间戳看成人读的时间），并说明 `left join` 与 `join` 在这个场景下的区别

**决策（复盘：为什么前三轮讲不明白、他后来是怎么懂的）**

他的行为里有四个动作，前三个我都没顺着走：

1. **他先自己看数据，再问概念** —— 在 Navicat 里翻两张表、看着真实行提问。我前面三轮都是先讲机制、后给数据，顺序正好反了。
2. **他一次只问一列**（`token_hash` 是什么？`user_id` 我猜是账号 id？后面两列是什么的开始结束？）—— 真正的突破口是**列级解释**，不是流程叙述。
3. **他问的是"缺失"**：是不是多余的？没有这张表会怎样？——**反事实**才是他理解"用途"的方式（"没有它会怎样"比"它能干什么"更有说服力）。
4. **他自己用大白话复述**（"登录过、一直没退出、也没过期的就存在呗"）—— 他只差一步时不要重讲一遍，只要补两个精度（过期行不会自己消失、30 天不会续期）。

我的失败方式，连着三轮换了三种载体但都错在同一个前提上：

- 第一轮讲**流程**（登录→发 cookie→查表）——流程假设读者已经知道两端是什么，而他要知道的正是"这东西是什么"
- 第二轮讲**比喻**（号码牌/柜子）——比喻让人"相信"，不让人"看到"；他缺的不是相信
- 第三轮做**实验**（删行→掉线）——证明的是"删了会怎样"，仍然没回答"每一列是什么"
- 而文档本身是**按 schema 的组织方式**写的（表 → 字段 → 索引），那是给"已经懂的人"查阅的格式，不是给"想懂的人"读的格式；也从来没写出他会问的那些问题（多设备为什么没有设备字段）

**问题**

- 我在这条线上还犯了一个错：他没要求，我自作主张造了样例库和演示，被明确指出后还原。**解释就是解释**，要动手先问一句。
- 复盘出的写作规矩：给这本文档写东西，**先把读者会问的问题写出来**（哪怕是负面的："是不是多余的""为什么没有设备字段"），再写答案。字段参考放后面，前面留给人看的"它是什么"。

**产出**

- `docs/数据库设计.md` 重写（更新记录里也写了为什么重写）
- 本文档自身第 §1.3 节 = 他问过的问题清单

<summary><b>2026-10-16 14:38 · 登录会话表改名 sessions → auth_sessions</b> —— 把「会话」这个词留给 Agent 的对话线程</summary>

<br>

**目标**

反馈：`sessions` 这个名字有误导性——将来做 Agent 相关开发时，「会话」指的是**对话线程**，两边迟早撞车。

**进展**

- 表名、索引名、两份文档、三处代码（含测试）一并改掉
- 老库由 `initSchema()` 里的 `migrateLegacyTableNames()` 幂等迁移：**存在旧表且没有新表**才 `ALTER TABLE … RENAME TO`；SQLite 改名表时不会跟着改索引名，所以旧索引手动丢掉、由 SCHEMA 按新名字重建
- 新增 `db.test.ts`：5 个用例（行一行不丢、索引按新名字重建、**改名后外键级联仍然生效**、重复执行不出错、全新的库直接就是新名字）
- 实测：本地那个**真实的库文件**迁移后，老会话行还在（id=17 属于 ogliu），旧表与旧索引都没残留
- 门禁三项全绿（45 个用例）

**决策**

- **改成 `auth_sessions`**：前缀指明「哪一类」会话，把裸词让给对话（`agent_sessions` / `chat_sessions` 以后都不撞车）；而 `auth` 正是项目里这个领域的词（`lib/auth/`、`AuthFormState`、`auth-card`）
- **落选**：`login_sessions`（只覆盖「登录」，登出与会话校验也在这张表里，动作名不如领域名）、`user_sessions`（读起来像「用户的会话」，跟 agent 会话并存时更含糊）
- **现在就改，不等做 Agent 时再改**：线上那张表**恰好是空的**，此刻的成本只是几个字符串；等它装了几百行会话、代码里到处是 `sessions` 的时候再动，就是一次有风险的迁移
- **迁移必须写在建表之前**：反过来先 `CREATE TABLE IF NOT EXISTS auth_sessions` 再改名的话，老库会因为「新表已存在」而跳过迁移，老行被留在旧表里成孤儿
- **不为一次改名引入迁移框架**：一条 `ALTER TABLE … RENAME TO` 加一个幂等判断就够；等真出现「改列 / 改语义」的需求时再谈框架

**问题**

- 迁移一度「没生效」，查下来是**两个懒加载叠在一起**：①数据库连接是懒建的（GET 页面不带 cookie 时压根不开库）②连接缓存在 `globalThis` 上，所以**正在运行的 dev server 不会重新执行 `initSchema()`**——必须重启进程。这一条对线上同样成立：发布重启一次，迁移自然完成
- 顺带印证了 `AUTOINCREMENT` 的一个作用：迁移后老会话行的 id 是 **17** 而不是 1——编号从不回收，这正是当初写 `AUTOINCREMENT` 想要的效果

**产出**

- 代码：`db.ts`（SCHEMA + 迁移函数）、`session.ts`、`session.test.ts`、新增 `db.test.ts`
- 文档：《数据库设计》§2.2 增加「为什么叫 auth_sessions」、《功能/登录注册》表名同步
- 验证：本地真实库文件迁移通过；线上由发布重启触发

<summary><b>2026-10-16 14:31 · 重名提示从两条收敛成一条</b> —— 一个错误，一处提示</summary>

<br>

**目标**

反馈：重名注册时页面上同时出现两条提示（用户名下方的红字 + 按钮上方的灰块），格式还不一样，读起来像两个错误。

**进展**

- `registerAction` 只回一个字段级错误 `该用户名已被占用`，不再同时给表单级提示
- 注册表单删掉表单级提示块（注册页的失败现在全是字段级）以及随之没用的 `anyDirty`
- 实测：重名注册后页面里 `[role=alert]` 数量为 **0**、用户名下方红字正确、红描边在、全文不再出现「换一个用户名试试」；改一下输入，提示立刻让位（`useDirtyFields` 仍生效）
- 门禁三项全绿，构建通过

**决策**

- **一次失败只出现在一处**（写进《界面设计规范》§7.16）：能归到某个字段的失败**只**用字段级提示；归不到任何字段的（整体失败、限流锁定）才用表单级灰块。两个提示位说的是同一件事时，用户会以为除了重名还另有问题
- **文案陈述事实、不给建议**：`该用户名已被占用`，不是「换一个用户名试试」——「被占用」三个字本身已经说明要换，建议只是噪音，还会把提示拉长、淹没信息
- **删掉注册页的表单级提示块，而不是留着备用**：它现在没有任何路径会返回 `formError`，留着就是死代码；真出现归不到字段的失败时再加（对比登录页，那边确实需要它）

**问题**

- 这个 bug 的形状值得记住：两处提示**各自都是"对的"，合起来才错**——单看字段级没问题，单看表单级也没问题，问题出在同时给出。写校验分支时"这条失败归谁"要问一次，而不是两个地方各塞一下

**产出**

- 代码：`src/lib/auth/actions.ts`、`src/components/auth/register-form.tsx`
- 文档：《界面设计规范》§7.16 新增两条规则；《功能/登录注册》决策表 +验收表第 4 条

<summary><b>2026-10-16 11:37 · 修掉入口页在中间宽度「贴左不居中」</b> —— 品牌块与表单改成同一列</summary>

<br>

**目标**

窗口从宽屏拖到手机的过程中，中间宽度（约 560–1023px）表单贴左、右侧空出一片。实测反馈：没有水平居中对齐。

**进展**

- 定位：`max-w-[420px]` 在窄屏就已生效，但"水平居中"当时挂在 `md:items-center` 上——于是 560–767 这一段里卡片被 `max-w` 收窄，却没有任何东西把它居中
- 改法：品牌块与表单卡都变成 `mx-auto w-full max-w-[420px]` 的**同一列**；两边的内容边距逐档对齐（文字块 `px-5 / md:px-8`，卡片 `px-5 / md:p-8`）
- 实测六个宽度（390 / 560 / 700 / 900 / 1100 / 1440），逐档读元素的 left 与内容左边距：**每一档品牌块与卡片完全相等**

**决策**

- **不用"给容器补一个 items-center"**：那种补丁只让卡片自己居中，品牌块仍贴左，两者不同轴——窗口一缩就露馅。并进同一列之后，无论宽度怎么变都对齐。
- **边距写在卡片上、不写在容器上**：容器留出整列宽度（`max-w-[420px] mx-auto`），卡片自己带 `px-5`。这样窄屏时卡片铺满、宽一点时限宽居中，同一条规则覆盖两端。

**产出**

- 代码：`auth-brand-compact.tsx`、`(auth)/layout.tsx`、`auth-card.tsx`
- 文档：《界面设计规范》§7.16 增「一列 420px 同轴」规则，尺寸表同步更新
- 验证：`pnpm run lint` / `pnpm run build` 通过；六个宽度的坐标逐档核对

<summary><b>2026-10-16 11:34 · 入口页定为「分栏 PC + 大口号手机」，并把断点之间的过渡做顺</b> —— 三个方向收敛成一个</summary>

<br>

**目标**

把三个候选方向收敛成一个：PC 用分栏版、手机用大口号版，并且回答"从 PC 尺寸缩到手机尺寸，中间怎么过渡"。

**进展**

- 撤销多版本展示：删掉 `/preview/auth` 整组预览路由与 `components/auth/variants/` 三个外壳，回到单一路径
- 收敛后的结构：`AuthBrandCompact`（手机 / 平板的品牌块）+ `AuthBrandPanel`（宽屏黑栏）+ `AuthCard` + `(auth)/layout.tsx` 的断点骨架
- 三档实测：390×844（手机）、900×1000（平板）、1440×900（宽屏）

**决策**

- **「一次只变一件事」就是过渡的全部答案**：底色与卡片在 **md（768）** 切换（白 → 灰底 + 白卡），版式方向在 **lg（1024）** 翻转（纵向流 → 左右分栏）。两件事压进同一个断点，1024px 附近会同时跳底色、跳卡片、跳方向——那才是"突兀"的来源。
- **底色统一写在外层容器**（品牌区与表单区都不自带底色）。第一版两块各自带底色，md 档出现"上面白、下面灰"的一条硬分界；这属于修形，不是风格问题。
- **手机上的大口号是配重，不是装饰**：34px 那句占住上半屏，下面 400 多像素的表单才不显得孤零零；上一轮靠"贴底一行小字"撑住的做法随之删掉。
- **装饰能力集中放 `globals.css`**：动效 token 与纹理类都用 Tailwind 类名调用，组件里仍不写自定义 CSS（§九 第 6 条的边界因此写清楚了：只有跨组件的公共能力才进 `globals.css`）。
- 三个方向里 V3（暗色沉浸）视觉冲击最大，但全站是浅色体系，暗色入口会与应用内部断层；V2（编辑式）的构图保留给了手机档——它的「大字号 + 1px 线 + 等宽脚注」在三档里都成立。

**问题**

- `prefers-reduced-motion` 只能靠系统设置触发，本轮是靠代码约定（`globals.css` 里的全局降级）保证的，**没有实测**。
- 中途遇到一次"改了没生效"：Next 16 的 dev 热重载有几秒延迟，第一张复核截图拍到的是旧状态。结论：**改完 CSS 立刻截图会拍到上一版**，要等一个编译周期，或读一次 computed style 确认。

**产出**

- 代码：`(auth)/layout.tsx`、`auth-brand-compact.tsx`（新）、`auth-brand-panel.tsx`（新）、`auth-card.tsx`、`globals.css`（动效 token + 纹理类）、`text-field.tsx` 与两个表单的尺寸档
- 文档：《界面设计规范》§7.16 重写、新增 §12「动效与装饰」、§一 第 4 条与 §九 第 6 条随放宽
- 验证：`pnpm run lint` / `pnpm run build` 通过；三档截图逐一核对（改动目前仍在工作区，未提交）

<summary><b>2026-10-16 11:13 · 登录注册页改成真正的响应式版式</b> —— 手机不再是一张「压扁的桌面卡片」</summary>

<br>

**目标**

登录 / 注册页在手机上「能用，但不够高级」：桌面和手机都是同一张居中卡片，只是宽度被压窄了。要按断点各给一套版式。

**进展**

- 规范先行：重写《界面设计规范》§7.16，给出三档完整尺寸表；§6 补一条总则——「每个页面必须给出至少三档断点的版式安排，只把桌面版压扁就等于没做响应式」
- **版式在 lg（1024）整档翻转**：手机＝上黑底品牌条 / 中表单 / 底品牌小字；宽屏＝左黑底品牌栏（`w-[42%]`，`xl:w-[45%]`）+ 右灰底白卡
- **尺寸档在 md（768）收紧**：输入框 `h-11 → h-10`、主按钮 `h-12 → h-11`、字段间距 `space-y-5 → space-y-4`
- 新增 `src/components/auth/auth-brand-panel.tsx`（一个组件两套排布）；`(auth)/layout.tsx` 改成断点骨架；`AuthCard` 去掉卡内品牌头、卡片外壳改为只在 lg 出现
- 实测三档：390×844（手机）、768×1024（平板）、1440×900（宽屏），逐档截图核对

**决策**

- **抽成 hook，而不是在两个表单里各写一遍**：符合 `src/hooks/` 的门槛——两个组件需要同一份状态逻辑，不是为一次性使用提前抽象
