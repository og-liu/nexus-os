## 一、先看懂这两张表（读代码之前先读这一节）

**一句话：**

| 表 | 一行是什么 | 它回答的问题 |
|---|---|---|
| `users` | **一行 = 一个人** | 这个账号**存在**吗？密码对不对？ |
| `auth_sessions` | **一行 = 一张还没过期的通行证** | 这个请求**是谁发的**？ |

再打个比方：`users` 是**户口本**（谁是这里的人），`auth_sessions` 是**门禁刷卡记录**（现在谁在屋里、手里那张卡还有效）。有户口本不代表人在屋里。

### 1.1 先说清一个词：「会话」不指聊天

HTTP 里把「一次登录 → 到登出或过期之间的这段时间」叫 **session（会话期）**。`auth_sessions` 的一行，就代表「这段时间还开着」，所以它的意思更接近「**一张还开着的通行证**」，跟"聊天会话"半点关系没有。

> 正因为这个词容易和将来的"AI 对话会话"混淆，这张表的名字从 `sessions` 改成了 `auth_sessions`（`agent_sessions` / `chat_sessions` 以后都不撞车）。

### 1.2 为什么需要 `auth_sessions`：cookie 里没有身份

- HTTP 有个天生的毛病：**每个请求对服务器来说都是第一次见面的陌生人**，它不记得上一个请求是谁。
- 登录成功的那一刻，服务器生成一串**随机号码**发给浏览器（存在 cookie 里）。注意：这串号码**不含任何身份信息**，就是随机字符。
- **为什么不把身份直接写进 cookie？** 因为 cookie 在用户自己手里，**能随便改**。写 `username=ogliu` 进去，用户改成 `username=别人` 就冒充成功了。
- 所以服务器得**自己记一份**：「这串号码 = 谁、什么时候作废」。这份记录，就是 `auth_sessions` 里的一行。
- 之后你每次请求：浏览器自动带上号码 → 服务器把它算一遍 sha256 → 拿结果查这张表 → 查到就知道你是谁。

**每次刷新、点页面、提交表单，都在查这一张表。** 不是"某个功能需要它"，是"登录之后的每一次请求都需要它"。

### 1.3 先破掉几个误解（不破掉，下面的字段表读不懂）

| 容易以为 | 实际上 |
|---|---|
| cookie 里存着「我是谁」 | 只存一串随机号码；「号码 → 谁」全靠查这张表 |
| 表里有行 = 有人登录着 | **过期的行还躺在里面**，要带上 `expires_at > 现在` 才算数 |
| 多设备应该有「设备」字段 | 表**根本不关心设备**。一行 = 一处登录，行数就是设备数；"iPhone / Chrome"那种设备名是另一个功能（活跃设备列表）才需要记 |
| 一个账号只能有一行 | **每登录一次加一行**，所以同一个账号可以有很多行 |
| 「在线」=「登录着」 | 登录着 = 手里有还没过期的通行证。29 天没打开过网站也仍然"登录着" |
| 一直在用就不会过期 | 有效期**从"登录那一刻"算 30 天，不续期**。天天来，第 31 天照样要重新登录 |

### 1.4 一行的一生

```
登录成功              → 加一行（有效期 = 登录时间 + 30 天）
你每次访问             → 查这一行（不改数据）
点「退出登录」          → 删掉这一行
30 天到点             → 那行作废（行还留着，等下一次有人登录时被顺手清理）
一直没退、也没到点      → 就一直在那儿，你每次来都靠它认你
删掉账号              → 它的所有行一起删（外键 CASCADE）
```

一台设备一行：手机登录一行、电脑登录一行，互不干扰；**删一行只让那一处掉线**（这就是"让某台设备退出"的原理）。

### 1.5 如果没有这张表会怎样

两条路，都比现在差：

1. **还是存随机号码（我们现在这样）**：没有表，服务器没法把号码翻译成"谁"，**每次刷新都会掉线** —— 登录根本保持不住。
2. **改成把身份写进 cookie 并签名防篡改**（就是 JWT / 签名 cookie 那套，是真实存在的方案）：不用表也能保持登录，但**签出去的凭证收不回来**——
   - 点"退出登录"只能删掉浏览器里那份，被复制走的那份照样用到过期
   - 改了密码，旧设备上**踢不掉**
   - 删掉账号，那张"通行证"还能用到期满
   - 做不了"现在谁登录着"

所以这张表换来的，就是 **「可撤销」** 这一个能力。至于"活跃设备列表""在线人数"，都是它的**副产品**（一行天然代表一处登录），做不做都不影响它存在的理由 —— 它不为任何功能服务，它就是「登录状态」本身的存放处。

### 1.6 常用查询（Navicat 里直接跑）

```sql
-- 现在有几个人登录着（去掉过期行、按人去重）
select count(distinct user_id) from auth_sessions where expires_at > strftime('%s','now')*1000;

-- 每人几处登录、其中有几处还有效
select u.username, u.username_key, count(s.id) as 通行证,
       sum(s.expires_at > strftime('%s','now')*1000) as 还有效
from users u left join auth_sessions s on s.user_id = u.id
group by u.id order by u.id;

-- 把毫秒时间戳看成人能读的时间（Navicat 显示的是 1791093204516 这种数字）
select s.id, u.username,
       datetime(s.created_at/1000, 'unixepoch', '+8 hours') as 登录时间,
       datetime(s.expires_at/1000, 'unixepoch', '+8 hours') as 过期时间
from auth_sessions s join users u on u.id = s.user_id order by s.id;
```

> `left join` 与 `join` 的区别在这里很要紧：`left join` 能把「有账号、但一行会话都没有」的人（比如 `olduser`）也列出来，普通 `join` 会让这种人凭空消失。想找"谁从没登录过"，就用 `left join ... where s.id is null`。

## 二、表结构（逐列说明）

### 2.1 `users` —— 账号

```sql
CREATE TABLE IF NOT EXISTS users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT    NOT NULL,          -- 展示用，保留用户输入的大小写
  username_key  TEXT    NOT NULL UNIQUE,   -- 归一化（小写）后的唯一键
  password_hash TEXT    NOT NULL,          -- 自描述格式，见 password.ts
  created_at    INTEGER NOT NULL           -- 毫秒时间戳
);
```

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这个人的**内部编号**，`auth_sessions` 靠它指回来 | 写 `AUTOINCREMENT` 是为了**编号永不复用**：不写的话，SQLite 会把删掉的最大号让给下一个新用户，于是"同一个 id 先后是两个人"，排查时像见鬼 |
| `username` | TEXT | NOT NULL | 用户**看到**的账号名，原样保留大小写 | 展示归展示：`Alice` 就该显示成 `Alice`，不该被我们的归一化改掉 |
| `username_key` | TEXT | NOT NULL **UNIQUE** | 归一化后的账号名：去首尾空白 + 转小写。**判断"重名"和"登录找账号"都走这一列** | 唯一约束建在它上面而不是 `username` 上：否则 `Alice` 与 `alice` 会变成两个账号，而没人需要两个只靠大小写区分的账号 |
| `password_hash` | TEXT | NOT NULL | 密码的**哈希**（不是密码本身），格式见 §五 | **永不存明文**；每个账号独立的随机盐，所以同一个密码在两个人身上哈希也不同 |
| `created_at` | INTEGER | NOT NULL | 注册时间（毫秒时间戳） | 展示、排序、排查都要用。数值好比较、好相减 |

### 2.2 `auth_sessions` —— 通行证（登录状态）

```sql
CREATE TABLE IF NOT EXISTS auth_sessions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  token_hash TEXT    NOT NULL UNIQUE,      -- sha256(cookie 中的原文)
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_auth_sessions_user_id ON auth_sessions(user_id);
```

| 字段 | 类型 | 约束 | 含义（人话） | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 这一行的内部编号 | 只给数据库自己用，**不对外暴露**。真正的凭证是浏览器 cookie 里那串号码，这个 id 泄露了也没用 |
| `token_hash` | TEXT | NOT NULL **UNIQUE** | **浏览器手里那串号码的「指纹」**。cookie 里是原件，这里是复印件 | 见下方逐条解释 |
| `user_id` | INTEGER | NOT NULL，外键 → `users(id)`，`ON DELETE CASCADE` | **这行属于谁**（就是 `users.id`） | 两张表**唯一的连接点**。删用户时它的行一起删，不留"指向空用户的僵尸行"（前提：外键真的开了，见 §一 pragma） |
| `created_at` | INTEGER | NOT NULL | **这次登录发生的时间** | 与 `expires_at` 相减就是有效期 |
| `expires_at` | INTEGER | NOT NULL | **这次登录什么时候作废** = `created_at` + 30 天 | 读会话时拿它和"现在"比；过期的行会被顺手清掉。cookie 的有效期与它同源（都由 `SESSION_TTL_MS` 决定），不同源就会出现"莫名其妙掉线" |

**`token_hash` 到底是什么（值得单独讲）**

登录成功时，服务器随手生成一串 43 个字符的随机号码（例如 `Mk-zLzmkJjCLjKraJ8FGaSIqbq_mqXk9Kl1WUIQgv3o`）：

- 这串**号码本身**发给浏览器，存进 cookie
- 号码算一遍 **sha256**，结果（64 个十六进制字符，例如 `5cb17971224a8f0e…`）存进 `token_hash`

为什么存"算过的"而不是原文：**sha256 是单向的**。号码 → 指纹很容易，指纹 → 号码基本不可能。所以这个库万一泄露，偷的人只拿到一堆指纹，反推不出能用的号码，也就冒充不了你。

**你可以自己验证**（随便拿一行，用 cookie 原文算一遍，结果就是库里那串）：

```bash
printf '%s' '<cookie 原文>' | shasum -a 256
```

**`expires_at - created_at` 恒等于 30 天**（2592000000 毫秒）。在 Navicat 里随便挑一行做减法就能验证 —— 这也是"有效期 30 天"这句话唯一的意义。

**一个用户可以有多行**：会话行不是"用户的属性"，而是"一次登录的事实"。所以行数 = 有几处还登录着（八台设备就是八行）。**注意同一台设备重复登录也会多一行** —— 我们每次登录都插新行，不去覆盖旧的。

**为什么表名叫 `auth_sessions` 而不是 `sessions`**：将来做 Agent 相关开发时，"会话"会被用来指**对话线程**，那才是更常见的 `sessions`。裸词留给对话，登录凭证带上前缀 `auth_`。表名改过一次，老库由 `initSchema()` 里的幂等迁移自动改名（见 `src/lib/auth/db.ts`）。

### 2.3 `sqlite_sequence` —— 别动它

你在 `.schema` 里会看到它，但它不是我们建的表：只要表里用了 `AUTOINCREMENT`，SQLite 就自动建这张内部表，记录"每张表的自增号发到几号了"。**不手动读写、不迁移、不写进业务代码**。

## 三、总览：库在哪、怎么建、两个开关

**存储形态**：SQLite —— **整个数据库就是一个文件**。

| 环境 | 文件位置 | 谁指定 |
|---|---|---|
| 本地开发 | `data/nexus-os.db` | 代码里的默认值（`data/` 不入 Git） |
| 线上 | `/opt/nexus-os/shared/data/nexus-os.db` | 环境变量 `DATABASE_PATH`（`shared/` 跨版本保留，发布不丢库） |

**建表由代码完成**：`initSchema()` 里的 `CREATE TABLE IF NOT EXISTS`，服务启动后第一次用到数据库时执行。
生产库（文件）与测试库（内存）**共用同一份定义**——两处各写一份迟早漂移，测试就会在"结构其实不同"的库上通过。

**每个连接都会开的两个 pragma**：

| PRAGMA | 值 | 为什么 |
|---|---|---|
| `journal_mode` | `WAL` | 读写不互斥：一个长查询不会把写入卡住 |
| `foreign_keys` | `ON` | **SQLite 默认关闭外键**。不打开的话，`auth_sessions` 上的 `ON DELETE CASCADE` 只是一句注释，删用户后会话会变成"僵尸行" |

**时间戳一律 INTEGER 毫秒。** 不存字符串、不存秒：毫秒是数值，能直接比大小、能直接相减算间隔；字符串时间要解析，还容易混进不同格式。（换算成人看的时间见 §1.6 第三条查询。）

## 四、索引

| 索引 | 所在表 | 由什么产生 | 服务于哪个查询 |
|---|---|---|---|
| `sqlite_autoindex_users_1` | `users` | `username_key UNIQUE` 自动创建 | 登录时按用户名取账号、注册时判重 |
| `sqlite_autoindex_auth_sessions_1` | `auth_sessions` | `token_hash UNIQUE` 自动创建 | **每个请求**：拿 cookie 原文算 sha256 再查会话 |
| `idx_auth_sessions_user_id` | `auth_sessions` | 显式建的 | 按用户批量操作会话（如将来"登出所有设备"）、以及外键 `CASCADE` 删除时的查找 |

**为什么 `idx_auth_sessions_user_id` 要显式建**：SQLite 只会为 `UNIQUE` 与主键自动建索引，**不会**为外键建。少了它，"按用户查/删会话"就要全表扫——表一大就明显。

## 五、两类"只存派生值"的列

这是本项目在数据层最重要的一条安全约定：**库里不能有可以直接拿去用的秘密**。

| 列 | 库里存的是什么 | 原文在哪里 | 怎么校验 | 库泄露会怎样 |
|---|---|---|---|---|
| `users.password_hash` | `scrypt$16384$8$1$<盐>$<哈希>` | 只在用户脑子里 | 用同一个盐和参数重算，再 `timingSafeEqual` 比对 | 拿不到任何明文密码；**每个账号盐不同**，同密码的两个账号哈希也不同，彩虹表与撞库比对失效 |
| `auth_sessions.token_hash` | `sha256(token)` 的十六进制 | 只在用户的 cookie 里（`HttpOnly`，JS 读不到） | 把 cookie 原文再算一次 sha256 去查 | 拿不到可用的登录凭证——哈希不可逆，且服务端随时能删掉这一行（即时登出） |

一句话：**密码用"故意慢"的算法存，通行证用"不可逆"的哈希存。**

## 六、改表结构的流程（给写代码的人）

1. **先改本文**：新表/新列先在这里写清楚含义与理由（这张文档就是评审件）。
2. **再改 `initSchema()`**：建表语句一律 `CREATE TABLE IF NOT EXISTS`，可重复执行。
3. **加列用幂等检测**：`PRAGMA table_info(<表>)` 查列在不在，缺则 `ALTER TABLE ... ADD COLUMN`。
   数据量还小的时候，这比引入迁移框架更轻，也不会有"迁移状态表"这种额外概念。
4. **改表名要带迁移**：`ALTER TABLE ... RENAME TO` 写在建表之前（先建新表会让老库跳过迁移、把老行留成孤儿）。SQLite 改名不会跟着改索引名。
5. **排序记得补 `rowid` 兜底**：毫秒时间戳会撞车，SQL 不保证等值行的稳定顺序。
6. **跑门禁**（`pnpm typecheck && pnpm lint && pnpm test`），测试库是内存库，建表语句一变就会被所有用例过一遍。
7. **《开发日志》记一条**：为什么加、加了之后谁受益。

## 七、目前还没有的东西（不提前建）

| 还没有 | 什么时候再说 |
|---|---|
| 全文检索（SQLite FTS5） | 等知识库 / 笔记功能落地——那时要顺带定分词器（中英文切分行为差别很大） |
| 多对多关系的关联表 | 第一个需要多对多的功能出现时；用独立关联表，不用 JSON 数组列 |
| 活跃设备列表 | 想做"某台设备退出登录"时：除了这张表，还要额外记浏览器自报的设备信息（那是给人看的，认证用不上） |
| ORM 与迁移框架 | 现在是手写 SQL（语句少、容易看懂）；什么时候值得换见《技术栈说明》候选表 |
| 备份策略 | 库文件是一个文件，备份就是复制它——但要等真正有值得备份的数据时再定 |
