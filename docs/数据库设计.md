# 数据库设计

> 本文只回答一件事：**库里有哪些表、每个字段是什么意思、为什么这么设计。**
> 选型与连接配置（为什么是 SQLite、怎么打包、环境变量）见《技术栈说明》§3.5；某个功能为什么要这些表见 `docs/功能/`。
>
> 维护规则：**先改本文，再改代码。** 表结构的唯一权威是 `src/lib/auth/db.ts` 里的 `initSchema()`
> ——本文与代码不一致时，以代码为准，并立刻回来改本文。
> 结构有变化时，同一次改动要一起更新：本文 + `initSchema()` + 对应功能文档 + 《开发日志》。

## 一、总览

**存储形态**：SQLite —— **整个数据库就是一个文件**。

| 环境 | 文件位置 | 谁指定 |
|---|---|---|
| 本地开发 | `data/nexus-os.db` | 代码里的默认值（`data/` 不入 Git） |
| 线上 | `/opt/nexus-os/shared/data/nexus-os.db` | 环境变量 `DATABASE_PATH`（`shared/` 跨版本保留，发布不丢库） |

**建表由代码完成**：`initSchema()` 里的 `CREATE TABLE IF NOT EXISTS`，服务启动后第一次用到数据库时执行。
生产库（文件）与测试库（内存）**共用同一份定义**——两处各写一份迟早漂移，测试就会在"结构其实不同"的库上通过。

**每个连接都会开的两个 pragma**：

| PRAGMA | 值 | 为什么 |
|---|---|---|
| `journal_mode` | `WAL` | 读写不互斥：一个长查询不会把写入卡住 |
| `foreign_keys` | `ON` | **SQLite 默认关闭外键**。不打开的话，`sessions` 上的 `ON DELETE CASCADE` 只是一句注释，删用户后会话会变成"僵尸行" |

**时间戳一律 INTEGER 毫秒。** 不存字符串、不存秒：毫秒是数值，能直接比大小、能直接相减算间隔；字符串时间要解析，还容易混进不同格式。

**当前实测**：本地库与线上库的 `.schema` 输出 **sha256 完全一致**（`04fc5952…`）——两份库是同一个 `initSchema()` 的产物，不是"看起来差不多"。

## 二、表

| 表 | 一句话 | 一行的含义 |
|---|---|---|
| `users` | 账号 | 一行 = 一个人 |
| `sessions` | 登录会话 | 一行 = 一次登录（一台设备 / 一个浏览器） |
| `sqlite_sequence` | （SQLite 自己的内部表） | 见 §2.3，不要动它 |

### 2.1 `users` —— 账号

```sql
CREATE TABLE IF NOT EXISTS users (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  username      TEXT    NOT NULL,          -- 展示用，保留用户输入的大小写
  username_key  TEXT    NOT NULL UNIQUE,   -- 归一化（小写）后的唯一键
  password_hash TEXT    NOT NULL,          -- 自描述格式，见 password.ts
  created_at    INTEGER NOT NULL           -- 毫秒时间戳
);
```

| 字段 | 类型 | 约束 | 含义 | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 用户的内部编号 | `sessions` 靠它指回用户。写 `AUTOINCREMENT` 是为了**编号永不复用**：不写的话 SQLite 会把删掉的最大号让给下一个新用户，于是"同一个 id 先后是两个人"，排查时会看到灵异现象 |
| `username` | TEXT | NOT NULL | 用户看到的账号名，**保留注册时的大小写** | 展示归展示：`Alice` 就该显示成 `Alice`，不该被我们的归一化改掉 |
| `username_key` | TEXT | NOT NULL **UNIQUE** | 归一化后的账号名：去掉首尾空白 + 转小写 | 唯一约束建在**它**上面，而不是 `username` 上：否则 `Alice` 与 `alice` 会变成两个账号，而没人需要两个只能靠大小写区分的账号。登录查询与注册判重都走这一列 |
| `password_hash` | TEXT | NOT NULL | 密码的 scrypt 哈希，自描述字符串 | **永不存明文**，格式与校验见 §五 |
| `created_at` | INTEGER | NOT NULL | 注册时间 | 展示、排序、排查都要用 |

### 2.2 `sessions` —— 登录会话

```sql
CREATE TABLE IF NOT EXISTS sessions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  token_hash TEXT    NOT NULL UNIQUE,      -- sha256(cookie 中的原文)
  user_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_sessions_user_id ON sessions(user_id);
```

| 字段 | 类型 | 约束 | 含义 | 为什么这么设计 |
|---|---|---|---|---|
| `id` | INTEGER | 主键，自增 | 会话行的内部编号 | 只给数据库自己用，**不对外暴露**。对外的凭证是 cookie 里的 token，这个 id 泄露了也没用 |
| `token_hash` | TEXT | NOT NULL **UNIQUE** | cookie 里那串 token 的 `sha256` | **存哈希不存原文**：库泄露也拿不到能直接用的登录凭证（见 §五）。UNIQUE 顺带成了查询索引——**每个请求**都靠它定位会话，这是全库访问最频繁的一次查询 |
| `user_id` | INTEGER | NOT NULL，外键 → `users(id)`，`ON DELETE CASCADE` | 这条会话属于谁 | 删用户时会话跟着删，不留"指向空用户的会话"。前提是 `foreign_keys` 真的打开了（见 §一） |
| `created_at` | INTEGER | NOT NULL | 这次登录发生的时间 | 将来做"活跃设备列表"要用 |
| `expires_at` | INTEGER | NOT NULL | 失效时刻 = `created_at + 30 天` | 读会话时拿它和当前时间比；过期的行会被顺手删掉。**cookie 的 `maxAge` 与它同源**（都来自 `SESSION_TTL_MS`），不同源就会出现"莫名其妙掉线" |

**一个用户可以有多行**（手机 + 电脑各一次登录）。会话行不是"用户的属性"，而是"一次登录的事实"。

### 2.3 `sqlite_sequence` —— 别动它

你在 `.schema` 里会看到它，但它不是我们建的表：只要表里用了 `AUTOINCREMENT`，SQLite 就自动建这张内部表，用来记录"每张表的自增号发到几号了"。**不手动读写、不迁移、不写进业务代码**。

## 三、索引

| 索引 | 所在表 | 由什么产生 | 服务于哪个查询 |
|---|---|---|---|
| `sqlite_autoindex_users_1` | `users` | `username_key UNIQUE` 自动创建 | 登录时按用户名取账号、注册时判重 |
| `sqlite_autoindex_sessions_1` | `sessions` | `token_hash UNIQUE` 自动创建 | **每个请求**：拿 cookie 原文算 sha256 再查会话 |
| `idx_sessions_user_id` | `sessions` | 显式建的 | 按用户批量操作会话（如将来"登出所有设备"）、以及外键 `CASCADE` 删除时的查找 |

**为什么 `idx_sessions_user_id` 要显式建**：SQLite 只会为 `UNIQUE` 与主键自动建索引，**不会**为外键建。少了它，"按用户查/删会话"就要全表扫——表一大就明显。

## 四、列命名的约定

| 约定 | 例子 | 为什么 |
|---|---|---|
| 表名复数、小写 | `users`、`sessions` | 一张表装的是**多行**；单个实体在代码里另起名字（`User`） |
| 列名 `snake_case` | `password_hash`、`created_at` | SQL 里的通行写法；与 TypeScript 的 `camelCase` 一眼区分开 |
| 时间列以 `_at` 结尾，存毫秒时间戳 | `created_at`、`expires_at` | 见到名字就知道是"某一刻" |
| 归一化/派生出来的键以 `_key` 结尾 | `username_key` | 一眼看出"它不是用户看到的那一列" |
| 一列只存一个值 | —— | 需要多值就建关联表（能走索引），不塞 JSON 数组（只能全表扫） |

**代码里的名字与库里的名字不一样，转换只在一个地方发生**：`src/lib/auth/user.ts` 的 `toUser()` 把 `snake_case` 的行转成 `camelCase` 的对象。库里是库、代码里是代码，中间只留一道门。

## 五、两类"只存派生值"的列

这是本项目在数据层最重要的一条安全约定：**库里不能有可以直接拿去用的秘密**。

| 列 | 库里存的是什么 | 原文在哪里 | 怎么校验 | 库泄露会怎样 |
|---|---|---|---|---|
| `users.password_hash` | `scrypt$16384$8$1$<盐>$<哈希>` | 只在用户脑子里 | 用同一个盐和参数重算，再 `timingSafeEqual` 比对 | 拿不到任何明文密码；**每个账号盐不同**，所以同密码的两个账号哈希也不同，彩虹表与撞库比对失效 |
| `sessions.token_hash` | `sha256(token)` 的十六进制 | 只在用户的 cookie 里（`HttpOnly`，JS 读不到） | 把 cookie 原文再算一次 sha256 去查 | 拿不到可用的登录凭证——哈希不可逆，且服务端随时能删掉这一行（即时登出） |

一句话：**密码用"故意慢"的算法存，会话用"不可逆"的哈希存。**

## 六、改表结构的流程

1. **先改本文**：新表/新列先在这里写清楚含义与理由（这张文档就是评审件）。
2. **再改 `initSchema()`**：建表语句一律 `CREATE TABLE IF NOT EXISTS`，可重复执行。
3. **加列用幂等检测**：`PRAGMA table_info(<表>)` 查列在不在，缺则 `ALTER TABLE ... ADD COLUMN`。
   数据量还小的时候，这比引入迁移框架更轻，也不会有"迁移状态表"这种额外概念。
4. **排序记得补 `rowid` 兜底**：毫秒时间戳会撞车，SQL 不保证等值行的稳定顺序。
5. **跑门禁**（`pnpm typecheck && pnpm lint && pnpm test`），测试库是内存库，建表语句一变就会被所有用例过一遍。
6. **《开发日志》记一条**：为什么加、加了之后谁受益。

## 七、目前还没有的东西（不提前建）

| 还没有 | 什么时候再说 |
|---|---|
| 全文检索（SQLite FTS5） | 等知识库 / 笔记功能落地——那时要顺带定分词器（中英文切分行为差别很大） |
