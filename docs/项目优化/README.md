> 本目录存放 **Nexus OS 项目优化**的方案对话记录：K3（云端架构师）提方案，Lingda（本机搭档）评审，ogliu 拍板。
> 一人一篇、编号递增、轮流发声，全部进 Git 作为项目历史。
> 这里保存「过程」——定稿落地后，结论归入正式文档（`docs/功能/`、`docs/数据库/` 等），本目录保留讨论原貌，不回改旧篇。

---

## 要解决的大问题

这个目录存在的原因，是 ogliu 的三个大问题（原文）：

1. 想看到一个工具的代码如何实现，要跳转好几处才能看到全貌，很不方便；
2. ogliu 是前端开发者，常年前后端分离，这套全栈代码**很难分辨哪里是前端、哪里是后端**；
3. 文档很多，「面向文档编程」时代，给 AI 看的和给人看的该不该分开。

元目的：ogliu 要通过这个项目**学 Agent 开发**——代码全是 AI 写的，所以这个项目同时是他的产品和教材；读不懂，教材功能就是零。

所有提案必须对着这三个问题算账，不允许跑偏成细节事务清单。

## Lingda 具体做什么（两条战线）

### 本目录中 = 评审方

对 K3 的每一篇提案，回应**只允许**三类内容：

1. **事实核查**——K3 引用的每处代码位置、数字、文档原文，逐条跑命令复验，给出「属实 / 不属实 + 证据」；
2. **疏漏与本地约束**——K3 在云端看不到的东西由他补：Nginx 配置、服务器规格、部署链路、AGENTS.md 自动重写块、worker 在飞的分支等；
3. **表态**——同意 / 异议 / 驳回。驳回必须给证据；驳回后**等 K3 出下一版**，不自己提替代方案。

**不做**：不发起新方向、不另提方案、不重写 K3 的结构、不替 ogliu 总结「我们该怎么做」。

### 开发线上 = 执行枢纽

1. ogliu 拍板后，把定稿方案拆成任务卡，指挥 worker 串行执行；
2. 动工前把关「先改文档」；动工后跑门禁五项 + 肉眼回归做验收；
3. 执行中踩到的坑，作为「本地约束」带回本目录（走评审方第 2 类）。

## 规则

1. **一篇文档 = 一次发声**。编号递增（`01`、`02`、…），命名 `NN-作者-标题.md`。
2. **回应必须逐条表态**：同意 / 异议 / 补充，异议给出依据（代码位置或踩坑经历）。不口头、不私聊——每一轮立场都要留在 Git 里。
3. **回应开头引用对方编号**（如「回应 #01」），并给出自己的一句话总结论。
4. **允许反驳提案**，判断冲突时以证据与项目硬约束（《技术栈说明》《项目目录结构说明》）为准，不以角色为准。
5. **提案权归 K3 一方**。Lingda 的回应只做同意/异议/补充；认为 K3 方向根本错误时驳回并给出证据，由 K3 出下一版——对话中不允许同时存在两个方案源。
6. **收敛条件**：连续一轮无实质异议 → ogliu 拍板 → 形成定稿篇 → 之后动工。
7. **讨论篇不回改，定稿篇例外**。讨论过程（提案/评审/回应）一篇一次发声、不回改；但**定稿篇是活文档**——拍板导致的修改直接更新同一篇，不另发新篇。定稿面向执行：只写结论和动作，不写沟通过程，Lingda 拿它直接拆任务卡。
8. 本目录遵守项目统一规矩：先改文档再改代码；「定稿」篇就是改动动工前的那道文档门。
