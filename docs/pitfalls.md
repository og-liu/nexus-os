### 9. 多步任务回复出现大批量重复内容（过程产出与最终回答共用一个展示通道）

**日期**：2026-08-26

**现象**：问「agent开发中的skill，帮我做个详解」，Plan-and-Execute 拆了 3 步执行，最终回复出现四份互相重叠的长文——前三步各产一份「面向用户的成文」，收尾汇总又整合出第四份；本轮消耗 92.2k tokens，输出大半是重复文字。

**根因**：编排层设计缺陷，不是模型抽风。① 中间步骤的流式产出与最终回答走同一条 SSE delta 通道、渲染进同一个正文气泡，而步骤指令只说「完成后用自然语言汇报这一步的结果」，没告诉模型「你的输出不会直接给用户看」——模型自然每步都写成完整成文；② 职责重叠：planner 拆出了「整合撰写详解输出给用户」这种交付型步骤（该步已写成成品文章），收尾又强制执行一次汇总指令再整合一遍——同一主题至少成文两次。

**解决方案**：素材与交付分离 + 流式阶段标记双保险（commit `5e9a37b`）。编排层：planner 拆解规则禁止交付型步骤、步骤指令明确「你的输出是内部工作笔记不展示给用户」、收尾汇总是整轮唯一成文点。协议层：delta/reasoning 事件带 phase=working/final 标记，route 层对 working 内容照常透传但不累积进落库正文，前端对 working 内容不追加主气泡——即使模型仍把笔记写成成文，也不会混进用户看到的回答里。

**一句话**：中间步骤的产出永远别直接给用户看——过程归进度面板，正文气泡只留给唯一一次成文。

### 8. 进程崩溃后 running 状态永久残留，续跑按钮点了报错（孤儿状态死锁）

- **日期**：2026-08-26
- **现象**：dev server 正在跑任务时被重启（Ctrl+C / 改配置重启），刷新页面看到任务还显示「生成中」，点「继续」却报「没有可恢复的中断任务」；换话题发新消息也无法触发归档，整个会话的任务状态彻底卡死。
- **根因**：计划的终态化（running→stopped/done/failed）依赖本轮流式请求自己的 catch/收尾逻辑执行。进程被杀时这段代码没有任何机会运行，DB 里就永久躺着一个假的 running：计划卡 running → resume 校验只认 stopped，拒绝续跑；占位消息卡 running → 永远渲染假死气泡，而历史查询又排除 running，成为看不见的僵尸行。「继续」走不通、「归档」条件也不满足，两头堵死。
- **解决方案**：读取前自愈 + 内存锁判据。进程内存里维护一份「正在执行的会话」名单（模块级 Set），名单上没有的会话，其 DB 里的 running 必然来自上个已死的进程——在 chat 入口与会话详情 GET 读取数据前，把这类孤儿 running 统一翻成 stopped，交还给断点恢复/整轮归档链路接管（见 `src/lib/agent/turn-lock.ts` 的 `healOrphanRunningState`）。关键在于判据不能用「查 DB 有没有 running」（无法区分真在跑还是残留），必须用进程内的活跃名单。
- **一句话**：跨请求的生命周期状态必须有「进程死了也能自愈」的出口；判断「真在跑还是残留」只能靠进程内存，不能靠数据库本身。

### 7. 同毫秒落库的消息排序不稳定，回复跑到提问前面

- **日期**：2026-08-26
- **现象**：对话历史偶尔出现 assistant 回复排在 user 提问前面的顺序颠倒；同一毫秒写入的两条消息，两次查询的相对次序可能不一样。
- **根因**：user 消息与 assistant 占位行在同一个请求里共用同一个 `Date.now()`，created_at 完全相同（毫秒精度撞车）。SQLite 对排序键相等的行不保证稳定次序，历史查询又是「内层 DESC 截窗口 + 外层 ASC 还原正序」两段排序——两段的 tiebreak 方向不一致时，同毫秒行的相对顺序就可能翻转。
- **解决方案**：排序一律补 `rowid` 作第二排序键（`ORDER BY created_at DESC, rowid DESC`）。rowid 是插入序号天然单调递增，同毫秒时后插入的行 rowid 更大，用它做 tiebreaker 即可稳定还原真实先后，且完全不用改写入逻辑。注意双层查询要在子查询里 `SELECT rowid AS rid, *` 显式带出，外层才能引用。
- **一句话**：时间戳只精确到毫秒，同毫秒写入是常态不是异常；排序永远带 rowid 兜底，别赌数据库的稳定性。

### 6. Node 原生模块加载即崩（SIGSEGV）：NAPI 版本 + 沙箱限制

- **日期**：2026-08-26
- **现象**：better-sqlite3 编译明明成功了（build/Release 下有 .node 文件），`require` 阶段直接段错误退出（退出码 139，SIGSEGV），一行 JS 都没执行到。
- **根因**：两个独立原因叠加。① **NAPI 版本不足**：better-sqlite3 v13 的 binding.gyp 声明 `NAPI_VERSION=10`，而 Node 20.20.2 / 22.13.0 只带 NAPI 9，ABI 不匹配导致加载即崩；② **沙箱限制**：Coze 桌面端 bash 运行在 macOS Seatbelt 沙箱中（环境变量 `COZE_SANDBOX=seatbelt`，进程级强制，`env -i`/`unset` 都绕不过），禁止加载原生 .node 模块。用 nvm 的 Node v22.23.2（NAPI 10）验证立即恢复正常。
- **解决方案**：统一 Node 版本到 v22.23.2（`.nvmrc` 固化），在该版本下从源码编译 better-sqlite3；涉及原生模块的验证与测试一律在本机终端跑，不在 Coze 沙箱里做。选 Node 版本前先查 `process.versions.napi` 与依赖的 NAPI 要求是否匹配。
- **一句话**：原生模块崩溃先查 NAPI 版本匹配和运行环境沙箱，「编译成功」不等于「能加载」。

### 5. pnpm rebuild「假成功」：有 prebuild 时 node-gyp 跳过编译 + 项目路径含空格

- **日期**：2026-08-26
- **现象**：`pnpm rebuild better-sqlite3` 退出码 0、无任何输出，看似成功，但 build/Release 目录里只有 obj.target 和 stamp、没有 .node 产物；改用 node-gyp 直接编译后，clang++ 报 `no such file or directory: 'OS/node_modules/...'`，路径从空格处被截断。
- **根因**：① better-sqlite3 v13 的 binding.gyp 检测到 prebuilds 目录存在预编译产物时，会把 target 设为 `type: none` **跳过编译**——rebuild 空转一圈假装成功；② 项目目录名含空格（`Nexus OS`）时，Makefile 把空格当参数分隔符，编译命令在空格处截断必然失败。
- **解决方案**：清掉 build 缓存后强制源码编译：在 node_modules/better-sqlite3 目录下执行 `npx node-gyp rebuild --release -- -Dforce_build=1`；同时把项目目录重命名为无空格的 `nexus-os`（编辑器里重新打开新路径即可）。
- **一句话**：带 prebuild 的包 rebuild 可能根本没编译（要 `-Dforce_build=1`）；项目路径别带空格，原生工具链会把它撕碎。

### 4. 输入法组合态回车误发送（IME composition）

- **日期**：2026-08-25
- **现象**：输入法候选词还没敲定时按回车，消息被直接发送出去。比如用输入法敲几个字母、习惯按一下回车把单词"落"下来，结果对话框把这个回车当成了发送命令，聊天打到一半就提前发出去。
- **根因**：`textarea` 的 `onKeyDown` 只判断了 `Enter && !shiftKey` 就调用发送，没有区分「输入法组合输入态」（IME composition）。候选窗还开着时按回车，浏览器的 `keydown` 事件一样会触发，于是被误当成"发送回车"。
- **解决方案**：给输入框加 `onCompositionStart` / `onCompositionEnd`，用 `composingRef` 记录组合态。`onKeyDown` 里增加 `&& !composingRef.current` 条件：候选词未敲定（composition 窗口内）按回车不发送，正常输入（无候选）回车照常发送。
- **一句话**：回车发送前必须先排除 IME 组合态，否则「回车确认候选」的输入习惯会误触发送。

### 3. 深度思考档位与供应商枚举不一致（DeepSeek 传非法 low）

- **日期**：2026-08-25
- **现象**：前端「深度思考」统一渲染「低/高/最高」三档，切到 DeepSeek 模型时选「低」也能点中、能发送，但不确定到底有没有真正生效。
- **根因**：low/high/max 是前端自己定义的统一枚举，但 DeepSeek 官方 `reasoning_effort` 只认 `high` / `max` 两个值，`low` 不是合法枚举。选「低」时把 `low` 原样透传给 DeepSeek，属于未定义行为（可能被归一化到 high，也可能报错），这一档等于"假的"。而 OpenRouter（openai 方言）那边 low/high/max 映射成官方 low/medium/high 是真三档，两套供应商枚举根本不匹配。
- **解决方案**：档位不再写死三档，改成「按模型声明」。在模型注册表给每个支持思考的模型加 `thinkingEfforts` 字段（DeepSeek 系只 `["high","max"]`，Ox Alpha 是 `["low","high","max"]`），前端档位按钮按模型动态渲染、恢复偏好时按模型档位表过滤非法值，后端 route 也用同一张表兜底。默认档位跟着模型走（DeepSeek 默认 high、OpenRouter 默认 low）。
- **一句话**：档位枚举必须对齐供应商真实取值，前端统一枚举 + 原样透传 = 迟早传非法值。

### 2. 懒加载 ≠ 虚拟列表（对话消息流卡顿）

- **日期**：2026-08-25
- **现象**：对话消息流已经做了分页懒加载（每页 50 条，往上滚用 `before` 参数拉更早的），以为解决了卡顿，但长时间往上翻历史、攒到几百条之后页面还是卡。
- **根因**：懒加载是「**追加**」不是「替换」。往上滚加载更早消息时数组只增不减（`setMessages(prev => [...older, ...prev])`），已经加载回来的消息会被**全部渲染成 DOM 节点**。所以卡不卡只看「累计渲染的节点总数」，跟每页多少条无关——10 条一页滚 50 次、和 50 条一页滚 10 次，最终都是 500 个节点，一样卡。
- **解决方案**：
  - **短期**：如果真实场景很少把消息流滚到几百条，分页懒加载已经够用，不必动。
  - **根治**：上「虚拟列表」——不管内存里攒了多少条，页面上永远只渲染可视区 + 上下缓冲区那几十个节点，其余用占位撑起总高度。三个关键点：① 动态高度用 `ResizeObserver` 测量；② 流式输出高度持续增长要实时更新；③ 处理滚动位置锚定（停在中间时新内容不能把视口顶乱）。可选 `react-virtual`（TanStack Virtual）或 `react-window`，也能手写练手。
- **一句话**：懒加载管「进得慢」，虚拟列表管「存得少」，两者是两个层面，不冲突也不互相替代。

### 1. API Key 硬编码进 Git 仓库

- **日期**：约 2026-08-24
- **现象**：调大模型时图省事，把 API Key（DeepSeek / OpenRouter / Tavily 等）直接写死在代码文件里。
- **根因**：一旦 key 进了 Git 历史，即使之后删除、公开仓库也会泄露，等于把扣费凭证交出去。
- **解决方案**：一律存在本地 `.env.local`（加入 `.gitignore`，不入 Git），代码里通过环境变量读取。
- **一句话**：所有 API Key 只进 `.env.local`，永不入库、永不硬编码。
