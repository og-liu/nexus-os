# 项目目录结构说明

> 本文只回答一件事：**文件该放在哪、每个目录负责什么。**
> 技术选型、版本、工程门禁见《技术栈说明》；本文只管「位置的规矩」。
>
> 维护规则：目录结构发生变化时，**先改本文，再改代码**。
>
> **2026-11-05 起是「垂直结构」**（《项目优化 04 · 垂直迁移》定稿）：一个工具 = 一个目录
> `src/features/<工具>/`，里面按 **client / server / shared** 三层分。「看一个工具的实现要
> 跨 4 个目录、10 个文件」这件事到此为止——打开一个工具目录，前端在哪、后端在哪、纯逻辑在
> 哪，不点开文件就看得见。

## 一、总览

```
nexus-os/
│
├── src/                        # 全部源代码
│   ├── app/                    #   路由层：只有薄壳（page 一行、route 三行）
│   ├── features/               #   ★ 业务层：一个工具一个目录，内含 client / server / shared
│   ├── components/             #   通用组件：外壳、工具页公共件、shadcn 原件
│   ├── lib/                    #   基础设施层：auth / 库 / 时区 / 密钥 / 跨工具纯函数
│   ├── hooks/                  #   自定义 React Hook
│   ├── fonts/                  #   自托管字体文件（next/font 加载）
│   └── types/                  #   跨模块共享类型（第三方包缺类型时的手写声明）
│
├── docs/                       # 项目文档
├── deploy/                     # 部署物料：服务器初始化、发布脚本、Nginx 与 systemd 配置
├── .github/                    # GitHub 相关：CI/CD 流水线定义
├── public/                     # 静态资源（不经构建，按原样提供）
├── data/                       # 本地数据文件（不入 Git）
│
├── package.json                # 依赖与脚本
├── pnpm-lock.yaml              # 依赖版本锁定
├── pnpm-workspace.yaml         # pnpm 行为配置
├── .npmrc                      # pnpm 依赖目录布局（node-linker=hoisted）
├── tsconfig.json               # TypeScript 编译配置
├── next.config.ts              # Next.js 配置
├── postcss.config.mjs          # PostCSS / Tailwind 集成
├── eslint.config.mjs           # ESLint 规则
├── vitest.config.mts           # Vitest 配置（node 环境、用例位置、@/ 别名、server-only 别名）
│
├── .nvmrc                      # Node 版本固化
├── .env.example                # 环境变量模板（键名与获取方式，入库）
├── .env.local                  # 真实环境变量与密钥（不入库）
├── .gitignore                  # Git 忽略规则
│
├── AGENTS.md / CLAUDE.md       # 给 AI 编码助手看的项目约定
└── README.md                   # 项目说明（面向人）
```

**分层原则：按「谁在跑」分层。** 浏览器跑的进 `features/*/client/`，服务端跑的进
`features/*/server/`，两边都能跑的纯函数进 `features/*/shared/`。一条工具的全部实现
（页面、动作、数据访问、组件、测试）都在同一个工具目录里。

## 二、垂直结构：`src/features/<工具>/`

### 1. 三层各是什么

```
src/features/<工具>/
├── README.md          ← 这个工具的说明书：三层各文件一句职责、入口、数据表、从哪开始读
├── client/            ← 浏览器：带 "use client" 的组件与 hook
├── server/            ← 服务端：page、Server Actions、数据访问、服务端组件
│   └── api/           ← 仅抖音 / 音频 / 音乐播放器：Route Handler 的实现本体
└── shared/            ← 两端共用：纯函数（只碰纯数据，不碰 db / 文件 / 网络 / 密钥）
```

**每个工具目录带一份 `README.md`**（`src/features/<工具>/README.md`）——**它是这个工具唯一的文档**，
2026-11-05 起原来 `docs/功能/<工具>.md` 的内容已全部并入（`docs/功能/` 现在只放不属于任何工具的
页面级文档：外壳、页签栏、工具中心、登录注册、用户密钥等）。

一份工具 README 的固定骨架（沿用功能文档的节次，代码注释里的 `§N` 引用靠它对齐）：

| 节 | 内容 |
|---|---|
| 头部 | 一句话职责 + 入口 / 接口 / 数据表 / 状态四行速查 |
| 一、要什么 | 做哪些 + **主动放弃**哪些（放弃项必须写原因） |
| 二、界面 | 路由 → 版式 → 交互契约 → 状态与边界 → 响应式 |
| 三、数据模型 | `CREATE TABLE` 原文 + 设计要点（不落库的写「不涉及」） |
| 四、关键决策 | 决策点 / 选择 / 理由 / **否决的备选** |
| 五、代码结构（三层） | `client/` `server/` `shared/` 三张表（文件 → 一行职责）+ 从哪开始读 |
| 六、验收标准 | 编号清单「操作 → 可观察的结果」，必须含负面用例 |
| 七、已知的坑 | 机制 + 对策 |
| 八、依赖变更 | 新增依赖，重申「先登记《技术栈说明》再安装」 |
| 变更记录 | 每次实质修改追加一行 |

**新增工具时第一件事就是写它**——先写文档再写代码，评审时的依据就是这份 README。

### 2. 归位规则（看文件头顶三行就能判）

| 文件特征 | 去哪层 |
|---|---|
| 带 `"use client"` | `client/` |
| 带 `"use server"`（actions） | `server/` |
| 数据访问（碰 db） | `server/`，且顶部加 `import "server-only"` |
| 无标记的组件（RSC 服务端组件，如 page、首页卡） | `server/` |
| 无标记的纯函数（不碰 db / 文件 / 网络 / 密钥） | `shared/` |
| 测试文件 | 跟着各自源文件走（同层同目录） |

举例（便签）：`server/page.tsx`（页面）、`server/actions.ts`（`"use server"`）、
`server/notes.ts`（数据访问 + `server-only`）、`server/sticky-notes-card.tsx`（首页卡，
无标记 = 服务端组件）、`client/*.tsx`（4 个客户端组件）、`shared/format.ts` 与
`shared/validate.ts`（纯函数）。

**一个文件既是纯函数又碰库怎么办**：那是「混合体」，按纯/不纯切开——纯的进 `shared/`，
碰库的进 `server/` 并加 `server-only`（本次迁移里 `vault/vault.ts`、`markdown/tags.ts`、
`html/tags.ts` 三个就是这么处理的）。

### 3. `app/` 只剩两种薄壳

```ts
// src/app/(app)/tools/<工具>/page.tsx —— 一行壳
export { default, metadata } from "@/features/<工具>/server/page";

// src/app/api/**/route.ts —— 三行壳，segment config 必须留在壳里
export const runtime = "nodejs";
export const dynamic = "force-dynamic";
export { GET, POST } from "@/features/<工具>/server/api/<名>";
```

`runtime` / `dynamic` 是 **Next 读的路由段配置**，不是实现，放进 `features/` 里不生效。
这两条壳的可行性在定稿 §一 已实测过（全绿）。

### 4. 铁律

1. **`features` 之间禁止互相 import**。跨工具共用只许去 `lib/shared/`（纯函数）或 `lib/`
   基础设施层（或 `components/tools/` 的四个公共件，见 §6）。
2. **`client/` 和 `shared/` 禁止 import 任何 `server/`**（同工具内也不行）。纯函数要数据，
   由 server 层调好后传进来。两个例外：`"use server"` 的 actions（客户端调 Server Action
   本来就要 import 它）、以及 `import type`（类型在编译期被擦除，不进浏览器 bundle）。
3. **import 方向**：`app/` → features / components / lib；`features/` → lib、
   `components/ui`（shadcn 原件）、`components/tools/` 的四个公共件、`components/layout/`
   的两处外壳接线（见 §6e）。
   `features/` ↛ 其他 features、↛ `app/`、↛ `components/` 的其他目录。
4. **`server/` 下碰 db / 文件系统 / 子进程的文件必须带 `import "server-only"`**
   ——构建期兜底：一旦有人把它 import 进客户端，构建当场失败，而不是等上线才发现。
5. **新工具一律按本节结构落地**，不允许再散进 `app` / `components` / `lib` 三层。

> 铁律 1 与铁律 2 目前**靠验收时 grep 兜底，CI 还没接**（`.github/` 的拦截脚本待加）。

### 6. 共享层白名单

`features/` 允许 import 的「工具之外」的东西，只有下面这些。**这份白名单是封闭的**
——不在这里的，要么搬进某个工具，要么先在本文登记。

**a. `components/tools/` 下的四个工具页公共件**（所有工具共用，不属于任何一个工具）

| 文件 | 是什么 |
|---|---|
| `tool-catalog.ts` | 工具目录数据（slug / 名称 / 分类 / `QUICK_TOOL_SLUGS`） |
| `tool-header.tsx` | 工具页标题条（无标记 = 服务端组件） |
| `tool-mobile-bar.tsx` | 工具页移动端底栏（`"use client"`） |

`tool-filter.ts` / `category-chips.tsx` / `tool-card.tsx` / `tools-view.tsx` 是「工具中心」
这一页自己的组件，**不属于公共件**，工具页不许 import。

**b. `components/ui/`**：shadcn 生成后归本项目所有的通用组件（`modal` / `dropdown-menu` /
`toast` / `confirm-dialog` / `text-field`）。

**c. `lib/shared/`**：跨工具共用的纯函数。现有一个文件：

`http.ts`（`BROWSER_UA`）、`content-disposition.ts`（下载文件名）、`zip.ts`（打包）、

**e. 外壳接线（两处既有例外）**：

## 四、目录详解

### `src/app/` —— 路由层（只剩薄壳）

**职责：把「URL」映射到「页面」，把「请求」映射到「处理函数」。这里不写实现。**

| 路径 | 作用 |
|---|---|
| `src/app/layout.tsx` | **根布局**：`<html>` / `<body>`、字体、全局元信息；不套业务外壳（登录页与受保护页各用各的组布局） |
| `src/app/globals.css` | **全局样式**：Tailwind 引入 + 主题 CSS 变量 + 基线样式 |
| `src/app/icon.svg` | **站点图标（favicon）** |
| `src/app/(auth)/` | **路由分组**：登录 / 注册页（不套外壳）。带括号的目录只影响布局归属，**不影响 URL** |
| `src/app/(app)/` | **路由分组**：受保护页面 + 组布局（套 AppShell）；**根路由 `/` 由 `(app)/page.tsx` 承担** |
| `src/app/(app)/tools/<工具>/page.tsx` | 工具页薄壳：一行 `export { default, metadata } from "@/features/<工具>/server/page"` |
| `src/app/api/<段>/route.ts` | HTTP 接口薄壳：导出 `GET` / `POST` / `PATCH` / `DELETE` 与 segment config，实现都在 `features/*/server/api/` |

**规矩**

- 页面文件里**不写业务逻辑**，也不写组件：实现全在 `features/<工具>/server/page.tsx`。
- 只有真正的路由文件才放 `app/`：一个新工具先建 `features/` 目录，`app/` 只加一行壳。
- 路由目录名用 `kebab-case`。

### `src/features/` —— 业务层（本文 §二）

十个工具各占一个目录，三层见 §二。**新增工具从这里开始，不从 `components/` 或 `lib/` 开始。**

### `src/components/` —— 通用组件层

| 路径 | 作用 |
|---|---|
| `src/components/ui/` | **基础组件**：由 shadcn/ui 生成后归本项目所有的通用组件。源码在仓库里，可直接改 |
| `src/components/layout/` | **布局组件**：全站外壳、页头、侧边栏、页签栏、页脚 |
| `src/components/tools/` | **工具页公共件**（四个，见 §二.6）＋ **工具中心**这一页自己的组件 |
| `src/components/dashboard/` | **首页非工具卡片**：日期时间面板、时钟、常用工具卡、每日一句卡 |
| `src/components/auth/` | 登录 / 注册页的展示组件 |
| `src/components/settings/` | 设置页的展示组件 |
| `src/components/agent/` | Agent 对话组件（Agent 域，本次迁移不动） |

**规矩**

- 基础组件（`ui/`）只关心样式与交互，**不知道任何业务概念**。
- 工具自己的组件**不进这里**，进 `features/<工具>/client/`。
- 组件文件命名 `kebab-case.tsx`，与 shadcn/ui 的生成规则保持一致。
- 优先命名导出。

### `src/lib/` —— 基础设施层

**职责：不属于任何单个工具的能力。** 账户、数据库、时区、密钥、跨工具纯函数。

| 路径 | 作用 |
|---|---|
| `src/lib/auth/` | 账户 / 会话 / 数据库（`db.ts` 的 `SCHEMA` 是全库唯一权威）/ 密码 / 限流 |
| `src/lib/secrets/` | 用户密钥：AES-256-GCM 加解密、provider 注册表、读写、验活 |
| `src/lib/settings/` | 设置页的 Server Actions |
| `src/lib/agent/` | 模型注册表与供应商适配（Agent 域，本次迁移不动） |
| `src/lib/datetime/` | 时区（Asia/Shanghai）、农历 / 节日、格式化 |
| `src/lib/quote/` | 每日一句（句子库 + 取句） |
| `src/lib/navigation/` | 页签栏的路由规则 |
| `src/lib/toast/` | 通知文案（如删除回执） |
| `src/lib/shared/` | **跨工具共用的纯函数**（见 §二.6c） |
| `src/lib/*.ts`（根下六个） | `format` / `format-bytes` / `http` / `content-disposition` / `zip` / `utils` |
| `src/lib/*.test.ts` | **与该模块同目录**的单元测试 |

**规矩**

- `lib/` 里不出现 JSX，不 import React 组件 —— 逻辑与界面互不反向依赖。
- **工具的业务逻辑不进 `lib/`**，进 `features/<工具>/`；`lib/` 只放多工具共用或全站基础设施。
- 访问密钥的代码只活在服务端（`lib/` 默认是服务端；要进浏览器必须显式声明）。
- 超过约 300 行就拆（例外见 §二.7）。

### `src/hooks/` —— 自定义 Hook

存放可复用的 React Hook（`use-xxx.ts`）。**只在多个组件需要同一份状态逻辑时才抽出来**，
不要为了一次性使用提前抽象。现有 `use-dirty-fields.ts`（登录 / 注册表单共用）。

### `src/types/` —— 共享类型

只放**被两个以上模块共用**的类型。某个模块专属的类型就放在那个模块的文件里，不要全往这儿堆。

现有文件：

- `lunar-javascript.d.ts`——`lunar-javascript` 没有自带类型声明，手写最小声明（只声明用到的 `Solar` / `Lunar`），不用 `any` 兜底。
- `imagequant-bg.d.ts`——`imagequant` 只发布了 wasm-bindgen 的 JS 胶水，没带类型；只声明图片压缩用到的那几个导出。
- `ffmpeg-installer.d.ts`——`@ffmpeg-installer/ffmpeg` 没带类型；只声明 `path`。

第三方包缺类型时走同一条路：**在 `src/types/` 补一个最小 `.d.ts`**，不用 `any` 兜底。

## 五、新文件该放哪（判断流程）

按顺序问自己：

1. **它是某个工具的一部分吗？**（页面、动作、数据访问、该工具的组件或纯函数）→
   `src/features/<工具>/{client,server,shared}/`，按 §二.2 的表格选层。
2. **它是一个新工具的入口吗？** → 先建 `src/features/<工具>/`（含一份 `README.md`），再在 `app/` 加一行壳。
3. **它是「所有工具都用的纯函数」吗？** → `src/lib/shared/`（并在 §二.6c 登记）。
4. **它是账户 / 密钥 / 时区 / 数据库这类基础设施吗？** → `src/lib/<领域>/`。
5. **它是通用 UI 组件吗？**
   - 通用、无业务含义 → `src/components/ui/`
   - 属于全站外壳 → `src/components/layout/`
   - 属于工具页公共件 → `src/components/tools/`（只有那四个，新增要改本文）
6. **它是一段可复用的状态逻辑吗？** → `src/hooks/`
7. **它是「被多个模块共用」的类型声明吗？** → `src/types/`
8. **它是文档吗？** → `docs/`
9. **它是静态文件，构建时不需要处理吗？** → `public/`

> 卡住的时候默认进 `src/lib/`：**宁可先放基础设施层，也不要塞进页面。**

| 对象 | 规则 | 示例 |
|---|---|---|
| 工具目录 | `kebab-case`，与路由 slug 一致 | `features/sticky-notes/` |

## 七、红线

以下情况一经出现就应当修正，不是风格偏好：

1. **`features/A/` 里 import `@/features/B/`**（A≠B）—— 见 §二 铁律 1。
2. **`client/` 或 `shared/` import `server/` 的东西**（`import type` 与 `"use server"` 的
   actions 除外）—— 见 §二 铁律 2。
3. **`server/` 下碰 db / 文件系统 / 子进程的文件没加 `import "server-only"`**。
4. **在 `app/` 的薄壳里写实现**，或在 `features/` 里写路由段配置。
5. **页面文件里写业务逻辑** —— 逻辑属于 `features/` 或 `lib/`。
6. **单个文件超过约 300 行** —— 拆（例外见 §二.7 登记表）。
7. **密钥硬编码 / 提交 `.env.local`** —— 一旦进 Git 历史就等于泄露。
8. **把 `node_modules/` / `.next/` / `data/` 提交进仓库**。
9. **`lib/` 里 import 组件，或 `lib/` 里放某个工具的业务逻辑**。
10. **跨目录相对路径** —— 用 `@/*` 别名。
11. **修改生成物**（`next-env.d.ts`、`tsconfig.tsbuildinfo`） —— 它们会被重新生成覆盖。
