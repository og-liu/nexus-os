# 图片压缩

> 选一张（或一批）图、拖一下质量、看体积掉下来，然后把结果下载走——**原尺寸压缩**，全程在浏览器里完成，图片一个字节都不上传。

| | |
|---|---|
| 入口 | `app/(app)/tools/image-compress/page.tsx`（一行薄壳）→ 实现住在本目录 `server/page.tsx` |
| 接口 | 无 HTTP 接口，也没有 Server Action：压缩全在浏览器里发生，服务端只负责把页面发下来 |
| 数据表 | 无（不落库、不写服务器文件） |
| 状态 | ✅ 已上线（v0.9.1，2026-10-30 起） |

**这份 README 是这个工具唯一的文档**：代码结构在 §五，需求 / 界面 / 数据 / 决策 / 验收 / 坑在一～四、六、七。
原来的 `docs/功能/图片压缩.md` 已于 2026-11-05 并入本文件，章节编号保持不变。

## 一、要什么

**做**

- 工具页 `/tools/image-compress`：单张 + **批量**压缩。拖入 / 点选 / 粘贴载图，只有一个参数（质量），看到「原体积 → 新体积」，一键下载。
- **批量模式**：一次多选 / 多拖（≥ 2 张）进入批量——逐张压、逐张下载，另有「下载全部（ZIP）」与「继续压缩」；1 张仍走单张流程。上限：单张 20 MB、每批 30 张 / 200 MB（超出逐条标「已跳过」）。
- **输入白名单**：只收 **JPG / JPEG / PNG**。其余（WebP / GIF / HEIC / BMP…）一律拒绝并说明原因。
- **纯浏览器端处理**：JPG 走 **mozjpeg 的 WASM**（`@jsquash/jpeg`）按质量重编码；PNG 走 **调色板量化（imagequant 的 WASM）+ oxipng 无损收尾**。两种格式都在 Worker 里编码，输出格式不变。
- **参数**：只有一个质量滑杆（0.5–0.95，默认 0.8）。**没有「最大边长」**：输出像素尺寸恒等于原图。质量对两种格式都有效：JPG 是重编码质量，PNG 是**调色板颜色数**（0.95 ≈ 256 色、0.5 ≈ 16 色）。
- **触发方式**：**手动点「开始压缩」才编码**。选图、拖质量只更新参数；参数一改，上一份结果立刻作废（数字必须与滑杆严格对应）。
- **结果**：体积对比、省下百分比、输出尺寸、精确字节数、下载；画面上用**对比滑块**（左原图 / 右压缩后）看两版接缝。
- **继续压缩**：结果出来后一键**降一档质量、从最初原图重压**（80% → 70% → …）；到最低质量或没变小就提示，已有结果保留。
- **目录与页签栏同步**：`tool-catalog` 状态改「可用」，`tab-routes.ts` 的 `TOOL_TAB_SLUGS` 加上 `image-compress`（页签栏是显式白名单，不登记就没有标签）。

**主动放弃（本版不做，不是遗漏）**

| 放弃项 | 原因 |
|---|---|
| 目标体积模式（压到 200 KB 以内） | 要二分试压 + 多轮编码，用户拿到的还是一个看不懂的滑块位置；直接给质量，拖两下更快 |
| 格式转换（JPG ↔ PNG ↔ WebP） | 与「图片格式转换」工具职责重叠；本工具的格式规则只为「压得动」服务 |
| 按边长缩放 | 2026-10-30 联调整个移除：只做原尺寸压缩，`targetSize` 一类尺寸计算一并删掉 |
| WebP / HEIC 作为输入 | 同日收窄为白名单，只支持两种最常用的；其余交给格式转换工具 |
| 服务端压缩 / 图片上传 | 见 §四 |
| 压缩历史 / 最近处理 | 图片本身不留存，留一份记录也只是一堆文件名 |
| 裁剪 / 旋转 / 水印 / 去背景 | 都是独立工具的事，塞进来会让参数面板失去边界 |
| 保存到「文件」页 / 云同步 | 「文件」页仍是占位；压完直接下载，不引入存储与清理策略 |

## 二、界面

### 2.1 工具页 `/tools/image-compress`

与便签 / 待办工具页同构：**没有 PageHeader**，工具名与状态在 `ToolHeader`（状态点「可用」）。手机上顶部是 `ToolMobileBar`（汉堡 + 「选择图片」，图标 `ImageUp`）。

```
移动端导航行（< lg）：汉堡 + 选择图片
内容区（px-4 py-4 md:px-6 md:py-6 space-y-4）
├─ 工具信息条（ToolHeader，状态「可用」）
└─ 工作区
   ├─ 预览区（左 / 上）
   │   ├─ 空态：拖入区（虚线框 + 图标 + 三行提示）
   │   └─ 已载入：图片预览 + 顶栏（文件名 · 尺寸 · 体积）+ 右上「换一张」
   └─ 参数面板（右 / 下）
       ├─「压缩参数」→ 质量滑杆 → 「开始压缩」
       ├─「结果」→ 体积对比 / 精确字节数 / 下载 / 继续压缩
       └─ 批量时换成「合计 → ZIP / 继续压缩」
```

**空态拖入区**：整块**本身是按钮**（`role="button"` / 点击开文件框 / `Tab` 可达 / `Enter` 触发），不再塞一个「选择文件」按钮——同一件事两个入口用户会犹豫。三行提示：「把图片拖到这里」/「或点击选择文件、按 ⌘/Ctrl + V 粘贴」/「支持 JPG / PNG，单张不超过 20 MB；可一次拖入多张，**图片不会上传到服务器**」。系统文件框 `accept` 同步收窄成 `image/jpeg,image/png,.jpg,.jpeg,.png`。
拖拽悬停（`dragover` 且确实带文件）→ 边框变黑、底色 `#F5F5F5`。**`dragover` 必须 `preventDefault()`**，否则浏览器默认「打开这张图」，整页跳走。

**已载入（预览区）**

- 图片 `max-h-full max-w-full object-contain` 居中，底色 `#F5F5F5`（透明 PNG 才看得出透明）。
- 顶栏：文件名（`truncate`）+ 尺寸与体积 + 右侧「换一张」。没结果时 `4000 × 3000 · 3.0 MB`；出结果后**两版并列** `4000 × 3000 · 原图 3.0 MB → 压缩后 1.4 MB`（画面上同时有两版，只写一个数会让人以为另一侧也是那个体积）。手机上尺寸另起一行，否则文件名被挤成「p…」。
- **对比滑块**：出结果后画面中间一条竖线 + 抓手，**左原图右压缩后**；按住左右拖（鼠标 / 触屏 / 触控笔）。点击画面任意位置直接跳过去；双击回 50%；抓手 `role="slider"`、可 Tab 聚焦、`←/→` 每次 2%（`Shift` 10%）、`Home`/`End` 到两端、`aria-valuenow` 0–100。
  - 位置按**图片实际显示矩形**换算，不按容器：竖图在宽容器里左右留白，按容器算会拖到留白区还在动、图片本身不变。
  - 触屏 `touch-action: pan-y`（左右拖归滑块、上下滑滚页面）+ `select-none` + `-webkit-touch-callout: none`（挡掉长按弹「存储图片」）。
- 换图 / 卸载时 `revokeObjectURL` 掉上一张。

**批量模式（≥ 2 张）**

- 左侧预览位换成**文件列表**：白卡，头部「批量压缩 · N 张」+ 右侧「清空」；每行「序号 / 文件名 / 原始体积 → 压缩后体积 / 下载或状态」。
- 行状态：待压缩（灰）、压缩中（`Loader2`）、已跳过（红字 + 原因：超过 20 MB / GIF / 非 JPG-PNG）、压不动、失败。成功后给「下载」（`<a download>`），文件名 `<原名>-compressed.<ext>`。
- 右侧参数面板与单张共用：质量 + 「开始压缩」+ 结果区（`BatchSummary`）：压缩中「正在压缩第 N / M 张…」（串行，进度真实）；完成「合计 X MB → Y MB / -Z%」「N 张可下载 · K 张跳过或压不动」；「下载全部（ZIP）」打成一个 `compressed-images.zip`（store 模式，不二次压缩）；「继续压缩」= 质量降一档、整批重压。
- 移动端批量**不吸底**：结果区的「下载全部」与列表同屏，吸底是重复入口（2026-10-30 联调删掉）。
- **串行**压缩：WASM 编码 CPU 密集，并行只会互相拖慢并顶高内存；串行还能给真实进度。
- 压缩中改质量 / 换一批 / 清空：当前这一轮**整体作废**（列表回「待压缩」、旧结果与 object URL 一起释放），不会出现「前几张旧质量、后几张新质量」。

**参数面板**

- 白卡，分组标题用 §7.2（黑竖条）。「质量」是 `input type="range"`，`min=0.5 max=0.95 step=0.05`，右侧当前值 `80%`；下方说明「越低体积越小，画质损失越明显（PNG 会做调色板量化，颜色变少）」。
- **「开始压缩」**（通栏黑底 CTA）：页面唯一触发编码的入口。没载图时置灰；编码中换「压缩中…」+ `Loader2` 并禁用（防连点排队）。
- **编码进度**：预览上盖 `bg-white/80` 遮罩，含 `Loader2`、「正在压缩… 已用 N 秒」、进度条（`role="progressbar"`）与「大图可能要几秒到十几秒，请不要关闭页面」。oxipng 拿不到真实进度，进度条按「已用时间 / 预计时间」推进、封顶 95%——它只回答「还在动、大概多久」，**秒数是真实的**。编码跑在 Web Worker，主线程不阻塞。
- **改质量让旧结果作废**：结果区退回虚线占位「点『开始压缩』生成结果」，下载按钮一起消失——不允许「滑杆 50% 而结果是 80% 压出来的」。

**结果区**

- 空态**不摆一排破折号**（会被读成一根横线）：换成与拖入区同语言的虚线占位块，一句话说明下一步，里面不出现任何数字。
- 体积对比 `原图 3.0 MB → 620 KB` + 右侧大字 `-79%`。
- **压不动**（重编码没变小）：**不显示百分比、不出下载、不出对比滑块**，只写一行来源 + 一句原因（PNG：「重编码后反而变大了（X MB）——这张 PNG 已经压到极限了，原图就是最优结果」；质量本来生效的 JPG：「把质量调低一点，再点一次试试」）。**绝不把更大的文件递给用户**。
- 自动降过质量时补一行「质量 95% 会压得更大，已自动降到 65%」。
- 输出信息两行：`1920 × 1440 · JPG` + **精确字节数**（`6985523 字节`）——`MB/KB` 带小数必然被舍入，而验收要拿 `ls -l` 逐字节核对。
- 下载按钮「下载压缩后图片」，文件名 `<原名>-compressed.<新扩展名>`。
- **「继续压缩」**（灰底次要操作，`RefreshCw`）：点一下把质量降一档（-10%）**从最初原图重压**（不是级联，避免代际画质损失）；更小才提交并回写滑杆，到 50% 或没变小就提示，已有结果保留。

### 2.2 版式与断点

| 档位 | 版式 | 关键差别（不是缩放） |
|---|---|---|
| 移动 < md（375 起） | 单列：拖入区 / 预览 → 参数 → 结果 → 下载 | 参数各占一行，滑杆触控区加高；**单张**下载按钮**吸底**（`sticky bottom-0`），批量不吸底 |
| 平板 md ~ lg（768–1023） | 单列，参数区横排 **2 列** | 质量 / 结果并排，预览 `min-h-[300px]`；下载回到结果卡内 |
| 窄屏 PC lg ~ xl（1024–1279） | **两栏**：预览 `flex-1` + 右栏 `w-[300px]` | 参数成独立竖栏，改参数不用上下滚 |
| 宽屏 ≥ xl（1280 起） | 两栏：预览 `flex-1` + 右栏 `w-[340px]` | 预览高度按视口给（实测 `xl:h-[calc(100vh-22rem)]`：1440×900 下图片完整可见、整页不滚） |

两栏的切换点是 **lg**；三段用互斥显隐（`hidden lg:flex` / `lg:hidden`），不做 JS 读视口——首屏 SSR 不闪。
**预览区高度不许手算**：`calc()` 里的常量要在真机上量一遍再定，验收按「图片完整可见、不被压成一条缝」判定。

### 2.3 状态与边界

| 状态 | 界面 |
|---|---|
| 初始 | 拖入区；参数可用但只有默认值；「开始压缩」置灰；结果区虚线占位（不显示数字） |
| 已载入 / 等待压缩 | 预览 + 顶栏；结果区「点『开始压缩』生成结果」；无下载按钮 |
| 压缩中 | 遮罩 + 秒数 + 进度条；按钮换「压缩中…」并禁用；**主线程不阻塞** |
| 批量（≥ 2 张） | 列表逐行状态；结果区合计 / 节省 / ZIP / 继续压缩 |
| 继续压缩 | 质量降一档、从原图重压，滑杆同步；到底或压不动则提示，已有结果保留 |
| 完成 | 体积对比 + 精确字节数 + 下载可点 |
| 压不动 | 只说明原因，不出百分比 / 下载 / 对比滑块 |
| 参数已改 | 结果区退回占位，下载消失；再点一次才出与当前参数对应的结果 |
| 不在白名单 | 预览位给虚线提示「只支持 JPG / PNG 图片」+「WebP、HEIC、BMP 等暂不支持——请先转成 JPG 或 PNG」 |
| GIF / 动图 | 「GIF / 动图暂不支持」+「压缩会把动图变成单帧静图，所以这里不做」 |
| 解码失败（改名成 `.jpg` 的 txt） | 「你的浏览器打不开这个格式」+ 建议用系统「预览」导出 JPG |
| 超过 20 MB | 立刻拒绝，Toast `图片超过 20 MB`，不留半截状态 |

## 三、数据模型

**不涉及。** 无数据库表、无 Server Action、无服务器文件。

图片只活在页面的内存里：`File` → `ImageBitmap` → `canvas` → `Blob` → object URL，离开页面即释放。
这正是本工具最重要的一条设计（§四 第 1 条），写在这里是为了让后来者一眼看到：**这个功能没有后端**。

## 四、关键决策

| 决策点 | 选择 | 理由 | 否决的备选 |
|---|---|---|---|
| 压缩在哪跑 | **全部在浏览器里** | ① 服务器是 2 核小机器，几张图并发重编码就能占满、拖慢别的页面；② 不上传就没有存文件 / 限流 / 清理过期这一整套脏活；③「图片不出本机」是能直接对用户说出口的承诺 | 服务端 `sharp`（原生依赖 + 上传带宽 + 限流清理）；传上去再返回也慢一步 |
| 参数给几个 | **只有一个质量** | 少一个控件少一次犹豫，质量是唯一能直接看到体积变化的杠杆 | 质量 + 最大边长（原设计，联调移除）；「目标体积」自动逼近（用户拿不到可控感） |
| 要不要缩放 | **不缩放**，输出像素恒等于原图 | 用户要的是「同一张图小一点」，不是改尺寸；也省掉「只缩不放」「等比取整」一套规则 | 按边长档位缩（2560 / 1920 / 1280），已删 |
| 载入方式 | 拖拽 + 点选 + **粘贴** | 截图 → `⌘V` 是最短路径 | 只给点选（每次都要过一遍文件对话框） |
| 继续压缩的语义 | **质量降一档、从最初原图重压**（能更小才提交） | 从原图重压而不是级联：JPG 不叠代际损失，PNG 颜色数可以一档档降；先试压再决定，避免点一下反而把可下载结果弄丢 | 在上一次结果上级联（越压越差、收益也小）；重复点「开始压缩」（质量不变） |
| 批量怎么压 | **串行逐张** | WASM 编码 CPU 密集，并行互相拖慢、顶高内存；串行能给「第 N / M 张」真实进度 | 并行 `Promise.all`；只做单张（联调要求批量） |
| 批量怎么下载 | **逐张下载 + 打包 ZIP** | 一次触发多个下载会被浏览器拦（只给第一个或弹权限） | 循环触发 `<a download>`；用现成 zip 库（待打包的已是压缩产物，store 模式自己写更轻） |
| 编码跑在哪 | **Web Worker**（PNG 的 oxipng）；JPG 的 canvas 快，留主线程 | oxipng 是同步 WASM，放主线程把页面连动画一起冻住——联调实测「点开始压缩就卡死」 | 主线程同步跑（卡死，已踩过） |
| 原图 / 压缩后怎么比 | **对比滑块** | 切换按钮要点两次才比得出差别，分割线一眼看到接缝；拖动还能停在任意位置逐块比 | 「看原图 / 看压缩后」按钮（手机上长按还会弹系统菜单）；并排两张缩略图（细节看不清） |
| 什么时候压缩 | **点「开始压缩」才压**，改参数旧结果作废 | 要一个明确的开始动作；作废旧结果让滑杆数字与结果数字永远严格对应 | 载入即压、改参防抖重压（原设计，联调改掉） |
| 收哪些格式 | **白名单 JPG / JPEG / PNG** | 格式规则少一半，提示语也简单——不支持就直说，不留「浏览器有时能解有时不能」的模糊地带 | 收 WebP（联调改为不支持）；按扩展名猜格式（改名文件被误判） |
| GIF / 动图 | 直接拒绝 | `canvas` 只画第一帧，压完动图变静图——静默毁图比拒绝更糟 | 静默按首帧处理 |
| 白名单判断依据 | **MIME 或扩展名任一命中即放行** | 拖拽路径下 `File.type` 可能是空串；改名成 `.jpg` 的 txt 要走到解码那步才报「打不开」，不能按扩展名提前判死 | 只看 MIME（空串误杀 JPG）；只看扩展名（提示不准确） |
| PNG 输出什么 | **仍是 PNG**，调色板量化 + oxipng 收尾 | PNG 必须还是 PNG；canvas 没有 PNG 优化能力，oxipng 单用只能再紧几个点，量化才是市面水平——实测 1.5 MB → 419 KB（−73%）、10 MB → 1.7 MB（−83%） | 换 WebP（联调否决）；只做无损（几乎压不动，以为工具坏了） |
| 质量对 PNG 有效吗 | **有效：控制调色板颜色数**（0.95 ≈ 256 色、0.5 ≈ 16 色） | 颜色数就是 PNG 的「质量」；滑杆对两种格式语义一致（越低越糊 / 颜色越少） | 置灰（PNG 只剩无损的 3–5%，等于没压） |
| 元数据（EXIF / GPS） | 重编码自然丢弃，**界面说明一句** | `canvas` 不携带元数据；丢 GPS 是隐私加分，但拍摄参数也没了，摄影的人会在意 | 保留（要额外解析回写，且与「体积更小」相背）；不说（用户后来发现会当 bug） |
| 体积单位 | **1024 进制** | 与技术口径一致，和 `ls -l` / 开发者工具看到的对得上 | 1000 进制（与 Finder 一致，但和命令行对不上，验收时来回问） |
| 没变小怎么办 | **判定「压不动」**：不给百分比、不给下载，只说明原因 | 工具的意义是把图变小，给更大的文件等于帮倒忙 | 给红色 `+N%` 让用户自己判断；强行输出 WebP（替用户改格式） |
| 精确字节数 | 结果区**额外显示不加工的字节数** | 小数必然被舍入，而验收要 `ls -l` 逐字节核对 | 只显示 MB / KB（数字对不上，验收来回解释） |

## 五、代码结构（三层）

**这就是原来的「文件落点」一节。**

`client/` —— 浏览器（`"use client"`）。本工具的重头都在这层。

| 文件 | 职责 |
|---|---|
| `compress-view.tsx` | 工具页视图：版式 + 组件组合（状态都在下面两个 hook 里） |
| `use-image-compress.ts` | 单张压缩状态机：载入 / 编码中 / 完成 / 拒绝，含白名单校验、竞态守卫、object URL 生命周期、粘贴监听 |
| `use-batch-compress.ts` | 批量状态机：串行编码、逐行进度、`runId` 取消机制、ZIP 下载、清空 |
| `compress-dropzone.tsx` | 拖拽 / 点选 / 粘贴入口（整块是按钮） |
| `compress-controls.tsx` | 参数面板：质量滑杆 |
| `compress-preview.tsx` | 预览区 + 状态条（两版体积） |
| `compress-compare.tsx` | 对比滑块（拖 / 点 / 键盘 / 双击复位、按图片显示矩形换算） |
| `compress-result.tsx` | 结果区：体积对比 + 精确字节数 + 下载 + 继续压缩 |
| `batch-list.tsx` | 批量模式的文件列表 |
| `batch-summary.tsx` | 批量结果区（合计 / ZIP / 继续压缩） |
| `image-source.ts` | 「一张已载入的图片」「一次压缩结果」的类型与纯操作（从 hook 拆出，把 hook 压回 300 行内） |
| `compress-encode.ts` | 浏览器端解码 / 编码原语：JPG 走 canvas / mozjpeg，PNG 交给 Worker |
| `image-worker.ts` | PNG 的 Web Worker：`imagequant` 调色板量化 + `@jsquash/oxipng` 收尾 |

`server/` —— 服务端。本工具没有数据层，只有页面接线（所以没有 `server-only` 文件）。

| 文件 | 职责 |
|---|---|
| `page.tsx` | 工具页接线：`requireUser()` + `metadata.title = "图片压缩"` |

`shared/` —— 两端共用，只碰纯数据（可单测）。

| 文件 | 职责 |
|---|---|
| `plan-output.ts` | 输出方案决策：源图信息 → 输出格式 / 是否转码 / 后缀；输入白名单与 MIME 归一化 |
| `plan-output.test.ts` | 决策用例（GIF 不动、透明 PNG、已是目标格式等） |
| `batch-rules.ts` | 批量准入：单张 20 MB、每批 30 张、整批 200 MB |
| `batch-rules.test.ts` | 准入用例 |
| `constants.ts` | 体积上限与质量滑杆常量 |

**从哪开始读**：`client/compress-view.tsx`（版面）→ `client/use-image-compress.ts`（一张怎么压）→
`client/compress-encode.ts` + `client/image-worker.ts`（真干活）。

**边界**：路由薄壳必须落在 `app/(app)/tools/image-compress/page.tsx`（只有一行 re-export），实现住在本目录
`server/page.tsx`；不另建别名路由；**不改首页**——本工具不进首页卡片。工具信息条复用 `ToolHeader`，
移动端导航行复用 `ToolMobileBar`（`newLabel="选择图片"`、`icon={ImageUp}`）。体积格式化与 ZIP 打包
不在本目录：它们在 `lib/format-bytes.ts` 与 `lib/zip.ts`（第二个工具也要用，已上移到基础设施层）。

**另外两处不在本目录但属于本工具的文件**：`src/types/imagequant-bg.d.ts`（imagequant 胶水的类型声明）、
`public/codecs/imagequant_bg.wasm`（升级依赖时同步替换）。

## 六、验收标准

**单张**

1. 打开 `/tools/image-compress`：出现工具信息条（「图片压缩」/「图片」/「可用」）；工作区是虚线拖入区，含「把图片拖到这里」「图片不会上传到服务器」，且只提「支持 JPG / PNG」。
2. 拖入一张 4000 × 3000 JPG → **预览出现但结果区不出数字**（占位「点『开始压缩』生成结果」、无下载）；点「开始压缩」→ 结果区出现体积、节省百分比、输出尺寸、下载按钮。
3. 下载后 `ls -l` 核对：**字节数与页面显示的精确字节数完全相等**。
4. 质量 0.8 → 0.5：旧结果立刻作废（下载消失）；再点「开始压缩」→ 后者字节数更小。
5. 输出尺寸恒等于原图（4000×3000 进 → 出；800×600 进 → 出，不放大也不缩小）。
6. 带透明背景的 PNG → 输出**仍是 PNG**（`file` 看到 `PNG image data`），透明区仍透明，体积至少小一半。
7. 不透明 PNG（UI 截图）：滑杆可用、说明提到「PNG 会做调色板量化」；压缩后体积大幅变小（通常 −50%~−80%），滑杆调低后颜色更少、体积更小。
8. 截图后 `⌘V` / `Ctrl+V` → 同样载入。
9. 对比滑块：左原图右压缩后、默认 50%；拖动跟手；点击跳转；`Home`/`End` 到两端；双击回 50%；抓手可 Tab、方向键每次 2%。
10. 「换一张」→ 回拖入区，质量保留、结果清空；刷新页面 → 回到初始空态（不缓存，参数复位 0.8）。

**批量**

11. 一次拖 4 张（含 1 张 GIF）→ 批量列表 4 行，GIF 那行「已跳过 / GIF / 动图暂不支持」。
12. 点「开始压缩」→ 逐行变压缩中、结果区「正在压缩第 N / 3 张…」；完成「合计 X MB → Y MB / -Z%」「3 张可下载 · 1 张跳过」。
13. 「下载全部（ZIP）」→ `compressed-images.zip`，`unzip -t` 无错误、里面 3 个文件与逐张下载字节一致。
14. 「继续压缩」→ 质量降一档（滑杆同步）、整批重压、合计更小。
15. 「清空」→ 回空态拖入区，URL 全部释放。
16. 压缩中把质量 80% → 50% → 整批回「待压缩」、无下载、无混合质量旧结果；再点按 50% 重压。
17. 压缩中点「清空」→ 直接回空态，不会几秒后冒出半截结果。
18. 一次塞 31 张 / 超过 200 MB → 超出的行标「已跳过」并写明原因，合法那批照常能压。
19. 手机照片（EXIF 方向 6）：状态条尺寸与产物像素一致（800 × 1200），不是横躺的 1200 × 800。

**负面路径**

20. 拖入 GIF / WebP / HEIC / BMP → 各自对应提示，页面不跳走、不白屏、不留半截预览。
21. 拖入 `.txt` 改名的假图片 → 「你的浏览器打不开这个格式」，不抛未捕获异常。
22. 拖入 25 MB 的图 → Toast 超过上限，预览区仍是空态。
23. 未登录直接访问 `/tools/image-compress` → 跳 `/login`。
24. Network 面板里看不到任何把图片内容发出去的请求——「不上传」的机械证据。
25. 连续快速拖质量滑杆 20 次 → 结果区作废（不显示任何中途快照）、页面不卡死；再点一次结果对应**最后一次**的值。

**响应式**

26. 375px：单列；拖入区约 220px；参数各占一行；结果出现后下载按钮吸底通栏。
27. 768px：单列；参数横排 2 列；预览 ≥ 300px；下载回到结果卡内。
28. 1100px：两栏（预览 + 右栏 300px），改参数时图片与结果同屏。
29. 1440px：两栏（预览 + 右栏 340px），图片完整可见、整页不滚。

**门禁**

30. 载入图片后不点按钮等 3 秒：结果区仍是占位、无下载（证明不会自动压缩）。
31. 压一张较大的 PNG：遮罩 + 进度条 + 秒数在涨，**期间页面不卡顿**；压完遮罩消失、结果出现。
32. 已压过的 JPG（q28）质量拉到 95%：结果仍比原图小、滑杆自动降到实际质量并标注「质量 95% 会压得更大，已自动降到 X%」。
33. 结果出来点「继续压缩」：质量降一档、两种格式都会再变小、原图基准同一张；到 50% 再点 → 「已经到最低质量了」，原有结果与下载都在。
34. 手机上拖分割线时页面不横晃、上下仍能滚；长按画面不弹系统「存储图片」。
35. `next typegen` / `typecheck` / `lint` / `test` / `build` 全过。
36. 单测覆盖：体积格式化（B / KB / MB 边界、1024 进制、0 字节、省百分比）、输出方案（JPG → JPG + 质量生效；PNG → PNG + 质量不生效）、输入白名单（JPG / JPEG / PNG 放行，WebP / GIF / HEIC / BMP / txt 拒绝）、文件名与 GIF 判定。

## 七、已知的坑

| 坑 | 机制 | 对策 |
|---|---|---|
| 拖拽文件时整页跳到那张图 | 浏览器对 `dragover` / `drop` 的默认行为是「打开文件」 | 两者都 `preventDefault()`；`drop` 里再取 `dataTransfer.files` |
| 手机照片方向歪了 | 方向存在 EXIF 里，解码时不应用就横躺；编码搬进 Worker 后有两处解码，漏一处产物就横躺 | 主线程读尺寸与 Worker 编码**都**显式 `createImageBitmap(..., { imageOrientation: "from-image" })`；验收用方向 6 的照片钉住 |
| 大图画出来是空白 | iOS Safari 的 canvas 面积上限约 1600 万像素，超了画布直接失效 | 画布按源尺寸创建（没有更小的目标尺寸可用）。桌面 Chrome 无碍；**手机上超大图仍有风险**，20 MB 上限不等于像素上限。彻底消除只能自动降采样＝恢复缩放，联调已否决，**记为已知限制** |
| oxipng 的 wasm 把构建卡死 | `@jsquash/oxipng/optimise` 入口会连带把并行 codec 与 `wasm-feature-detect` 拉进构建，Turbopack 解析直接卡住（实测 10 分钟无进展） | 只 import 单线程 glue 子路径 `@jsquash/oxipng/codec/pkg/squoosh_oxipng.js`；wasm 由 glue 的 `new URL(…)` 交给打包器发成静态资源 |
| imagequant 的 wasm 在 Worker 里加载不了 | 包入口是 `import * as wasm from "./imagequant_bg.wasm"`（wasm-bindgen bundler 目标），打包器在 Worker 里解析不了，运行时**一直停在压缩中且无报错** | 只用 JS 胶水 `imagequant/imagequant_bg.js`，wasm 从 `public/codecs/imagequant_bg.wasm` 手动 `fetch + WebAssembly.instantiate`，再 `__wbg_set_wasm` |
| 大 PNG 压缩耗时、页面像卡死 | 量化与 oxipng 都是 CPU 密集的**同步** WASM；1.1 MP 约 1 s、4.8 MP 约 3 s，放主线程会冻住动画 | 放进 Web Worker；遮罩里给进度条 + 真实秒数 + 「不要关闭页面」；oxipng 级别取 2 |
| JPG 自动降档可能编码多次 | 每次 -5%、最多 10 次；4000×3000 一次 mozjpeg 约 0.5 s | 在 Worker 里跑；只降必要的次数（一旦变小就停） |
| 调色板量化的画质代价 | 真彩 PNG 压成较少颜色的调色板，渐变可能出现色带、透明边缘略锯齿 | 默认 0.8（约 200 色）、最高 0.95（256 色）；「继续压缩」时提示质量在下降；PNG 仍保留透明 |
| 输出比原图还大 | PNG 无损 / 量化后再用 canvas 重编码成真彩 PNG 会涨（实测 6.9 MB → 9.3 MB）；JPG 极高质量 + 小图也可能涨 | 编码完先比字节数：**没变小就判定压不动**，只说明原因、不生成下载、不出滑块 |
| 连点开始压缩 / 编码途中改参数 | 每次编码都要重画一张 4000px 的图，排队会把主线程和内存拖垮 | 编码中禁用按钮（第一道）+ 回调带自增序号丢弃过期结果（第二道） |
| 结果与参数对不上（乱序） | `toBlob` 是异步的，连续调用返回顺序不保证 | 每次任务带自增序号，序号不是最新就丢结果 |
| 内存泄漏 | 每次重压都生成 object URL，不 revoke 会一直占 | 换图 / 重压 / 卸载时 `revokeObjectURL`（在 `useEffect` 清理里成对处理） |
| 手机上拖滑块时页面跟着滚 / 长按弹系统菜单 | 触屏默认把横向拖动当滚动；长按图片会弹「存储图片」 | 对比层 `touch-action: pan-y` + `select-none` + `-webkit-touch-callout: none`；只给分割线绑交互 |
| 体积数字与 Finder 对不上 | Finder 用 1000 进制，本工具用 1024，同一文件差约 5% | 文档与验收都以**字节数**为准；界面另给一行精确字节数 |
| 换了图但预览还是旧的 | object URL 变了而 `<img src>` 复用了同一节点 | `<img key={url}>` 强制重建 |
| 批量一次触发多个下载被拦 | 浏览器限制「同一手势触发多次下载」 | 给「逐张下载」+「下载全部（ZIP）」两个出口，ZIP 一次触发 |
| 批量把内存顶满 | 十几张 4000×3000 同时解码 + 编码，ZIP 还会把全部结果再读进内存 | 串行 + 准入上限（30 张 / 200 MB）；换批 / 清空 / 卸载时逐个 revoke；ZIP 峰值是「压缩后总量 × 2」 |
| 批量压缩到一半改参数 / 清空 | 循环还在跑，结果会写进已重置的列表：前几张旧质量、后几张新质量，甚至给已删行创建 URL 释放不掉 | 每次列表 / 参数变化递增 `runId`，循环在每个检查点比对、过期整轮退出；创建 URL 前确认这一行还在 |
| 只在 Chromium 上做过完整验收 | CDP 跑的是 headless Chromium；Firefox / Safari 没有真机回归 | 关键 API 都做了存在性判断与失败提示；发版后建议在 Safari / 微信内置浏览器各点一次单张 + 批量 |
| 服务端组件里用了浏览器 API | `page.tsx` 是服务端组件，`document` / `canvas` 不存在 | DOM 操作只写在 `"use client"` 的视图里；页面只做 `requireUser()` 与渲染 |

> **已退役的坑**（方案改掉后不再存在，留作教训）：透明 PNG 转 JPEG 变黑底（现在 PNG 一律输出 PNG，不经 JPEG 编码器）；
> 「PNG 的质量滑杆骗人」（现在 PNG 走调色板量化，quality 真的控制颜色数）；HEIC「有时能开有时不能」（现在按白名单直接拒绝）；
> 粘贴事件在别的应用里不触发（文案写「在本页按 ⌘V」，不承诺系统级）。
